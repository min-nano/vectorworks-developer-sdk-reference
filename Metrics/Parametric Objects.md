# プラグインオブジェクト（PIO） — 計測記録

結論は [Findings「Parametric Objects」](../Findings/Parametric%20Objects.md)。ここには各調査で
測った環境（VW の版・OS）・使ったプローブ・見本・手順・実測の表とログ・切り分けの経緯
（潰した道・帰属の訂正）を、元の記録のまま置く。節の並びは Findings と同じにしてある（見出しは記録の言い方にしてある）。

> ここには計測の手順と結果だけを置く。結論・解釈は Findings にある。

特に断りが無ければ VW 2026 / mac・新規の空図面での実測。

## パスの型（3D / 2D）を替えた実測

- 水平材: 2 頂点の 3D ポリラインに絶対 Z を持たせて渡したところ、構造材オブジェクトは
  数百本生成されたが、**長さ 0 で画面に何も出なかった**（OIP は「スパン 0 / 長さ 0」）。
  2D ポリライン（`VWPolygon2DObj`）で渡すと描かれた。
- 鉛直材（柱・小屋束）: `CreateNurbsCurve` ＋ `Add3DVertex` で下端 → 上端の 2 点を渡した。
  `Insert3DVertex` では頂点が増えなかった。

## `VWPolygon2DObj` で `SetClosed(true)` を呼ばなかったときの実測

頂点を一周ぶん足して `SetClosed(true)` を呼ばなかったところ、**最後の頂点から最初の頂点へ
戻る辺が描かれなかった**（実機では直角三角形の**斜辺だけが出なかった**。3 辺のうち 2 辺は
出ていた）。

## ストーリバウンドと `ResetObject` 後のパス・高さの実測（#56）

[issue #56](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/56) で
実機確認（VW 2026 / mac。`probes/runtime/custom-object-path-coordinate-system/` で
実在の構造材 PIO を対象に検証。以下の値は同プローブの実行ログそのまま）。

発端: ホームズ君 IFC 取り込みプラグインで、構造材 PIO の柱 46 本が「オブジェクトとしては在るのに
長さ 0（実体無し）で図に出ない」事故が起きた
（[あちらの PR #113](https://github.com/min-nano/vectorworks-plugin-import-ifc-homeskz/pull/113)）。
[issue #59](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/59) で
「階だけが違う 2 本の `_Story` バウンド」を潰した結果は下記のとおり**白**だった。46 本の原因は
[issue #61](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/61) で
測った（下記「`ResetObject` がバウンドからパスを作り直す長さの境目の実測（#61）」）。

**観察**（鉛直材。X=Y=0 の 2 点）:

1. `CreateCustomObjectPath` に世界座標 `(0,0,572)→(0,0,3531)` のパスを渡すと、挿入点は
   `(0,0,572)`、読み戻したパスは `(0,0,0)→(0,0,2959)`（渡した差 `2959` と一致）だった。
2. `SetCustomObjectPath` は、渡した曲線がそのまま読み戻った（世界座標っぽい値を渡せば
   そのまま、相対っぽい値を渡せばそのまま）。挿入点は変わらなかった。
   実機の別報告: 挿入点Zが572のオブジェクトへ世界座標`572→3531`のパスを`SetCustomObjectPath`
   したら、実測は`1144→4103`——572だけ余計に足された。
3. 両端に `eStoryObjectBound_LayerElevation`（自階基準、offset=572/3531）を設定して
   `ResetObject` を呼ぶと、**挿入点が上端の解決済み絶対Z（3531）へ移り**、パスは
   `(0,0,0)→(0,0,-2959)` に書き換わった（符号が反転）。
4. 両方のバウンドを同じ絶対Z（3531）へ解決させて `ResetObject` すると、パスは
   `(0,0,0)→(0,0,-0.000000)` になった（`z1-z0 = 0`）。バウンドを 1 本も持たないまま
   `ResetObject` を呼んでも 0 長になった（下記「同じオブジェクトに 2 本のバウンドを書いた実測（ID 0 / 1。#59）」）。
5. わざと大きく外れた絶対Z（`0→1`）のパスで新しいオブジェクトを作り、3 と同じバウンド
   （572/3531）を掛けて `ResetObject` すると、結果は 3 と寸分違わず一致した（挿入点
   `(0,0,3531)`、パス `(0,0,0)→(0,0,-2959)`）。長さが `(0, 1e-7)` の帯にあるパスでは
   作り直されなかった（#61。下記）。

**実機で 3 周かけて切り分けた記録**（旧記録。鉛直材の場合）:

| 鉛直パス | バウンドの差 | 結果 |
| --- | --- | --- |
| 1 点 | 0 | スパン/長さ/高さ 0。オブジェクトはレイヤ原点に置かれ、offset まで VW に上書きされる |
| 1 点 | 部材高さ | OIP の値は指定どおりになるが、**長さ 0 で描かれない** |
| **2 点** | 部材高さ | **正しく描かれる** |

**検証範囲**: 上記の 1〜5 は**鉛直材**（X=Y=0 の2点）で測ったもの。水平材・斜め材（両端が
異なる X/Y を持つ）は [#73](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/73) /
[#75](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/75) で測った
（下記「鉛直でないパスで潰れ方と残差を測った（#73）」「水平成分を持つ部材で 0 長の死角を測った（#75）」）。
`eStoryObjectBound_Story`（他階基準）と `fLayerLevelType`（横架材天端等の名前付きレベル）
は下記の節で測った。

**ヘッダ／同梱実装ソースを読んだ記録**（VW 2026 SDK / mac。`sdk-grep`）:

- `CreateCustomObjectPath` には `CreateCustomObjectPathNoOffset` という別の入口がある
  （`ISDK.h`）。
- VWFC のラッパー（`VWParametricObj` のパス付きコンストラクタ・`GetObjectPath`・
  `SetObjectPath`）は `GS_CreateCustomObjectPath` 等の `extern "C"` callback を素通しで
  呼ぶだけで、座標変換のコードは SDK に同梱されていない。
- `SetObjectStoryBound` / `GetObjectStoryBound` が扱う `SStoryObjectData` はヘッダ上は
  レコード（`fBound` / `fBoundStory` / `fLayerLevelType` / `fOffset`）。
  バウンドを解決した絶対Zだけを読み取れる `GetObjectBoundElevation(hObject, id)` がある。

### `ResetObject` がバウンドからパスを作り直す長さの境目の実測（#61）

[issue #61](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/61) で
実機確認（VW 2026 / mac。`probes/runtime/reset-object-path-rebuild-threshold/` を
**2 つの図面**——事故のモデル（`_Story` バウンド。解決Z 572 / 3531）と新規の空図面
（`LayerElevation` バウンド。解決Z 2500 / 5500）——で走らせ、事故のモデルでは 3 回とも
同じ結果が出た。以下の値は実行ログそのまま）。

#### 実測: 渡したパスの長さと `ResetObject` の作り直し

手順: `CreateCustomObjectPath` でオブジェクトを作り、バウンドを 2 本書いて `ResetObject` を
呼び、パスの長さを読み戻した。

実測（基準Z 2500 / バウンドは 2500 と 5500 へ解決 ＝ 作り直されたときの長さ 3000）:

| 渡した Z の差 | `ResetObject` 後の `z1−z0` | |
| --- | --- | --- |
| `0` | `3000` | 作り直された |
| `4.5474735088646412e-13`（1 ULP） | `4.5474735150684958e-13` | **作り直されない** |
| `1.8189894035458565e-12`（4 ULP） | `1.8189894134720238e-12` | **作り直されない** |
| `1.0004441719502211e-11` | `1.0004442019768773e-11` | **作り直されない** |
| `9.999894245993346e-10` | `9.9999242453588253e-10` | **作り直されない** |
| `9.9999851954635233e-08` | `1.0002985186580708e-07` | **作り直されない**（温存の最大） |
| `3.0000001061125658e-07` | `3000` | 作り直された |
| `9.9999988378840499e-07` / `3.0000001061125658e-06` / `1.0000000202126103e-05` | `3000` | 作り直された |
| `0.001` / `0.1` / `1` / `100` | `3000` | 作り直された |

- 温存された最大が `9.9999851954635233e-08`、作り直された最小が `1.0011717677116394e-07`
  ——**1e-7 を 1.2e-10 の幅で挟んだ。**
- 基準Zを 572 / 2500 / 1,572,000 / 3,500,000 と変えても、切り替わる位置は動かなかった。
- Z の差が 1 ULP でも `dx` を 1000 や `1e-5` にすると作り直された。`dx = 9.9999999999999995e-08` ／
  `dz = 9.9999851954635233e-08`（**どの成分も 1e-7 未満**だが長さは `1.41e-7`）も
  作り直された。
- 基準Z 3,500,000 で作った個体は、パスは温存されたまま挿入点だけ 2500（ID 0 の解決Z）へ
  移った（画面上は「その場に潰れた線」）。
- 温存された値は入力とビット一致しなかった。`L` → `L + H·L²`（`H` は作り直したときの
  長さ）の形: `9.9999851954635233e-08` → `1.0002985186580708e-07`
  （差 `3.00e-11` ＝ `3000 × (1e-7)²`。事故のモデル側でも `1e-7` → `1.0002955562113858e-07`
  で差 `2.96e-11` ＝ `2959 × (1e-7)²`）。非鉛直のパスは #75 で測った（下記
  「水平成分が 1e-7 以上ある部材は…」6）。

#### 「柱 46 本が長さ 0」の事故のパス長で測った

事故の取り込みが渡していたパスは**長さ 2959**（＝3531 − 572）。この長さを作り直しに掛けると
**1 ULP（`4.54747e-13`）が残った**（下記「残差の出どころを測った（#67）」）。事故は 197 本中
46 本。**実測で確かめたのは高さ 2959 の分で、残り 45 本それぞれの高さまでは数えていない。**
実機で採った 3 地点の読み戻し（`4.54747e-13` が ①②③ とも変わらない）は、上の表の 2 行目と
同じ値である。[#56](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/56)（パスの型・
バウンドの書き方）と
[#59](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/59)（2 本の
バウンドの扱い）の切り分けは白だった。

> **帰属の記録（2 回書き直した。[issue #67](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/67) で決着）**:
> 1. 当初ここには「事故の取り込みは**両端の世界座標Zを別々に計算しており**、片方に丸めが
>    残った」＝**呼び出し側の算術**が原因だと書いていた。その後 #67 で測ると、呼び出し側は
>    厳密な整数 mm を渡しており、`CreateCustomObjectPath` はそれを**ビット一致で保っていた**
>    （65 ケース全件）。残差は作り直しの後に現れた。
> 2. [#68](https://github.com/min-nano/vectorworks-developer-sdk-reference/pull/68) では
>    出どころの候補として **mm ↔ インチの往復**（`v / 25.4 * 25.4` で戻らない値が危険）を
>    仮説として置いていた（5 点のビット一致が根拠。偶然の確率 約 7% と添えて）。
>    実機では 61 ケースで一致 35 / 不一致 26 で、「戻らないのに残差なし」も「戻るのに
>    残差あり」も出た（下記 5）。

#### 残差の出どころを測った（#67）

[issue #67](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/67) で
実機確認（VW 2026 / mac。`probes/runtime/path-z-residual-origin/` を 3 版・4 回
走らせた。最終版は 65 ケース。以下の値は実行ログそのまま）。

1. **生成の段:** `CreateNurbsCurve` ＋ `Add3DVertex` ＋ `NurbsSetPt3D`
   で作った曲線も、`CreateCustomObjectPath`（および `CreateCustomObjectPathNoOffset`）も、
   渡した世界座標をビット一致で保った——挿入点＝始点の絶対Z、局所パスの差＝渡した差。
   **65 ケース全件で誤差 0**（1 mm 〜 8002 mm。断面あり／なし・両方の入口で）。
2. **作り直し（regen）の段:** バウンドを 1 本も持たないまま `ResetObject` を
   呼んで 0 長へ潰すと、**長さによっては厳密な 0 にならず、渡した長さ L の 1〜2 ULP が
   残った**（符号は L と同じ）。この大きさは `(0, 1e-7)` の帯に入る。
3. 長さ 2959 を `0→2959` / `100→3059` / `572→3531` / `1000→3959` / `3531→6490` の
   **5 通りの端点**で渡すと、**5 件とも同じ `+4.5474735088646412e-13`**。上端を 4000 に
   固定して下端を振ると、**長さが 3428 のときだけ**残差が出た（4000 / 3900 / 3000 / 2000 は 0）。
4. 同じ長さは、**順番を変えても**（5 値 × 3 巡）・**別のレイヤでも**・
   **別の実行でも**ビット一致で同じ残差を出した。
5. `v / 25.4 * 25.4 != v`（mm ↔ インチの往復）との突き合わせ: 61 ケースで
   一致 35 / 不一致 26——「往復で戻らないのに残差なし」（1・2・13・103・813・1626・6503 …）も
   「戻るのに残差あり」（長さ −569・3428）も出た。SDK ヘッダの inline と同じ逆数形
   （`v * (1/25.4) * 25.4`）では一致 26 / 不一致 35。
6. 厳密に退化させて渡すと（L = 0）、0 のままだった。往復で戻らない値（3531・13）を
   両端に置いた 4 ケースでも残差は出なかった。

測った作り直しは `ResetObject`（バウンドを 1 本も持たないまま呼ぶ経路）である。事故の
プラグインが潰れを見たのは `SetPluginObjectStyle` を挟んだ後だったので、**同じ regen だとは
確かめていない**。事故と同じ長さ 2959 からは、ビット一致で同じ残差が出た。

実測（`ResetObject` で 0 長へ潰したときに残った長さ。基準Zは 0 / 100 / 572 / 1000 / 2000 /
3531 / 8002 を使い分けたが、**同じ L なら基準Zに依らず同じ値**になった）:

| 渡した長さ L | 潰した後に残った長さ | |
| --- | --- | --- |
| **2959** | **`+4.5474735088646412e-13`**（L の 1 ULP） | **事故の柱と同じ値** |
| 3428 | `+9.0949470177292824e-13`（2 ULP） | |
| 3518 | `+9.0949470177292824e-13`（2 ULP） | |
| 7430 | `+1.8189894035458565e-12`（2 ULP） | |
| −569 | `−1.1368683772161603e-13`（1 ULP） | 符号は L と同じ |
| 0 / 1 / 2 / 13 / 241 / 328 / 559 / 1054 / 1428 / 1857 / 1928 / 2000 / 2843 / 3000 / 3900 / 4000 / 4928 / 5333 / 5802 / 5931 / 7428 | **厳密に 0** | |

**ヘッダを読んだ記録**（`sdk-grep`。上の実測とは独立）: `Kernel/Math/MathCoordTypes.h` で
`WorldCoord` は `double` の mm 固定（`kWorldCoordsPerMM = 1` /
`kWorldCoordsPerInch = 25.4`）で、図面の単位設定には依らない。インチとの変換は
`InchesToWorldCoord` / `WorldCoordToInches`（後者は `kInchesPerWorldCoord = 1 / 25.4` を
**掛ける**形）。`Kernel/Base/TypesFloat.cpp` に `kNearlyEqualEpsilonForDoubles = 1e-13`・
`kWorldCoordBumpEpsilon = 1e-11` がある。

#### 残差を残す長さ L を振った実測（#71）

[issue #71](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/71) で
実機確認（VW 2026 / mac。`probes/runtime/path-collapse-residual-rule/` で
**512 ケース**——うち鉛直のパスが 506——を 1 回で走らせた。11.3 秒。以下の値は実行ログ
そのまま）。

**1. 大きさ（116 / 116）。** 残差が出た **116 件すべてが `round(m) × ULP(L)`**（`m` は L の
仮数。m < 1.5 なら 1 ULP、m > 1.5 なら 2 ULP。**`L × 2⁻⁵²`（＝`DBL_EPSILON`）を L の刻みへ
丸めた値**と同じ）**とビット一致した**。それ以外の大きさは 1 件も出なかった（3 ULP 以上も、
中途半端な値も無い）。

**2. 種を 4 つ取り、それぞれ 2⁻⁶ 〜 2⁺⁶ 倍**の 13 本を通した **52 ケースが、系列ごとに
完全に同じ**だった:

| 種（仮数） | 2⁻⁶ 〜 2⁺⁶ 倍の 13 本 |
| --- | --- |
| 2959（1.44482421875） | **全部 1 ULP**（46.234375 / 92.46875 / … / 189376 まで） |
| 3428（1.673828125） | **全部 2 ULP**（53.5625 / … / 219392） |
| 3000（1.46484375） | 全部 0 |
| 1857（1.8134765625） | 全部 0 |

#### 鉛直でないパスで潰れ方と残差を測った（#73）

[issue #73](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/73) で

#### `SetCustomObjectPath` で差し替えたパスの `ResetObject` 後とバウンドの実測

一度 `ResetObject` を通したオブジェクトのパスを `SetCustomObjectPath` で差し替えると、
その後の `ResetObject` はパスを作り直さなかった（0 長 / 1 ULP / 100 /
階の間隔の倍、いずれも渡したパスがそのまま残った）。その `ResetObject` の後、
バウンドのレコードのほうが差し替えたパスへ合わせて書き換わっていた——ID 0 の解決Zは
差し替えたパスの始点の絶対Zに、ID 1 の解決Zは終点の絶対Zに、それぞれ厳密に一致した。
書き換わったのは `fOffset` だけで、`fBound` / `fBoundStory`（基準の階）/
`fLayerLevelType`（レベル種別）は変わらなかった。
`LayerElevation`（[#61](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/61)）と
`_Story`（[#63](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/63)）の
両方で測った。

- #61（`LayerElevation`）では ID 0 が動かなかった。そのときは差し替えたパスの始点を常に
  挿入点（＝ID 0 の解決Z）と一致させていた。#63 で始点をずらすと ID 0 の `fOffset` も
  書き換わり、挿入点もその始点へ動いた（下表 4〜6 行目）。
- `fOffset` は負にも正にもなり、上階のレベルより上を指す値（下表の `+2959`）も書かれた。

`_Story` バウンドでの実測（#63。VW 2026 / mac。

#### 差し替えで `fOffset` が書き換わった部材の階を動かした実測（#65）

[issue #65](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/65) で
実機確認（VW 2026 / mac。事故のモデル——1階 612 / 2階 3571、レベル種別 `耐力壁`
（階内 −40）で解決Z 572 / 3531、階間隔 2959——の複製で
`probes/runtime/story-move-after-path-replace/` を走らせた。以下は実行ログそのまま）。

3 体を同じ図面に並べ、`SetStoryElevation` で階を動かして読み直した（**A** ＝ 0 長へ
差し替えた事故の形。`ID1.fOffset = −2959` を持つ／**B** ＝ 差し替えていない対照／
**C** ＝ 長さ 100 を残して差し替えた形。`ID1.fOffset = −2859`）:

| 階の状態（間隔） | A（0 長だった） | B（対照） | C（100 だった） |
| --- | --- | --- | --- |
| 元のまま（2959） | **0** | 2959 | 100 |
| **上階 +100**（3059） | **100** | 3059 | 200 |
| 上階を戻す（2959） | **0** | 2959 | 100 |
| **自階 +100**（2859） | **−100**（上下が逆） | 2859 | 0 |
| 自階を戻す（2959） | **0** | 2959 | 100 |

- どの段階でも実体は「ID 0 の解決Z → ID 1 の解決Z」ちょうどだった（端点の絶対Zと解決Zが
  5 段階とも一致）。表の全 15 マスが **長さ ＝ 現在の階間隔 − 差し替え時点の階間隔 ＋
  差し替えたパスの長さ** に合う（A は `2859−2959+0 = −100`、C は `3059−2959+100 = 200`）。
- 自階を上げると A が `−100`（始点のほうが終点より高い）になった。描画がどうなるかは
  測っていない。
- `SetStoryElevation` の後に**こちらは何も呼ばずに**読んだ時点で、3 体とも新しい階高どおりの
  長さになっていた（その後に `ResetObject` を呼んでも 1 ビットも動かなかった）。
  `SetStoryElevation` の時点で作り直しているのか、読み出しが引き金かは切り分けていない。
- 階を動かしても `fBound` / `fBoundStory` / `fLayerLevelType` / `fOffset` はすべて据え置きで、

別の測定（#61）: パスに触らずバウンドだけを書き換えて 2 度目の `ResetObject` を呼ぶと、
新しい解決Zで作り直された（ID 1 の `fOffset` を 5500 → 4500 にしたら、パスは `3000` →
`2000` になった）。

#### 最初の `ResetObject` より前に `SetCustomObjectPath` で差し替えた実測

**まだ一度も `ResetObject` を通していないオブジェクト**のパスを `SetCustomObjectPath` で
差し替えてから `ResetObject` を呼ぶと、作り直しはされるが**長さが足りない**:

| 作るときに渡した長さ | 差し替えた長さ | `ResetObject` 後 | 解決済みの長さは 3000 |
| --- | --- | --- | --- |
| 100 | 0 | **2900** | 100 足りない |
| 500 | 0 | **2500** | 500 足りない |
| 100 | 100 | 3000 | 合っている |

## 線分 PIO の両端と長さ——`LineLength` の有無と `Set/GetLinearObjectPos` の実測

[`Info/Parametric Object Types.md`](../Info/Parametric%20Object%20Types.md) は「線分 PIO
（`kParametricSubType_Linear`）は行列＋**隠しパラメータ** `LineLength`（`kFieldCoordDisp`）で
形が決まる」と言う。ところが **SDK には `LineLength` という綴りがどこにも無く**（`SDKLib` の
`Include` ＋同梱の実装 `Source` の全数検索。出るのは `glm/gtx/closest_point.inl` のローカル
変数と `VWLine2D/3D::IsPtOnLine` の引数 `lineLength` だけ）、長さを返すオブジェクト変数も、
サブタイプを実行時に問い合わせる API も見つからなかった（`EPluginObjectSubType` の
`kLineLike = 10` は登録時の資源 `PExt` の値。`MiniCadCallBacks.h:1107`）。

[issue #181](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/181) で、
**実機の組み込み PIO 10 件を同じ手順に掛けた**（VW 2026 / mac・新規の空図面。
`CreateCustomObject(名前, (10000, 5000), 0°)` で作り、読み書きして読み戻した）。

- `LineLength` は `GetParamsCount` / `GetParamName` の表に出てきた（欄型 `7` ＝
  `kFieldCoordDisp`）。`VWParametricObj::GetParamReal` / `SetParamReal` で読み書きでき、
  `ResetObject` を挟むと外接もその長さになった。
- `VWParametricObj::Set/GetLinearObjectPos`（＝`GS_Set/GetEndPoints`＝`ISDK::Set/GetEndPoints`）は、
  `LineLength` を持つ PIO では `Set` で行列の i 軸と `LineLength` が書き換わり（`ResetObject`
  を待たずにその場で読み戻せた）、`Get` が両端を返した。持たない PIO では `Get` が
  `(0, 0), (0, 0)` を返し、`Set` は例外も戻り値も無く、行列も外接も 1mm も動かなかった。

### OIP でパラメータを編集した前後の行列と長さの実測

測り方は 2 段——プローブが 1 回目に読んだ値の**指紋を図形の名前へ書き込み**、利用者が OIP で
編集し、2 回目に読み直して突き合わせる（OIP の編集は SDK から起こせず、`SetParamReal` ＋
`ResetObject` で真似ると調べたいものを迂回してしまうため）。被験体は `Break Line`
（原点 (10000, 5000)・30°・`LineLength` 4321）。

```

2 回目の指紋 = VWPROBE181 g=ae021063 p=000157eb
                         ↑ 幾何は一致   ↑ パラメータは変わった
1 回目の値 = off=10000.000,5000.000;i=0.866,0.500;len=4321.000;
             ep=10000.000,5000.000,13742.096,7160.500;bw=4694.596;bh=3810.278
2 回目の値 = off=10000.000,5000.000;i=0.866,0.500;len=4321.000;
             ep=10000.000,5000.000,13742.096,7160.500;bw=4694.596;bh=3810.278
```

- 利用者が OIP でパラメータを 1 つ編集した前後で、行列（offset・i 軸）・`LineLength`・
  両端・外接のすべてが 1 桁も変わらなかった。パラメータの指紋は変わり、幾何の指紋だけが
  一致した。
- 編集せずに 2 回目を走らせると両方の指紋が一致し、プローブが「まだ編集されていない」と
  言う作りにしてある。
- `Recalculate` の中から何が見えるかは
  [issue #183](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/183) で
  測った（下記「`Recalculate` の中から見える環境を『取り込み時のリセット』と『OIP 編集』で比べた（#183）」）。

#### 条件を変えて表を比べた実測

構造材（`StructuralMember`）のパラメータは **181 件**。次のどれでも、**件数・並び・

| 比べたもの | 結果 |

- **`GetParamsCount` / `GetParamName(i)`** は、インスタンスの aux list から見つけた
  **パラメータレコード**（parametric ビットの立った format を持つ record）のフィールド数と
  フィールド名である（`GetNameOfField` は **1 始まり**なので内部で `+1` している）。

  `provider->GetParamNameAt(i)`、無ければフォーマット名と universal 名で

### `FillStyle`=6 / `PenStyle`=4 でクラス属性を当てた実測

見分けが付くように、**クラス側を黄（塗り solid・線とも `(255,255,0)`・
太さ 99）**、**per-part の色欄をマゼンタ `(255,0,255)`** にして食い違わせ、1 値 1 個体で
描いて**描かれた子の実際の属性**を読んだ。

| 書いた値 | 断面の面（型 21・全面） | 稜線（型 21・上下） |
| --- | --- | --- |
| 既定（`FillStyle`=1 カラー / `PenStyle`=1 実線） | **マゼンタ**（per-part の `FillColor`） | **マゼンタ**（per-part の `PenColor`） |
| `MemberFillStyle`=**6**（クラス属性） | **黄**・`GetFillColorByClass`=true・**子のクラスが指定したクラスになる** | マゼンタ（線は触っていない） |
| `MemberPenStyle`=**4**（クラス属性） | マゼンタ（面は触っていない） | **黄・太さ 99**（クラスの太さ）・`GetPenColorByClass`=true・**子のクラスが指定したクラスになる** |
| 両方（6 と 4） | **黄** | **黄・太さ 99** |
| `FillStyle`=5 / `PenStyle`=3（オブジェクト別） | **黒**（クラスの黄でも per-part のマゼンタでもない） | **黒・太さ 2** |

- 「オブジェクト別」で黒になった回、PIO 自身の属性は既定（黒）だった。
- 構造材の欄だけを書いた回、中心線と端部はそれぞれの `CenterlinePenStyle` / `CapsPenStyle`
  のまま描かれた。

### `AttributesMode` は 4 択だが、`ResetObject` 後の描画には効かなかった

`AttributesMode`（179）と `AttributesMode3D`（180）の選択肢は
**0＝オブジェクト / 1＝線種 / 2＝クラス / 3＝マテリアル**（上の表）。ローカライズ名は
どちらも「使用する属性設定:」である。

**0〜3 を振っても描画は 1 か所も変わらなかった**（1 値 1 個体・4 通り。
PIO 自身を目立つクラスへ入れ、per-part の色をマゼンタにして振った——どの値でも
per-part のマゼンタが出続けた）。**値は書けていて読み戻せる**（`GetParamValue` が
書いた値を返す）。
**VW へ戻った後に読み直しても同じ**（[#245](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/245)。
4 個体 × 描かれた子 7 つの塗り・線・太さ・クラスを、書いた直後・ランループの後・undo
イベントを閉じた後・戻った後の 4 時点で読み、変わった欄は 0。どの値でも子は
塗りマゼンタ・稜線マゼンタ・クラスの黄は 0 か所のまま）。

### クラス欄（欄型 18 = `kFieldClassesPopup`）の書き方を比べた

| 書き方 | `GetParamValue` の読み戻し | `ResetObject` 後 | `GetParamClass` |
| --- | --- | --- | --- |
| `SetParamValue(索引, クラス名)` | **クラス名** | **残る** | 空 |

### 真偽欄の読み戻し（文字列は `True` / `False`）

`SetParamBool(索引, false)` の後、`GetParamValue(索引)` は **`False`** を返した（`0` では
ない）。この調査の 1 版目は、書いた `"0"` と読み戻した `"False"` を突き合わせて「戻された」と
誤判定した。

### `ResetObject` を繰り返したときの undo の置き石（型 90）の数

構造材 1 本へ `ResetObject` を繰り返すと、PIO の子に
`kUndoPlaceholderNode`（型 90）が**1 回につきちょうど 1 つ**増えた（30 回で 29 個。
5 回刻みで実測）。プローブは undo イベントを開かない
（[Undo](../Findings/Undo.md)）。

- undo イベントを閉じても、VW へ戻った後も減らなかった（[#245](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/245)。5 回で 5 個、
  1 つ `DeleteObject` しても 5 個のまま）。

- 描かれた子の数は 30 回まで 7 つのまま保たれた。
- 同じ個体で `AttributesMode` を 0→1→2→3 と振った回では、型 84（3D 実体）と
  断面のポリラインが消え、値を既定へ戻しても戻らなかった。`ResetObject` を 30 回
  繰り返すだけの個体では消えなかった。何が消したかはこの調査では切り分けず、
  [issue #166](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/166) で
  測った（下記「構造材 PIO の子が消えた件を表示欄と属性モード（`AttributesMode`）で切り分けた（#166）」）。
- この節の実測はすべて 1 値 1 個体で採り直したものである。

### 取り込みの形（構造材＝クラススタイル・被覆と中心線は非表示・端部は両端）で 1 本作った実測

実機確認（次のコードで 1 本作り、読み戻しと描かれた子を確かめた）。

```cpp
VWParametricObj pio(member);                 // CreateCustomObjectPath で作った構造材
const char* const kFaces[] = { "_Above", "_At", "_Below" };
for (const char* face : kFaces) {
    // 構造材＝クラススタイル（面 6 / 線 4）。クラス欄は**名前**で書く。
    pio.SetParamValue(TXString("MemberClass")     + face, TXString("木構造_柱"));
    pio.SetParamValue(TXString("MemberFillStyle") + face, TXString("6"));  // 面の属性＝クラス属性
    pio.SetParamValue(TXString("MemberPenStyle")  + face, TXString("4"));  // 線の属性＝クラス属性
    pio.SetParamBool (TXString("MemberDisplay")   + face, true);
    // 被覆と中心線は非表示。
    pio.SetParamBool(TXString("CoverDisplay")      + face, false);
    pio.SetParamBool(TXString("CenterlineDisplay") + face, false);
    // 端部は両端（＝始端と終端の両方を表示。これは既定でもある）。
    pio.SetParamBool(TXString("StartCapDisplay") + face, true);
    pio.SetParamBool(TXString("EndCapDisplay")   + face, true);
}
gSDK->ResetObject(member);                   // 1 回で足りる
```

結果（実行ログ）:

- 書いた値は**全部残った**——`MemberDisplay` / `StartCapDisplay` / `EndCapDisplay` が
  3 面とも true、`CoverDisplay` / `CenterlineDisplay` が 3 面とも false、
  `MemberFillStyle`=6・`MemberPenStyle`=4・`MemberClass`＝クラス名。
- 描かれた子は 7 → **6 に減り、中心線の子（型 21・`(0,0,3000,0)`）が消えた**。
- 断面の面は**クラスの塗り色**・`GetFillColorByClass`=true・クラスは指定したもの。
  稜線は**クラスの線色と太さ**・`GetPenColorByClass`=true・同じクラス。
- **端部は 2 つとも残った**（型 5 が `x=0` と `x=3000`）。
- 被覆では子が 1 つも減らなかった（`CoverDisplay` の読み戻しは 3 面とも false）。
  被覆の厚み（`CoverTopThickness` など・索引 34〜45）の既定は測っていない（この調査は
  48 以降を採ったもの）。
- 端部の表示欄は `StartCapDisplay_<面>` と `EndCapDisplay_<面>` の真偽 2 つだった。

`d` を 100 へ書き戻して `ResetObject` すると、型 84 が戻り、高さZ も 600 へ戻った。

### `3`（カスタム）——`ProfileSymbol` を書いた実測

| 何をした | 幅Y × 高さZ | 群の子 |
| --- | --- | --- |
| `MemberType` を `3` へ書いて `ResetObject` | **60 × 60** | 型 3（`Rect`）`(-30,-30→30,30)` |
| さらに `ProfileSymbol` にシンボル定義（矩形 Y120 × Z240）を与えて `ResetObject` | **120 × 240** | 型 3（`Rect`）`(-60,0→60,240)` |

- 群の子の外接が、定義に入れた矩形と 1 の位まで一致した。
- `SetParamValue(索引, シンボル名)` と `SetParamSymDef(索引, 参照)` の両方で効いた。
- 寸法 4 欄を書いても変わらなかった。

シンボル定義は `CreateSymbolDefinition` → `AddObjectToContainer` で 2D 図形を入れる →
`ResetObject` で作った。`CreateSymbolDefinition` は名前を参照で受けて書き換えた（重複していれば
別名になる）。

### プロファイル（断面）グループを外から書いた実測

## 既定値を変えた PIO を、前に使った文書で取り込み直した実測

実機での症状: 自作 PIO の記号の離れの既定（`SParametricParamDef` に書いた値）を 4 → 200 に
変えたのに、その PIO を前に使った文書で取り込み直しても、ログはずっと `記号の離れ 4.0mm` の
ままで、記号が横架材の下へ潜って見えなかった。新しい文書では新しい既定が出た。
コードを読む限り新しい値が入るはずなので、原因を PIO の外（レイヤ・重ね順）に探して
遠回りした。

## 生成時に「オブジェクトの設定」ダイアログが出た記録

止まった。PIO 側の `OnInitXProperties` で `kObjXPropShowPrefDialogWhen` を宣言しても
1 回目には出た（定義が作られる過程で走る）。描き始める前に
`DefineCustomObject(name, kCustomObjectPrefNever)` を 1 度呼ぶと出なかった。

組み込みのドア・窓で、初めて作るときの呼び方を変えて測った
（[issue #122](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/122)。
VW 2026 / mac・新規の空図面。`probes/runtime/create-pio-with-params/` の実行ログ）。

| 初めて作るときの呼び方 | 所要 | ダイアログ |
| --- | --- | --- |
| `CreateCustomObject("Door" / "Window", …)` | 42.6 秒 / 102.7 秒 | 出た（ドア設定・窓設定。利用者の目視） |
| `CreateCustomObjectPath("Door", nil, nil, doRegen=false)` | 10.6 秒 | **出た**——再生成を止めても止まらない |

## パラメータを指定して 1 回の描画で作る経路を探した（#122）

「作る → パラメトリックレコードを書く → `ResetObject`」を 1 回の描画にできるかを
[issue #122](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/122) で
調べた（VW 2026 / mac・新規の空図面・組み込みのドア / 窓。
`probes/runtime/create-pio-with-params/` を 4 版・計 5 回走らせた。3 版目は 2 回とも同じ値）。
「作成の直後に描かれたか」は PIO の子の数と外形で判定した——描かれる前の PIO は
子が 1 つ（型 0）で、外形は PIO の種類ごとの決まった小さな枠だった。所要時間は各 1 回の
実測なので、1 本あたりの費用としては引かない。

- ヘッダを読んだ記録: 生成の入口は
  `CreateCustomObject(name, loc, angle, bInsert)` / `CreateCustomObjectByMatrix(name, matrix)` /
  `CreateCustomObjectByMatrixEx(name, matrix, bInsert)` / `CreateCustomObjectPath(name, path,
  profile, doRegen)` / `CreateCustomObjectPathNoOffset` / `CreateCustomObjectDoubleClick`。
  パラメータの値を受け取る引数も、`doRegen` 以外に再生成を止める旗も見当たらなかった。
- `CreateCustomObject` で作った直後に、ドアは子 11・外形 910、窓は子 15 だった（既定値のまま
  描かれていた）。
- `bInsert=false` でも作成直後に子 11 / 15 まで描かれていた（親は nil）。
  `CreateCustomObjectByMatrixEx(…, false)` も同じ。後から `AddObjectToContainer(h, layer)` で
  入れられ、入れただけでは子の数は変わらなかった。

### 1 回で済ませる経路と、いつもの経路（A）との差

A は `CreateCustomObject` → `Width` を 1410 に → `ResetObject`。全欄を文字列
（`GetParamValue`）で突き合わせた（ドア 672 欄・窓 618 欄）。

| 経路 | 描く回数 | ダイアログを通した文書 | ダイアログを飛ばした文書（`kCustomObjectPrefNever`） |
| --- | --- | --- | --- |
| **書式の既定値を書き換えてから `CreateCustomObject`**（`VWRecordFormatObj::SetParamReal`。作ったら戻す） | 1 | **効く**（外形 1410。既にある個体は変わらない） | **効かない**——`Width` はドア 826・窓 896 のまま（既定と同じ）。A と 11 / 15 欄違う |
| **`CreateCustomObjectPath(name, nil, nil, doRegen=false)` → `SetEntityMatrix` → 書く → `ResetObject`** | 1 | **ドアは 672 欄すべて一致**（外形・子の型の並びも一致） | **別物になる**——何も書かずに描かせるとドアは子 47・幅 1589.6（**袖 FIX 付き**の別のドア）。A0 と 67 / 61 欄違い、窓は書いた幅が外形に出ない |
| 同上で、**`CreateCustomObject` で作った個体（A0）の全欄を `SetParamValue`（文字列）で写してから**書く | 1（＋見本の 1 本） | — | **外形・子の型の並びは A と一致。ただし線の種類の欄とそこから決まる欄が 17 / 18 欄違う**（`2D…LineStyle` が A=2 / 写した側=0、`WallLineLW` など） |
| 同上で、**欄型ごとの口で写してから**書く（下記「手順」） | 1（＋見本の 1 本） | — | **全欄一致**（ドア 672・窓 618 欄とも差 0。外形・子の型の並びも一致） |

- ダイアログを飛ばした文書で、書式（F）と何も書かずに作った A0 は 61 / 98 欄違った
  （`__version` 0→3160、`DoorClass` None→一般、`SizeReference` Rough Opening→Leaf Size、
  `ROWidth` 0→910 など）。1 版目（ダイアログを OK で通した文書）では書式経路が効いた。
- Path の入口（`doRegen=false`）で何も書かずに描かせると、書式とも A0 とも違う値の組
  （`DetailLevel` Low、`SideLights` True、インチ由来の 19.05 / 25.4 など）で描かれた。
  ダイアログを通した文書ではドアが全欄一致した。
- 線の種類の欄（欄型 `kFieldPenStyle` = 26）は、`SetParamValue` で文字列 `2` を書いても
  `0` が残った（写した直後、`ResetObject` の前に読み戻して確認。ドア・窓とも 15 欄）。
  そのまま `ResetObject` すると、そこから決まる整数の欄（`WallLineLW` / `SwingLW` /
  `OpDirectionLineWeight` など、欄型 1）も A と違う値になった。`SetParamPenStyle` で写すと
  差 0 だった。同梱の `VWParametricObj::SetParamValue` は `kFieldText` とそれ以外で書き方を
  分けている、までは読んだ（文字列で写らない理由は突き止めていない）。

### 手順（1 本 1 回で、いつもの経路と同じ個体を作る）

```cpp
// 0) 文書ごとに 1 度: ダイアログを止める
gSDK->DefineCustomObject(name, kCustomObjectPrefNever);

// 1) 文書ごと・種類ごとに 1 度: 見本を普通に作る（この 1 本は作成時に描かれる）
MCObjectHandle sample = gSDK->CreateCustomObject(name, WorldPt(0, 0), 0.0, true);
VWParametricObj from(sample);

// 2) 1 本ごと: 描かずに作る → 置く → 見本を欄型ごとの口で写す → 値を書く → 1 回描く
MCObjectHandle h = gSDK->CreateCustomObjectPath(name, nil, nil, false);
gSDK->SetEntityMatrix(h, placement);          // 位置・角度（描き直さない）
VWParametricObj to(h);
for (size_t i = 0; i < from.GetParamsCount(); ++i) {
    const TXString p = from.GetParamName(i);
    switch (from.GetParamStyle(p)) {
    case kFieldPenStyle:  to.SetParamPenStyle(p, from.GetParamPenStyle(p)); break;
    case kFieldPenWeight: to.SetParamPenWeight(p, from.GetParamPenWeight(p)); break;
    case kFieldFill:      to.SetParamFill(p, from.GetParamFill(p)); break;
    case kFieldColor:     to.SetParamColor(p, from.GetParamColor(p)); break;
    case kFieldClass:     to.SetParamClass(p, from.GetParamClass(p)); break;
    case kFieldBuildingMaterial: to.SetParamBuildingMaterial(p, from.GetParamBuildingMaterial(p)); break;
    case kFieldTexture:   to.SetParamTexture(p, from.GetParamTexture(p)); break;
    case kFieldSymDef:    to.SetParamSymDef(p, from.GetParamSymDef(p)); break;
    default:              to.SetParamValue(p, from.GetParamValue(p)); break;
    }
}
to.SetParamReal("Width", width);              // 欲しい値を書く
gSDK->ResetObject(h);                         // ここで 1 回だけ描く
```

（上は測ったときの写し方。）

- 実測でずれが出たのは線の種類（欄型 26）だけだった。`switch` のうち、ドア・窓で
  効き目を確かめたのは `kFieldPenStyle` の枝で、他の欄型はドア・窓に文字列で写して
  差が出なかった。
- 見本は図面に 1 本残る。写し終えた後で消してよいかは確かめていない。
- 所要は各 1 回の実測で、`ResetObject` 1 回が 15〜19ms、作成時の 1 回が 10〜20ms。
  写す手間は測っていない。

### `SetEntityMatrix` で位置と角度を与えた実測

`CreateCustomObjectPath(name, nil, nil, doRegen=false)` は原点・角度 0 に置く。
`SetEntityMatrix`（0.00ms）で原点 (6000, 5000)・30° を与えても子は 1 のまま
（描き直さない。undo イベントを閉じた後も VW へ戻った後も 1 のままだった——[#245](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/245)）。その後の `ResetObject` で、`CreateCustomObject(pt, 30°)` と**同じ外形・
同じ子の型の並び**になった（ドア・窓とも）。

`ResetObject` の後で `SetEntityMatrix` で動かすと、外形（`GetObjectBounds`）は古い位置の
ままだった（原点は動いている）。もう一度 `ResetObject` するとその場で追い付いた。

- 最初は同じ呼び出しの中で読んで「古い位置のまま残る」と記録した。
  [#245](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/245) で、
  ドアを `ResetObject` → `SetEntityMatrix` で +5000 動かし、時点を変えて外接を読んだ:

  | いつ読んだか | 外接 |
  | --- | --- |
  | 書いた直後（同じ呼び出しの中） | L23545 … R24455（**古い位置**） |
  | 呼び出しの中でランループを 1.5 秒回した後 | L23545 … R24455（**古い位置**） |
  | **自動で開いた undo イベントを `EndUndoEvent()` で閉じた直後** | **L28545 … R29455（新しい位置）** |
  | VW へ制御を返し、数十秒置いた後（別の走行） | L28545 … R29455（新しい位置） |

  undo イベントを閉じずに 7 分置いた回では、古い位置のままだった。

### スタイルを当てた後のバウンドの実測（#112）

[issue #112](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/112) で
実機確認（VW 2026 / mac・新規の空図面。`probes/runtime/style-story-bound-overwrite/` を
**2 度**走らせた。下記 1〜6 は 2 度とも同じ値。実行ごとに違ったのは最後の「読み戻せない
バウンド」だけ。以下の値は実行ログそのまま）。

きっかけは [#109](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/109)
の副産物で、**両端とも offset 2500 で書いた水平材にスタイルを当てたら、解決バウンドが
2500 / 5500——書いていない値——になった**。そのスタイルの元にした PIO が
バウンド 2500 / 5500 の鉛直材だった。

1. `SetPluginObjectStyle` で当てる直前と直後を `ResetObject` を挟まずに読むと、
   レコードも解決結果も 1 ビットも変わらなかった（変わったのは `styleRef` だけ）。
   その後の `ResetObject` / `UpdateStyledObjects` の後に置き換わっていた。
   - [#245](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/245): `SetPluginObjectStyle` だけを
     掛けて `ResetObject` を呼ばずにおくと、undo イベントを閉じても、VW へ戻って数十秒
     置いても、記録 1000/6500・値 `HON-GOTO`/120 のままだった。
2. 書いた `fOffset` 2500 が、`GetObjectStoryBound` で読み戻すと **5500**（スタイルの値）に
   なっていた（解決結果だけでなくレコードも）。
3. 順序を 3 通り試して 3 通りとも置き換わった。

   | 順序 | `ResetObject` 後の解決バウンド |
   | --- | --- |
   | バウンド → スタイル → `ResetObject` | 2500 / **5500** |
   | **スタイル → バウンド** → `ResetObject` | 2500 / **5500** |
   | バウンド → スタイル → **バウンドを書き直し** → `ResetObject` | 2500 / **5500** |
   | （対照）バウンドのみ・スタイル無し → `ResetObject` | 2500 / 2500（書いたとおり） |
4. 同じ材へスタイルを当て分けた。

   | 当てたスタイル（元にした PIO のバウンド） | 当てた先の解決バウンド |
   | --- | --- |
   | 2500 / 5500 | 2500 / **5500** |
   | 2500 / 2500 | 2500 / 2500（＝書いた値と同じなので変化に見えない） |
   | **バウンドを 1 本も持たない** | **0 / 0**（書いた 2500 が消える） |
5. `UpdateStyledObjects` だけ（`ResetObject` を 1 度も呼ばない）でも
   2500 / 2500 → 2500 / **5500** になった。
6. スタイルを `SetAllPluginStyleParameters(hSymDef, kPluginStyleParameter_ByInstance)` で
   作っておくと、`ResetObject` でも `UpdateStyledObjects` でも書いたバウンドが残った
   （2500 / 2500）。バウンドの名前はパラメータ表に無かった（#118 で持ち主を特定した。下記）。

バウンドを 1 本も持たない材にスタイル（2500 / 5500）を当てて `ResetObject` すると、
バウンドは 2 本生え（ID 0 / 1）、実体もスタイルどおり（2500→5500）に建った。`fOffset` は
スタイルどおり（2500 / 5500）だったが、片方の `fBound` が `EStoryObjectBound` の 3 つの値
（`_LayerElevation` / `_LayerWallHeight` / `_Story` ＝ 0 / 1 / 2）のどれでもない値で返り、
`GetObjectBoundElevation` は実体と食い違った。どの ID が壊れるかも、返る値も、実行ごとに
違った:

| | 壊れていた ID | その `fBound` | `GetObjectBoundElevation` | 実体 |
| --- | --- | --- | --- | --- |
| 1 度目 | ID 1 | `1807343432` | 0 / 0 | 2500→5500 |
| 2 度目 | ID 0 | `-1254535200` | 0 / 5500 | 2500→5500 |

2 度目は渡す前に `fBound` を 0 で埋めてから呼んでいる。両端を書いてあった材（上記 3・4）は、
どれもレコードが素直に読み戻った。

### バウンドだけ by-instance のスタイルを作った実測（`DialogStartElevationReference`。#118）

[issue #118](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/118) で
実機確認（VW 2026 / mac・新規の空図面。`probes/runtime/style-bound-only-by-instance/` を

[`probes/runtime/README.md`](../probes/runtime/README.md) に一般則として書いた）ので、
**下記の値は 1 度目と 3 度目のもの**。総当たりは 2 度とも同じ 1 件を指した。実行ログそのまま）。

```cpp
gSDK->SetAllPluginStyleParameters(hSymDef, kPluginStyleParameter_ByStyle);
```

1. 由来表（`'PSMP'`）の鍵はパラメータ名しか無い（同梱ソースを読んだ）。その **181 件を

   | 掃引 | バウンドが動いた名前 |
   | --- | --- |
   | 全件 by-style → **1 つだけ** by-instance | `DialogStartElevationReference`（他 180 件は無反応） |

3. `SetAllPluginStyleParameters(ByInstance)` の後に 181 件を読み戻すと、全件が by-instance
   だった（外れ値 0 件）。
4. `SetPluginStyleParameterType(hSymDef, 名前, 種別)` で書いた値は `GetPluginStyleParameterType`

バウンドの違う水平材 6 本
（3000/3000・3200/4000・1000/6500）へ当て、**インスタンス側にはスタイルと違う値**

走らせると、**6 本とも書いたバウンドのまま**で、パラメータは**スタイルの値に揃った**。

1. バウンドを両端とも書く
2. `SetPluginObjectStyle` でスタイルを当てる
3. **1 本ごとに `ResetObject`**
4. 最後に `UpdateStyledObjects` を 1 回

#### `UpdateStyledObjects` を流したときのバウンドと長さの実測（#125）

[issue #125](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/125) で
実機確認（VW 2026 / mac・新規の空図面。`probes/runtime/update-styled-bound-delta/` を

5 本を作っている）。以下の値はすべてその実行ログそのまま。
**群ごとにスタイルを分けてある**——`UpdateStyledObjects` は当てた全件を舐めるので、
1 本を共有すると後の群の呼び出しが前の群の材を作り直してしまう）。

上の手順の 3（1 本ごとの `ResetObject`）を省いた本（#118 の 3 本。#125 でも 1 ビット違わず
再現した）:

| 書いたバウンド | 期待する Δz | 実測 Δz | 終端の絶対Z（期待 → 実測） |
| --- | --- | --- | --- |
| 3000 / 3000 | 0 | **−3000** | 3000 → **0** |
| 3200 / 4000 | 800 | **−2200** | 4000 → **1000** |
| 1000 / 6500 | 5500 | **2500** | 6500 → **3500** |

実測（下記の表）に合う規則（バウンドが by-instance のとき）:

```
バウンドが、最後に ResetObject で作り直した時点から変わっている本:
    Δz（後） ＝ Δz（前） ＋ (自分のバウンドの span) − (スタイルのバウンドの span)

変わっていない本:
    Δz（後） ＝ Δz（前）（＝正しいまま。作り直し前の値が保たれる）
```

14 本すべての実測がこの 2 行に合った（下記）。後者が「触られなかった」のか
「正しく作り直された」のかは、この物差しでは分かれない。

ずれた 3 本も、挿入点は 0 → 3000 / 3200 / 1000 と書いた下端どおりになっていた。

**スタイルの span を替えた。** スタイルだけを span 2000（2500 / 4500）に替えて同じことをすると、**ずれ幅も 2000 になった**。

| 書いたバウンド（span） | スタイル span **3000** の実測 Δz | スタイル span **2000** の実測 Δz |
| --- | --- | --- |
| 3000 / 3000（0） | **−3000** | **−2000** |
| 3200 / 4000（800） | **−2200** | **−1200** |
| 1000 / 6500（5500） | **+2500** | **+3500** |

6 本すべてが `自分の span − スタイルの span` に一致した。どちらのスタイルでも、
1 本ごとに `ResetObject` を通した対照の本は正しいままだった。

**後から `ResetObject` を通した。** 狂った 3 本へ `ResetObject` を 1 度通すと、**3 本とも解決バウンドどおりに戻った**。

| 本 | 狂っていた Δz | `ResetObject` 後の Δz（正しい値） |
| --- | --- | --- |
| 3000 / 3000 | −3000 | **−4.5474735088646412e-13**（＝0） |
| 3200 / 4000 | −2200 | **800.00000000000045** |
| 1000 / 6500 | 2500 | **5500** |

残差は 1〜2 ULP（[#67](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/67) /
[#71](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/71) と同じ大きさ）。
狂っていた間も、レコードと解決結果は書いた値のままだった。

**2 度流した。** `ResetObject` を通していない本へ `UpdateStyledObjects` を 2 回流すと、**2 回ぶん足された**。

| 書いた span | 1 回目の後 | 2 回目の後 | 収束していれば | 据え置きなら |
| --- | --- | --- | --- | --- |
| 0 | −3000 | **−6000** | 0 | −3000 |
| 5500 | +2500 | **+5000** | 5500 | +2500 |

[#245](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/245): `ResetObject` を通さずに
`UpdateStyledObjects` を 1 回流した材の Δz（−3000 / +2500）も、2 回流した材の累積（+5000）も、
undo イベントを閉じた後・VW へ戻って数十秒置いた後に 1 桁も動かなかった。

**バウンドが by-style のスタイル。** バウンドまで by-style のスタイル（＝`DialogStartElevationReference` を裏返さない）で、
**書く span をスタイルと違えて**測ると、こうなった。

| 書いたバウンド（span） | Update 後のレコード | Update 後の Δz | 判定 |
| --- | --- | --- | --- |
| 3000 / 3000（**0**） | 2500 / 5500（置き換わった） | **3000** | 解決バウンドどおり |
| 1000 / 6500（**5500**） | 2500 / 5500（同） | **3000** | 同 |
| （対照）1000 / 6500 を `ResetObject` 済み | 2500 / 5500 | 3000 | 同 |

書いた span が 0 でも 5500 でも結果は同じ 3000（＝置き換わった解決バウンドの span）で、
挿入点も 2500（スタイルの下端）に揃った（差分を足す規則なら 0 のまま／−3000 になる）。
#118 では「by-style では自分の span とスタイルの span が同じなので、上の式でも差が 0 になる」と
書いていたが、この 3 本は Update 前 Δz=0 で、実測は 3000 だった。

**`ResetObject` で建てた後にバウンドを書き換えた。** `ResetObject` で正しく建てた本のバウンドを書き換えて
`UpdateStyledObjects` だけを流すと、**やはり差分で動いた**（スタイル span は 3000）。

| 本 | `ResetObject` で建てた（span） | 書き換え先（span） | Update だけを流した後の Δz | 正しい値 |
| --- | --- | --- | --- | --- |
| 広げる | 1000 / 3000（2000） | 1000 / 6500（**5500**） | **4500** | 5500 |
| 狭める | 1000 / 3000（2000） | 1000 / 2000（**1000**） | **≈0**（2.2737367544323206e-13） | 1000 |

どちらも `Δz（前）2000 ＋ (新しい span − スタイル span 3000)` に一致した
（2000 + 2500 = 4500 ／ 2000 − 2000 = 0）。

### シンボル定義のサブタイプに PIO の内部 ID を書いてスタイルを作った記録（#98）

同 issue #98。次のコードで定義を組み立て、作ったスタイルを別の本へ当てて `styleRef` が
付くところまで確かめた（ダイアログは 1 つも出なかった）。

```cpp
TXString        name("新しいスタイル");
MCObjectHandle  hSymDef = gSDK->CreateSymbolDefinition(name);  // 名前が使われていれば nil
MCObjectHandle  seed    = /* その種別の PIO を 1 つ作る */;

gSDK->AddObjectToContainer(seed, hSymDef);   // 中へ「その種別の PIO を 1 つ」入れる
gSDK->ResetObject(hSymDef);                  // ★ サブタイプを書く**前に**通す（下記）
gSDK->SetSymbolDefSubType(hSymDef, VWParametricObj::GetInternalID(seed));
gSDK->SetAllPluginStyleParameters(hSymDef, kPluginStyleParameter_ByStyle);

const RefNumber ref = gSDK->GetObjectInternalIndex(hSymDef);
VWParametricObj(target).SetStyle(ref);       // 当たる（styleRef が ref になる）
```

実測（VW 2026 / mac）:

```
① CreateSymbolDefinition        中身: 0(kTermNode)                     ← 空の定義
② AddObjectToContainer=true     中身: 86(kParametricNode)=StructuralMember 0(kTermNode)
                                入れた PIO の親 = 定義のハンドルと一致
③ ResetObject の後              外接=[x 0〜3000 / y 3917.196〜4082.804]  ← 外接が付く
④ SetSymbolDefSubType(537)  →   読み戻し=537  **IsPluginStyle=true**
⑤ SetAllPluginStyleParameters   subType=537 ref=113  IsPluginStyle=true
⑥ 別の本へ SetStyle(113)     →   styleRef=113                            ← 当たった
```

- 順序を入れ替えた版（`Add` → `SetSymbolDefSubType` → `SetAllPluginStyleParameters` →
  `ResetObject`）では、`SetSymbolDefSubType(537)` の読み戻しが `0`、`IsPluginStyle=false`、
  当てても `styleRef=0` だった。
- 同梱ソースを読んだ記録: `VWSymbolDefObj::HasPluginStyleSupport()` は
  `GetSymbolDefSubType() > 0` だけを見、`PluginStyleObjectID()` はその値をそのまま返す。
  内部 ID はインスタンスから `VWParametricObj::GetInternalID(h)`（static）で取った。
  文書にあったスタイルを読んで突き合わせると、種別ごとに一致した:

  | PIO | 内部 ID（＝スタイルのサブタイプ） |
  | --- | --- |
  | `StructuralMember` | 537（インスタンスから取った値と、文書のスタイル 2 本の subType が一致） |
  | `Title Block Border` | 552 |
  | `Data Tag` | 599 |
  | `Drawing Label2` | 642 |
  | `Section Line2` | 645 |
  | `GridAxis` | 647 |
  | `GraphicLegend` | 658 |

- 上の ⑤ で `true` だった同じ定義が、中の PIO が消えた後（`CreatePluginStyle` に中身を
  壊された定義を、呼んだ後にもう一度読んだ）は `subType=537` のままでも `IsPluginStyle` が
  `false` だった。
- 文書に構造材用のスタイルが 2 本ある状態でも、自分でスタイルを作った直後でも、
  `GetPluginStyleForTool("StructuralMember")` は `true` を返しつつ `ref=0` だった。
- 同梱ソースを読んだ記録: `VWFC::Tools::VWStyleSupport::GetStylesFolder(名前)`
  （無ければ `CreateSymbolFolder` で作る）と `MoveStyleToFolder(スタイル, フォルダ)`
  （`AddObjectToContainer` で移す）がある。上の手順はフォルダへ入れずに当たった。
  1 つずつの由来は `SetPluginStyleParameterType(定義, 名前, 種別)` / `AddItemToPluginStyle`
  （種別は `kPluginStyleParameter_ByInstance` / `_ByStyle` / `_AllwaysByInstance` /
  `_ByCatalog` / `_ByMixed`。`MiniCadCallBacks.h`）。由来表の置き場はシンボル定義の
  タグ付きデータ（`'PSMP'`。`VWStyleSupport::InitFromSymbolDefinition`）。

  SDK ヘッダのどこにも定義されていなかった（`kAssociation*` のヒットは文書ノード種別の
  `kAssociationNode = 124` だけ。`Kernel/API/Objs.TDType.h:190`）。VW 開発者 wiki 側には
  `kOnDeleteDelete = 4` / `kOnDeleteReset = 5`（所有側を消したとき相手を消す／リセットする）
  しか出ていない。
- `Interfaces/Base/ExtendedProperties.h:70-71` に `kKludgeAddAssociation = 19` /
  `kKludgeRemoveAssociation = 20` があるが、"DO NOT USE THOSE SELECTORS !!!" と明記された
  private API で、渡す `fData` の構造体は公開されていない。
- VectorScript を SDK から流す口として `IVectorScriptEngine::ExecuteScript(const TXString&)`
  ／ `IPythonScriptEngine::ExecuteScript`（`Interfaces/VectorWorks/Scripting/`）がある。

## 自作 PIO で実機で初めて出た 3 点

自作 PIO（ホームズ君プラグインの `Extensions/ExtColumnMark`）で、CI が全て緑でも実機で
初めて出たもの:

1. 最初の 1 個で設定ダイアログが出た（上記「生成時に…」）。
2. 走査して見つけた対象のワールド座標へそのまま描くと、PIO を動かした量だけ絵がずれ、
   リセットしても同じ相対位置に描き直されて直らなかった。`GetObjectToWorldTransform` ＋
   `InversePointTransform` でローカルへ落としてから描くと、PIO を回しても絵は対象の上に残った。
3. リセットの契機を何も宣言していないと、印刷でも再オープンでも描き直されなかった。

- `kObjXProp*` を全数確認したところ、リセット系はすべて PIO 自身に関するもの（自分の
  レコード・自分のパス／プロファイル・ビューポート倍率・書類単位・書き出し前）だけで、
  association にも追加の公開 API は見当たらなかった。参照先の図形を動かした瞬間には PIO は
  追随しなかった。
- プラグインを外して過去の図面を開くと、PIO が描いたジオメトリは保存されていて表示できた
  （更新はできない）。

### 測り方（#183 の数値の出どころ）

PIO の配置（ローカル座標 → 世界座標の変換）を読む口の綴り 4 つを、同梱の VWFC 実装 `.cpp`

| 口 | 実装 | 中で呼んでいるもの |

入ったかどうかは結果に載る「ビルドの素性」の `殻:` の行で見た（`main` のままなら入れ替え先が
違う。id が新しくなっていても同じ）。

## リセット（再生成）をまとめられるかの実測（#81）

構造材を 200〜400 本置く取り込みで、1 本ごとの `ResetObject` が効いて 1 本 93〜130ms
掛かっている（[issue #81](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/81)）。

以下の数値はすべてその実行ログ。新規の空図面・構造材 PIO 30 本）。

別の調査で、描画属性を「クラスに従わせる」書き込み（`SetPColorsByClass` 等）と
`SetObjectClass` も、PIO では 1 回ごとに作り直しを起こした（構造材 PIO で 1 回 9ms。
非 PIO では無料。[Attributes and Classes](../Findings/Attributes%20and%20Classes.md)）。

### 再生成・再描画を止めておく口を探した（ヘッダを読んだ）

### `CreateCustomObjectPath` の `doRegen`（ヘッダを読んだ）

### バウンドが by-style のスタイルで `UpdateStyledObjects` を流した実測（issue #81 の (b)）

この節で使ったのはバウンドまで by-style のスタイル（by-instance のときは上記
「[`UpdateStyledObjects` を流したときのバウンドと長さの実測（#125）](#updatestyledobjects-を流したときのバウンドと長さの実測125)」。
[#125](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/125)）。

**スタイルを当てた PIO を `ResetObject` 抜きで 5 本置き、`UpdateStyledObjects` を 1 回だけ
呼ぶと、5 本ともバウンドどおりに作り直された**（渡したパスの Z 差 1 → 解決済みバウンドの
span 3000）。

- 順序は「スタイルを当てる → バウンドを書く → `UpdateStyledObjects`」。その後に 1 本ごとの
  `ResetObject` を重ねても値は変わらなかった（5 本とも 3000 のまま）。当てたスタイルの持つ
  バウンドも span 3000 だった（食い違うときは上記

### `doRegen=false` で水平材・斜め材を作った実測（#109）

#81 は鉛直材だけを振った（そこでは Z の差 0 ＝ 0 長）。水平材・斜め材は
[#109](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/109) で測った
（VW 2026 / mac・新規の空図面。`probes/runtime/doregen-nonvertical/` の実行ログ）。

#### 実測——同じケースを `doRegen` の true / false で 2 本ずつ作り、1 回目の `ResetObject` を読み比べた

`doRegen=true` の結果を「この実機での正しい形」とする物差しに使っている。**dz** は読み戻した
Z の差、**平面長** は `sqrt(dx² + dy²)`。

| 渡したパス Δ(x, y, z) | バウンドの span | 渡した 3 次元長 | 1 回目（`doRegen=false`） | 1 回目（`doRegen=true`） | 判定 |
| --- | --- | --- | --- | --- | --- |
| 鉛直 `(0, 0, 0)` | 3000 | 0 | dz **3000** ／ 平面長 0 | 同じ | **○ 1 回で正しい** |
| 鉛直 `(0, 0, 1)` | 3000 | 1 | dz **3001** ／ 平面長 0 | dz 3000 | × span ＋ 1 |
| **水平 `(2000, 0, 0)`** | **0** | 2000 | dz **0** ／ 平面長 **2000** | 同じ | **○ 1 回で正しい** |
| **斜め `(2000, 0, 0)`** | 3000 | 2000 | dz **3000** ／ 平面長 **2000** | 同じ | **○ 1 回で正しい** |
| 斜め `(2000, 0, 3000)` | 3000 | 3605.5512754639894 | dz **6000** ／ 平面長 2000 | dz 3000 | × span ＋ **3000** |
| 水平 `(2000, 0, 1)` | 0 | 2000.0002499999844 | dz **1** ／ 平面長 2000 | dz ≈ 0 | × span ＋ 1 |

- 5 行目（斜め・Z の差 3000）のずれは、3 次元長の 3605.55 ではなく **3000 ちょうど ＝
  渡した Z の差**だった。
- 平面長のずれは 6 ケースとも 0（3 行目・4 行目が 1 回目から正しい）。
- 両端の絶対 Z も 1 回目から解決バウンドの値と一致した（水平は 2500→2500、斜めは
  2500→5500。挿入点 ＋ ローカル Z で実測）。
- 狂った本は 2 度目の `ResetObject` で正しい値に収まった（3001 → 3000、
  6000 → 3000.0000000000005、1 → −2.22e-16）。

#### 端部オフセットとプラグインスタイルを当てた実測

水平材・斜め材に**端部オフセット**（`StartOffset` = 150 ／ `EndOffset` = −250。読み戻しで
確認）と**プラグインスタイル**（`SetPluginObjectStyle`。読み戻しで `styleRef` を確認）を、
片方ずつ・両方の 3 通りで当てて 1 回だけ `ResetObject` した結果は、**`doRegen` の
true / false で 1 文字も違わなかった**（6 通り × 2）。

副産物: 両端とも offset 2500 で書いた水平材にスタイルを当てると、`ResetObject` 後の解決
バウンドが **2500 / 5500** になり（書いていない値）、dz が 3000 になった。当てたスタイルの元に
した PIO はバウンド 2500 / 5500 の鉛直材だった。`doRegen` の true / false 両方で同じように
起きた。[#112](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/112) に
切り出して測った（上記「スタイルを当てた後のバウンドの実測（#112）」）。

#### `doRegen=false` で作った材で自己修復（`SetCustomObjectPath` → もう一度 `ResetObject`）を試した

1 回目の後に長さを読み戻し、狂っていたら**正しい最終形のパス**を `SetCustomObjectPath` で
差し替えてもう一度 `ResetObject` する、という直し方は、`doRegen=false` で作った材でも
そのまま効いた（鉛直・Z 差 1 の 3001 → **3000**）。差し替え後の解決バウンドは 2500 / 5500 の
ままで、`fOffset` は書き換わらなかった（渡したパスは、そのバウンドが解決する形と同じだった）。

### 実測（構造材 PIO 30 本 / VW 2026 / mac / 新規の空図面）

## 構造材 PIO の子が消えた件を表示欄と属性モード（`AttributesMode`）で切り分けた（#166）

「同じ構造材へ `AttributesMode` を 0 → 1 → 2 → 3 と書き換えて毎回 `ResetObject` を呼ぶと
描画が段階的に消えていき、値を既定へ戻しても戻らない」という観測があった
（[issue #166](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/166)）。
それを実機で採り直した記録（VW 2026 / mac・新規の空図面。`probes/runtime/pio-value-sweep-breaks-draw/` の
実行ログ 2 本。以下の数値はすべてそこから）。`AttributesMode` / `AttributesMode3D` /
`MemberAttributes_3D` を、素の個体・クラスやスタイルを先に書いた個体・同じ個体で何度も、
振ったが、子の数・型の内訳・外接・立方は 1 度も動かなかった（下記の網）。

### どの欄がどの子を消すか（実測）

素の構造材（`CreateCustomObjectPath("StructuralMember", 2 点のパス, nil, doRegen=false)` ＋
`ResetObject` 1 回）の子は、**置き石と終端を除いて 9 つ**——
`11(Group)×2` `84(CSGTreeNode)×1` `21(Polyline)×4` `5(Polygon)×2`。
そこから表示欄を**上から順に累積で** `false` にしていった:

| 書いた欄（累積） | 子（幾何） | 減ったもの |
| --- | --- | --- |
| （既定） | **9** = Group×2, CSGTree×1, Polyline×4, Polygon×2 | — |
| `MemberDisplay_*` = false | **8** | Polyline 1 本 |
| `CoverDisplay_*` = false | **8** | **なし**（既定の構造材は被覆を持たないため） |
| `CenterlineDisplay_*` = false | **7** | Polyline 1 本 |
| `StartCapDisplay_*` = false | **6** | Polygon 1 つ |
| `EndCapDisplay_*` = false | **5** = Group×2, CSGTree×1, Polyline×2 | Polygon 1 つ |

そこから**逆順に `true` へ戻す**と、5 → 6 → 7 → 8 → 8 → **9** と 1 段ずつ戻り、
最後は型の内訳まで既定と一致した。

- 型 84（`kCSGTreeNode`＝3D 実体）は、どの欄でも 1 度も消えなかった（表示欄でも
  `AttributesMode` でも `AttributesMode3D` でも `MemberAttributes_3D` でも）。
- 3 面（`_Above` / `_At` / `_Below`）へ同じ値を書いての結果である。平面図で使われる面は
  `_Below` だけ（[#158](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/158)）。

### 属性モードを振って子を数えた（実測の網）

| 振り方 | 子（幾何） |
| --- | --- |
| 1 個体で `AttributesMode` を 0→1→2→3→**0**（＝#166 の再現手順そのもの） | **9 のまま**（5 段とも） |
| 1 値 1 個体（0 / 1 / 2 / 3 を別々の個体で） | 9 ×4 |
| 同じ値（0）を 4 回書いて毎回 `ResetObject` | 9 ×4 |
| `MemberID`（文字欄）を 4 回振る／`MajorDepth` を 4 回振る | 9 ×4 |
| `ResetObject` だけを 4 回 | 9 ×4 |
| 置き石を 10 個積んでから `AttributesMode`=3 を 1 回、さらに 0 へ | 9 |
| undo イベント中で 0→1→2→3→0 | 9 ×5 |
| **per-part のクラス・`MemberFillStyle`=6・`MemberPenStyle`=4 を先に書いてから** 0→1→2→3→0 | 9 ×5 |
| `AttributesMode3D` を 0→1→2→3→0 ／ `MemberAttributes_3D` を 0 / 1 | 9 |

直後に作った新しい個体も、全部やり終えた後の新しい個体も既定どおりだった。

### 「消えた」と読んだ経緯（子の型を決め打ちして数えていた）

元の観測（#158 のプローブ）は、描かれた子を「型 5 / 21 / 84 のどれか」と決め打ちして
数えていた。構造材の子には型 11（`kGroupNode`）が 2 つ居る。加えて、同じプローブが
`AttributesMode` を振る前の段で表示欄を `false` にしていた。

### ついでに測ったこと

- 置き石（型 90 = `kUndoPlaceholderNode`）を 11 個積んだ状態でも、子の内訳は既定のままだった。
- undo イベントが開いている間の `ResetObject` でも置き石は積もった（以前の記録は「プローブが
  undo イベントを開かないから置き石が残る」と見立てていた）。
- 型 90 の子へ `DeleteObject(h, useUndo=false)` を 7 個ぶん呼んでも 1 つも減らず、
  `ClearUndoTableDueToUnsupportedAction()` を呼んでも減らなかった。
- `DeleteRegenerableSubObjects(hParametric)` を PIO の外から呼ぶと、子（幾何）が 9 → 3
  （Group×2 と終端だけ）になり、次の `ResetObject` で 9 へ戻った。置き石は減らなかった。
  ヘッダは「`kObjXPropPreserveContents` を宣言した PIO の Regenerate イベント中に使え」と言う。
- 子には常に型 0（`kTermNode`）が 1 つ在った。`DeleteRegenerableSubObjects` でも消えなかった。
- `doRegen=false` で作った直後（`ResetObject` を通す前）に `GetObjectBounds` を呼ぶと、`true` を
  返して ±`DBL_MAX` の反転した矩形が返った（`GetObjectCube` も同じ）。
- `MajorDepth` を 600 → 800 → 1000 と書いても、読み戻しは一致し、外接も立方も 1mm も動かなかった
  （このときの個体は `MemberType`＝`0`。#169 で測り直した——上記「`MemberType`（材質）を振って断面と
  `MajorDepth` の効き方を測った」）。
