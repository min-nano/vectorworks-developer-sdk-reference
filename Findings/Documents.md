# 図面（ドキュメント）を開く・作る

プラグインの実行中に**別の図面（文書）を開いて、以後の描画をそちらへ向けられるか**の
調査（[issue #34](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/34)）。
背景は [issue #23](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/23) /
[#27](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/27) /
[#31](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/31)（[Undo](Undo.md)）
の続き——「前回の実行結果を戻す」手段が undo にもレイヤ削除にも無い場面で、
「テンプレートから新しい図面を開き直す」が使えないかという問い。

## 存在する API【ヘッダ根拠】

ISDK（`Interfaces/VectorWorks/ISDK.h`）に、複数の図面（文書）を開いて切り替えるための
一群の呼び出しがある。**すべて宣言と、実装ソース側の薄い転送コード（`gCBP` 経由で
Vectorworks 本体へ渡すだけ）までしか確認できていない**——実際に何が起きるかは
Vectorworks 本体側（SDK に同梱されていない）の実装に依存する。

| API | 効果（ヘッダのコメントより） |
| --- | --- |
| `bool OpenDocumentPath(IFileIdentifier* pFileID, bool bShowErrorMessages)` | `pFileID` の指すパスの文書を開く。`GS_OpenDocumentPath` の説明: 「Opens the document specified by inPath. Set inShowErrorMessages to false if you want to make sure no dialogs come up.」 |
| `bool CloseDocument()` | 現在の文書を閉じる。引数は無く、**保存の要否を指定する口が無い**（後述） |
| `bool GetActiveDocument(IFileIdentifier** ppOutFileID, bool& outSaved)` | 現在アクティブな文書のパスと、**ディスクに保存されたことがあるか**を返す（**未保存の変更があるかではない**。下記「[未保存の変更ありは読めない](#未保存の変更ありは読めない)」） |
| `void GetOpenFilesList(TVWArray_OpenFileInformation& outInformation)` | 現在開いている**すべての**文書の一覧を返す（後述） |
| `bool SwitchToOpenFile(Sint32 fileRef)` | 開いている別の文書へアクティブを切り替える。`fileRef` は `GetOpenFilesList` から取る |
| `GSError SaveActiveDocumentPath(IFileIdentifier* pFileID)` | アクティブな文書を、ダイアログを出さずに指定パスへ保存する（エラー時のアラートを除く） |

`GetOpenFilesList` が返す `SOpenFileInformation`（`ISDK.h`）は 1 文書につき

```cpp
struct SOpenFileInformation
{
    IFileIdentifierPtr  fpFileID;
    Sint32              fFileRef;         // SwitchToOpenFile へ渡す鍵
    bool                fIsActive;        // これがカレント文書か
    bool                fIsInMemoryOnly;  // true = まだディスクに保存されていない
};
```

を持つ。**Vectorworks は元から複数の文書を同時に開いた状態を扱える**（`sdk-grep` で
見つかった `VWResourceListCategorized.cpp` のコメント: "List resources from open
documents other than the current document"）。「今の文書を閉じてから次を開く」以外に、
「開いたまま裏に残し、`SwitchToOpenFile` で行き来する」という選択肢も API 上は存在する。

## テンプレート（`.sta`）から新規文書は作れる——**専用 API ではなく `OpenDocumentPath` で**

**結論: できる。** ただし「テンプレートから新規作成する」という名前の API は無く、
**`.sta` のパスを `OpenDocumentPath` へ渡す**という形になる。渡すと、**その `.sta` 自体では
なく、それを元にした無題の新規文書が開く**（実機確認済み。下記「`.sta` を渡すとテンプレート
として扱われる」）。

以下は「専用 API を探して見つからなかった」という経緯である——**探し方が見当違いだった**
（`New`/`Create` 系を探していたが、実際は `Open` 側にテンプレートの扱いが入っていた）。

SDK 全体（`Include` + `Source` の実装ソース）を次のパターンで検索したが、**該当なし**。

| 検索パターン | 結果 |
| --- | --- |
| `(New\|Open\|Create)[A-Za-z]*(Document\|Drawing\|File)` | ヒットは `OpenDocumentPath` 系・`OpenPDFDocument`・`CreateNewXMLDocument`（XML の話）など、いずれも文書「作成」とは無関係 |
| `GS_(New\|Create)[A-Za-z]*(Doc\|File\|Draw)` | 0 件 |
| `ISDK.{0,5}New[A-Za-z]*\(` | 0 件 |
| `NewFromTemplate\|CreateFromTemplate\|kFileTypeVWTemplate\|SaveAsTemplate\|NewDrawing` | 0 件 |

「テンプレートから新規作成する」専用の ISDK / VWFC の呼び出しは無い。

**【訂正】ただし「メニューコマンドを名前で起動する汎用 API 自体が無い」というかつての
根拠は誤りだった**——`ISDK::DoMenuName(name, chunkIndex)` が実在する
（[Plug-in Interop](Plug-in%20Interop.md) の 2。
[issue #217](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/217)）。
`DoMenuName` が実際にコマンドを実行することは実機で確かめてあるので、
**「新規」に当たるメニューコマンドの内部名が分かれば、そこから起こせる見込みがある**
（内部名そのものは未調査）。**ただし `DoMenuName` には引数を渡す口が無い**ので、「このテンプレートから」を
指定する手段はこの経路には無く、下記の `OpenDocumentPath` のほうが扱いやすい。

**唯一実在する「新規文書を開く」経路は `OpenDocumentPath(nullptr, false)`。** 公式ドキュメント
（[`Info/Writing automated tests.md`](../Info/Writing%20automated%20tests.md)）に
用例として明記されている:

```cpp
void SystemTests::YourTest::setUp()
{
    // This opens a blank new document
    CPPUNIT_ASSERT(gSDK->OpenDocumentPath(nullptr, false));
}
```

これは**テンプレートを選べない「空の」新規文書**である。**テンプレート由来の初期状態
（通り芯レイヤ・クラス・シンボル定義・スタイル）が要るなら、`nullptr` ではなく
`.sta` のパスを渡す**（同じ `OpenDocumentPath` で、下記のとおりテンプレート扱いになる）。
上の用例は自動テストの `setUp`/`tearDown`（`System Test Manager` から走らせる文脈）の
ものだが、**プラグインのメニューコマンド実行中（`DoInterface` の中）から呼んでも動く**
ことは実機で確かめた（下記「実機で確かめたこと」）。

## 既存ファイル（`.vwx` / `.sta`）をパス指定で開ける（実機確認済み）

`OpenDocumentPath(IFileIdentifier*, bool)` に実在するファイルの `IFileIdentifier` を渡せば
開ける。SDK 自身の自動テスト基盤（`VWFC/Tools/CatchSystemTest.cpp` の
`TEST_OpenDocument`）が実際にこの形で使っている:

```cpp
IFolderIdentifierPtr testFolder(IID_FolderIdentifier);
IFileIdentifierPtr testFile(IID_FileIdentifier);
gTestEnv->GetTestFileDirectory(testFolder);
testFile->Set(testFolder, relativeFilePath);
fOpened = gSDK->OpenDocumentPath(testFile, inbShowErrorMessages);
// ...
gSDK->CloseDocument();
```

**実機でも同じ形で開けた**（下記「実機で確かめたこと」）。`.sta` を渡したときの扱いも
実機で確かめてある（テンプレートとして扱われる。同じく下記）。

## 実機で確かめたこと（VW 2026 / macOS）

以下は**プラグインのメニューコマンドの中（`DoInterface` の中）から**実機確認プラグイン
（VwSdkProbes）でプローブを走らせた実測。**印の無い記述は実機確認済み。**
プローブは 3 度作り直し、3 回走らせている（`open-document` 1 回、`close-document` 2 回。
いずれも役目を終えたので削除済み）。**一度も落ちていない。**

**戻り値を信じないこと。** この節でいちばん値の張る教訓がこれである——
`CloseDocument()` も `SetObjectName()` も、**成功しているのに `false` を返す**
（下記）。文書まわりの成否は、**`GetOpenFilesList` の件数や、書いた値を読み戻して**
確かめる。

### コマンド実行中に呼んでよい

`gSDK->OpenDocumentPath(nullptr, false)` をコマンド実行中に呼んで **`true`**。落ちない。
`SwitchToOpenFile` / `CloseDocument` も同じ文脈で呼べた。下記
「[`CloseAllFilesAndQuitVectorworks`](#closeallfilesandquitvectorworks終了)」の
**プラグイン読み込み中には呼べない**のような「呼べる場面」の制約は、**少なくとも
コマンド実行中については無い**。

### カレント文書とカレントレイヤは即座に新しい文書へ移る

| | 開く前 | `OpenDocumentPath(nullptr, false)` の直後 |
| --- | --- | --- |
| `GetCurrentLayer()` の名前 | `7` | `レイヤ-1`（ハンドルも別物） |
| `GetActiveDocument()` のパス | `/Applications/VW2026/名称未設定 1` | `/Applications/VW2026/名称未設定 3` |
| 同 `outSaved` | `no` | `no` |
| `GetOpenFilesList()` の件数 | 1 | 2 |

**呼んだ瞬間に描画先が新しい文書へ移る**（切り替えてから `CreateRectangle` が新しい文書に
入ることを確認）。ついでに分かったこと 2 つ:

- **未保存の文書でも `GetActiveDocument` はパスを返す。** `/Applications/VW2026/名称未設定 1`
  のように「アプリケーションのあるディレクトリ＋無題の文書名」が入るので、**保存済みか
  どうかはパスの有無ではなく `outSaved` で見る**。
- 新規文書の名前は「名称未設定 2」ではなく**「名称未設定 3」**だった。無題の連番は VW の
  セッション全体で進むので、**名前から文書を同定しない**。

- **図面が 1 枚も無ければ `GetCurrentLayer()` は `nullptr`**（落ちない。全部閉じた後も起動
  直後も。件数と常に一致した）。**閉じた文書のレイヤと後で開いた文書のレイヤが同じアドレスで
  返った**ので、ハンドルの値で文書を同定しない（[Timers and Notifications](Timers%20and%20Notifications.md)
  の 4 の 8。mac / Windows で実測）。

### `GetOpenFilesList` と `fileRef`

```
[0] fileRef=2 active=no  inMemoryOnly=yes path=/Applications/VW2026/名称未設定 1
[1] fileRef=9 active=yes inMemoryOnly=yes path=/Applications/VW2026/名称未設定 3
```

- **`fileRef` は連番ではない**（2 の次が 9）。**不透明な鍵**として `GetOpenFilesList` から
  取り、そのまま `SwitchToOpenFile` へ渡す（値を自分で組み立てない）。
- 一度も保存していない文書は `fIsInMemoryOnly=yes`。

### 前の文書のハンドルは、別の文書がアクティブでも読める

開く前に取ったレイヤハンドルへ、**新しい文書がアクティブな状態で** `GetObjectName` を
呼ぶと、開く前と同じ「7」が返った。落ちないし、無効値にもならない。

**書くこともできる。** 別の文書 Y をアクティブにした状態で、文書 X のレイヤハンドルへ
`SetObjectName(layerX, "probe-g4-renamed")` を呼ぶと、**落ちずに名前が変わった**——
Y のまま読み戻しても、X へ切り替えてから読んでも `probe-g4-renamed` だった。

- **ただし `SetObjectName` は `false` を返した**（`CloseDocument` と同じ）。
  **成否を戻り値で判定しない。書いた値を読み戻して確かめる。**
- 確かめたのは**名前の書き換え 1 種類**だけである。図形を足す・消すのような、
  カレント文書やカレントレイヤを暗黙に見る呼び出しが同じように振る舞うかは別問題なので、
  **描くときは `SwitchToOpenFile` でその文書をアクティブにしてから**にするのが安全。

### 文書を開く・切り替える操作は undo イベントを開かない。**開いているイベントも壊さない**

`IsCurrentlyBuildingAnUndoEvent()` は開く前・開いた直後・`SwitchToOpenFile` で戻った後の
いずれも `no`（自分でイベントを開いていない場合）。

**自分で undo イベントを開いたまま文書を開いても、そのイベントは生きている。**
`IsCurrentlyBuildingAnUndoEvent()` は**文書ごとの状態**だった:

| 見た場所 | `building` |
| --- | --- |
| 文書 A でイベントを開き、中でレイヤを 1 枚作った直後 | `yes` |
| そこから `OpenDocumentPath(nullptr, false)` で開いた文書 B | **`no`** |
| **B から `SwitchToOpenFile` で A へ戻った直後** | **`yes`** |

A へ戻ればイベントは開いたままで、**その中で作ったレイヤも残っている**。つまり
B で見た `no` は「イベントが終わった」ではなく「**B にはイベントが無い**」という意味。

- **[Undo](Undo.md)「間接経路: スクリプトエンジン経由…」の事例とは別物**である。
  あちらでイベントを終わらせていたのは**取り消しの実行**であって、文書を開く操作では
  なかった（同じ形でスクリプトだけを差し替えて切り分け済み）。
- とはいえ、**イベントを開いたまま別の文書へ行って描く**のは、記録がどちらの文書に
  積まれるのかが曖昧になる。**イベントは開いた文書の中で閉じる**のが素直。

### `SwitchToOpenFile` で行き来できる

`SwitchToOpenFile(2)`（開く前の `fileRef`）は `true` を返し、**カレントレイヤは開く前と
同じハンドル**に戻った。「今の文書を閉じてから次を開く」だけでなく、
**開いたまま裏に残して行き来する**が実際に動く。

### `CloseDocument()` は **`false` を返しながら閉じている**——未保存の変更も黙って捨てる

**この節は一度書き換えている。** 最初は「未保存の変更がある文書は `CloseDocument()` では
閉じられない」と書いた。戻り値が `false` だったからである。しかし**開いている文書の件数を
前後で数えたら、ちゃんと減っていた**。

| 呼んだ場面 | 戻り値 | 所要 | `GetOpenFilesList` の件数 |
| --- | --- | --- | --- |
| 未保存の変更（矩形を 1 つ作った）がある無題文書 | `false` | 74ms | **3 → 2** |
| `SaveActiveDocumentPath` で保存済みの文書 | `false` | 135ms | **2 → 1** |
| 同上（別の走行、3 例） | `false` | 73 / 237 / 201ms | **いずれも 1 件減った** |

- **戻り値は当てにならない。** 5 回とも `false` を返しながら 5 回とも閉じている。
  **判定は `GetOpenFilesList` の件数でする。**
- **保存確認ダイアログは出ない。** どの回も 73〜237ms で戻っており、**人を待っていない**
  （モーダルが出れば秒単位になる。[Undo](Undo.md)「間接経路…」で実際に 18108ms を
  観測している）。**未保存の変更は黙って捨てられる。**
- したがって **`bShowErrorMessages` に相当する引数が無いのは困らない**——ダイアログが
  そもそも出ない。逆に言えば、**利用者に「保存しますか」を尋ねる機会も無い**ので、
  **人の作りかけを消しうる**。自分が開いた文書だけを閉じるなりの判断は**呼び出し側の
  責任**になる（`GetActiveDocument` の `outSaved` は**未保存の変更を表さない**ので、
  この判断には使えない。下記「未保存の変更ありは読めない」）。
- 「保存してから閉じる」も通る（`SaveActiveDocumentPath` が `GSError=0`、その後
  件数が減る）。ただし**保存しなくても閉じられる**ので、捨ててよい文書のためにわざわざ
  保存する必要は無い。

#### Windows と、「閉じる」で確認が出る図面（#305。mac も）

**問い**（[issue #305](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/305)）:
上の mac の結果が Windows でも成り立つか。あわせて、**メニューの「閉じる」（`DoMenuName("Close", 0)`）なら
確認が出る図面**——`OpenDocumentPath` で開いただけの図面・コピーで開いた図面（`fIsInMemoryOnly=yes`）・
大きな図面——でも `CloseDocument()` は確認を出さないか。

**実測（Windows）**: VW 2026（31.6.0）/ Windows 11 ARM64 の VM（x64 エミュレーション・3D アクセラレーションなし）。
`probes/runtime/newpath-close/` の `steps-win-305.do` / `steps-win-305-large.do` を、MCP ブリッジのスプールを
直に叩いて回した＝**殻の `SetTimer` の刻みの中**から呼んだ。ビルド `a188da4237a8`。`closedoc` は
`CloseDocument()` の呼び出しの間だけ 100 ms の見張りのタイマーを仕掛け、新しい窓が出れば文言を書いて
キャンセルを押す作り（#283 と同じ）。**どの回も窓は出ず、見張りは 1 度も刻まなかった**（Windows では確認の
最中に刻みが配られるので、刻み 0 回＝メッセージループに入っていない）。

| 閉じた図面 | 戻り値 | 所要 | 件数 | 確認 |
| --- | --- | --- | --- | --- |
| 無題・未保存の変更あり（undo イベントの外の矩形） | `false` | 231 ms | 2 → 1 | 出ない |
| 無題・無変更（「閉じる」では確認が出る） | `false` | 151 ms | 2 → 1 | 出ない |
| 保存した後に矩形を足した | `false` | 132 ms | 2 → 1 | 出ない |
| 保存した直後 | `false` | 123 ms | 2 → 1 | 出ない |
| **`OpenDocumentPath` で開いただけ**（「閉じる」では確認が出る） | `false` | 145 ms | 2 → 1 | 出ない |
| 裏の図面を `SwitchToOpenFile` で前へ出して（CLI の `close` の形。3 回） | `false` | 87 / 91 / 138 ms | −1 | 出ない |
| **読み取り専用のファイルを開いたコピー**（`ro コピー 1`・`fIsInMemoryOnly=yes`） | `false` | 129 ms | 2 → 1 | 出ない |
| 同上・矩形を足してから | `false` | 123 ms | 2 → 1 | 出ない |
| **使用中のファイルを開いたコピー**（別のハンドルが書き込み・共有は読み取りのみで握る。`held コピー 1`） | `false` | 114 ms | 2 → 1 | 出ない |
| **大きな図面**（#290 と同じ合成。11.2 万件）・無題・作った同じ刻みの中で | `false` | 628 ms | 2 → 1 | 出ない |
| 同上・保存してから・描画の前 | `false` | 522 ms | 2 → 1 | 出ない |
| 同上・**`OpenDocumentPath` で開いただけ・描画の前**（#290 では「閉じる」の確認が出るまで 31.8 秒） | `false` | **578 ms** | 2 → 1 | 出ない |
| 同上・開いてメッセージを 60 秒回し、描画させてから | `false` | **8926 ms** | 2 → 1 | 出ない |

- **Windows でも mac と同じ。** 戻り値は 17 回とも `false` で、17 回とも閉じた（表に無いのは、コピーを作るために保存した図面を閉じた回）。**確認は 1 度も出ない**
  ——「閉じる」なら確認が出る図面（無題・無変更、開いただけ、コピー）でも出ない。未保存の変更は黙って捨てる。
- **描画の前の大きな図面でも 0.5〜0.6 秒で戻る。** #290 の「閉じる」で確認が出るまでの 31.8 秒は、確認を出す
  前の描画だったと読める【推定】（確認を出さない `CloseDocument()` では起きない）。描画した後は 8.9 秒かかる
  （#290 の「閉じる」の 9.3〜12.5 秒と同じ程度。この VM はソフトウェア描画）——**約 5 秒を超えるので
  応答なしの表示になりうる**（#290）。
- **閉じた後の前面と、戻し方**: 閉じた後に前へ出るのは、**最後に開いた図面**だった（3 枚のとき、走り出しの
  図面を前にしてから裏の `c.vwx` を前へ出して閉じると、前へ出たのは c の後に開いた `d.vwx`）。覚えておいた
  `fileRef` へ `SwitchToOpenFile` すれば、**どの回も `true` で、カレントレイヤも同じハンドルに戻った**。
- **`.<名前>.lck` は閉じると消えた**（保存済み・開いただけの図面）。コピー（`ro コピー 1` など）は元のフォルダに
  `.lck` を作らず、閉じた後もアプリのフォルダ（`C:\Program Files\VW2026\`）にファイルは残らない。
- 古い版のファイルは Windows では作れないので測っていない（#291）。mac では下で測った。

**実測（mac）**: VW 2026（31.6.0）/ macOS 27.0.1（Apple M1 Pro の VM）。同じプローブの `steps-mac.do` を
MCP ブリッジ（`vw_run_probe`）で回した。ビルド `7961f913f452`。見張りは同じ作り——**mac でも確認の最中には
刻みが配られる**（同じ周の #304 で、保存の警告の間に見張りが 11〜12 回刻んで OK を押した）ので、刻み 0 回は
「モーダルに入っていない」と読める。使用中の場面は、**2 つ目の Vectorworks を `open -n` で起動して `held.vwx` を

### `.sta` を渡すとテンプレートとして扱われる——**無題の新規文書が開く**

**この節が issue #34 の本題への答えである。**

`.sta` の拡張子を持つファイルのパスを `OpenDocumentPath` へ渡すと、**そのファイル自体では
なく、それを元にした無題の新規文書が開いた**:

```
G3: OpenDocumentPath(.sta, false) = true elapsed=467ms
G3: 開いた後のアクティブ文書: /Applications/VW2026/名称未設定 7（saved=no）
```

パスが `.sta` ではなく**無題**（`名称未設定 7` / `saved=no`）になっている。
**Finder で `.sta` をダブルクリックしたときと同じ扱い**である。

- **中身も引き継がれている。** この `.sta` は、直前まで編集していた文書を
  `SaveActiveDocumentPath` でその名前に保存したもので、中にレイヤ `probe-g1-inner` が
  あった。開いた無題文書のカレントレイヤが**その `probe-g1-inner`** だった——
  **テンプレートの中身を持った、まっさらな（未保存の）文書**が手に入る。
- したがって「テンプレートからの新規作成専用 API が無いので、テンプレート由来の初期状態は
  再現できない」という以前の結論は**誤り**だった。**`OpenDocumentPath` にテンプレートの
  パスを渡せばよい。**
- **`.vwx` を渡したときは無題にならない**（アクティブ文書のパスが渡したパスそのものに
  なり、`saved=yes`）。**扱いを分けているのは拡張子**だと読める【推定】——
  中身の形式まで見ているのかは確かめていない。

### 既に開いているファイルは、もう一度は開けない

いま開いている文書のファイルを `OpenDocumentPath` へ渡すと **`false`**（20ms、件数も
変わらない）。**閉じてから同じパスを渡すと `true`**（529ms）。

- これは**引っ掛かりやすい**。`SaveActiveDocumentPath` で保存すると**その文書自身が
  保存先のファイルになる**ので、「保存 → そのパスを開く」と続けて書くと必ず失敗する。
  （実際この調査の 1 度目で踏んで、`.sta` の判定を 1 周やり直した。）
- **失敗は速い**（20ms）。時間が掛かっていないことも、ダイアログではなく即座の拒否で
  あることの裏づけになる。

## 未保存の変更ありは読めない

**問い**（[issue #240](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/240)）:
開いている図面のうち、**保存済みの図面を変更した状態（未保存の変更あり）**を SDK から
取れるか。[vectorworks-plugin-command-line-interface](https://github.com/min-nano/vectorworks-plugin-command-line-interface)
の `quit` が、終了を頼む前にダイアログなしで「未保存の変更がある図面」を見つけたい。

**答え: 取れない。** 読める手掛かりは `GetActiveDocument` の `outSaved` と
`GetOpenFilesList` の `fIsInMemoryOnly` の 2 つだけで、**どちらも「ディスクに保存された
ことがあるか」を表す**。保存済みの図面に保存の確認が出る状態になっても値は変わらない。
macOS の窓の「編集済み」（`NSWindow` の `isDocumentEdited`）も、保存の確認とは食い違う。

### 読む口は 2 つしか無く、どちらも「ディスクにあるか」【ヘッダ根拠】

- **SDK に「変更あり」を読む宣言は無い。** `SDK Index/` を `Modified` / `Dirty` / `Changed` /
  `Saved` で引いて、文書の状態として見つかるのは**変更ありに「する」側**の
  `ISDK::MarkCurrentDocChanged()`（`ISDK.h:1386`。`kcbMarkCurrentDocChanged`）と、
  メニューの有効条件 `EMenuEnableFlags::DocChanged`（`MiniCadCallBacks.h:4950`）だけ。
  `IApplication::GetActiveDocument(IDocument**)` で取れる `IDocument` は設定ダイアログを
  出す 4 つの関数しか持たない（`IDocument.h:16-19`）。
- `outSaved` の意味は旧 API の説明文に書いてある（`APIBase.Legacy.Defs.h`、
  `GS_GetActiveDocumentN`）: 「The saved parameter indicates whether the document has been
  **saved to disk**. If it has not, then activeDocumentPath is only a file name.」
  ——**ディスクにあるか**であって、変更の有無ではない。

### 実測: 正解（「閉じる」で保存の確認が出るか）と突き合わせた

**実測**（VW 2026 / macOS arm64。`probes/runtime/doc-dirty-staged/` をローカルの Claude Code
から MCP ブリッジで回した＝**OS タイマーの刻みの中**（殻の `CFRunLoopTimer`）。ビルド
`3ba4ea7d79bb`。プローブは役目を終えたので削除済み）。

**測り方が肝なので先に書く。** 最初の測定（#241）は 1 回の実行の中で「変更 → 読む」を
していたので、VW が変更ありの印をコマンドや undo イベントの終わりに付けるなら読み損ねて
いる疑いがあった（利用者の指摘）。そこで:

- **1 回の実行で 1 段だけ進める。** ケースごとに「設定の実行（図面を開き、保存済みの
  ケースは別名で保存し、操作を 1 つする）→（取り消しのケースだけ）取り消す実行 →
  確かめる実行」と分け、**読むのは前の実行が返った後**にした。どの段の冒頭でも
  `IsCurrentlyBuildingAnUndoEvent()` は `no`（undo イベントは閉じている）。
- **正解を機械で取る。** 確かめる実行で `DoMenuName("Close", 0)`（メニューの「閉じる」。
  内部名 `Close` で引けた）を呼び、`kCFRunLoopCommonModes` のタイマーから
  `NSApp.modalWindow` を見て、保存の確認が出たかとその文言を記録した（出たら
  `abortModal` で閉じた。VW はこれを「保存しない」として扱い、図面は閉じた）。

| ケース | `outSaved` | `fIsInMemoryOnly` | 窓の「編集済み」 | 「閉じる」で保存の確認 |
| --- | --- | --- | --- | --- |
| 保存済み・無変更 | `yes` | `no` | `no` | **出ない**（91 ms で閉じた） |
| 保存済み・undo イベント付きで矩形 | `yes` | `no` | `yes` | **出た** |
| 保存済み・undo イベント付きで矩形 → 次の実行で `DoMenuName("Undo")` | `yes` | `no` | **`no`** | **出た** |
| 保存済み・`MarkCurrentDocChanged()` | `yes` | `no` | **`no`** | **出た** |
| 保存済み・undo イベントの外で矩形 | `yes` | `no` | `no` | **出ない**（90 ms。矩形は黙って捨てられた） |
| 無題（`OpenDocumentPath(nullptr)`）・無変更 | `no` | `yes` | `yes` | **出た** |
| 無題・undo イベント付きで矩形 | `no` | `yes` | `yes` | 出た |
| 無題・`MarkCurrentDocChanged()` | `no` | `yes` | `yes` | 出た |

確認の文言はどれも「ファイル「…」で行った変更を保存しますか? / 保存しない場合、変更は
失われます。 / [保存] / [保存しない] / [キャンセル]」（呼んでから 91〜145 ms で出た）。

- **`outSaved` と `fIsInMemoryOnly` は、全ケース・全段で `outSaved == !fIsInMemoryOnly`。**
  保存済みの 5 ケースはどれも `outSaved=yes` で、**確認が出る 3 ケースと出ない 2 ケースを
  見分けられない**。実行が返った後に読んでも同じ（同じ実行の中で読んだ #241 の 14 局面とも
  同じ）。**値が変わるのは保存した瞬間だけ**。
- **窓の「編集済み」も正解ではない。** 取り消した後と `MarkCurrentDocChanged()` の後は
  `no` なのに確認が出る。**この印は undo の段の位置を追っているだけ**と読める
  （undo イベント付きの変更で `yes`、取り消すと `no`、`MarkCurrentDocChanged()` では
  動かない）【推定】。無題の図面は開いた瞬間から `yes`。
- **VW の「変更あり」は取り消しでは消えない。** 変更してから取り消して保存時点の中身に
  戻しても、確認は出る。**消えるのは保存したときだけ**。
- **undo イベントの外の書き込みは「変更あり」にしない**（刻みの中で。[Timers and
  Notifications](Timers%20and%20Notifications.md) の 4 の 9 の【推定】をここで確かめた）。
  確認が出ないので、**閉じれば黙って捨てられる**。
- **無題の図面は、何もしていなくても確認が出る**（「閉じる」で）。
  - #230 で「新規の図面に刻みの中で線を引いただけでは、終了の確認が出なかった」のは、
    **その図面がブリッジによって既に一時ファイルへ保存されていた**ため——つまり上の表の
    「保存済み・undo の外の変更」と同じ形だった——と読める【推定】（ブリッジは
    実行のたびに自分が開いた図面を保存する。#220 から）。
- **取り消された図形は、保存するまで一覧に残る。** 取り消した後も `FirstMemberObj` /
  `NextObject` で数えた図形数は減らず、上書き保存した瞬間に減った（#242 の段ごとの測定）。
  **図形数で「取り消しが効いたか」を判定しない。** #241 の測定で「取り消しで戻らない」と
  見えたのはこれで、取り消し自体は効いていた（窓の「編集済み」が `no` に戻っていた）。
  **残っているのは図形ではなく型 `90` の置き石**で、`ForEachObjectN` には出ない（[Layer
  Objects](Layer%20Objects.md) の 4。#282）。
- **刻みの中から呼んでよい。** 上の測定はすべて OS タイマーの刻みの中で、落ちず、
  `GetActiveDocument` は 1 回 7〜94 µs（#241）。**図面 0 枚・起動直後の刻みでも
  `GetOpenFilesList()` は落ちない**（[Timers and Notifications](Timers%20and%20Notifications.md)
  の 4 の 1・4 の 8）。
- **同じパスへの上書き保存は通る**（`GSError=0`・パスも変わらない。#241・#242）。殻のブリッジの
  「既にあるファイルへの**別名**保存は通らなかった」（`plugin/src/McpBridge.cpp`）とは別の
  場面で、**その文書自身のファイルへの保存**は通る。
- 正解に使ったのは**「閉じる」の確認**で、**終了（`CloseAllFilesAndQuitVectorworks(true)`）の
  確認ではない**。保存済みの「無変更」「`MarkCurrentDocChanged`」「undo の外の変更」の 3 つは
  #230 の終了の実測と一致する（出ない／出る／出ない）ので、同じ判定だと見ている【推定】。
- Windows では測っていない。`outSaved` の意味は SDK の説明文どおりなので変わらないと見るが
  【推定】。窓の「編集済み」は macOS だけの口。

### `quit` の事前確認への帰結

- **ダイアログなしで分かるのは「無題の図面がある」までである。** `GetOpenFilesList` の
  `fIsInMemoryOnly=yes`（無題）を拾えば、その図面は**変更が無くても**保存の確認を出す
  （「閉じる」で実測。終了でも同じと見る【推定】）。**保存済みの図面に未保存の変更が
  あるかは、事前に知る口が無い。**
- **未保存の変更が無いときの `CloseAllFilesAndQuitVectorworks(true, false)` は、確認なしで
  終わる。** 確認があるときは**キャンセルされても呼び出しから戻り、図面は残る**（件数で
  分かる）。どちらも #230 で実測済み（下記「[呼んだ後の振る舞い](#呼んだ後の振る舞いmac--windows-で実測)」）。
  **issue #240 の 5・6 はこれで答えが出ている**——確認は呼び出しの時点の状態で決まるので、
  「確かめてから呼ぶまでの間に変更ができた」場合も、ふつうに確認が出て、キャンセルなら戻る。
- したがって「確認を出さない」を保証する手は、事前確認ではなく次のどれかになる:
  1. **保存してから終える**——開いている保存済みの図面を順に `SwitchToOpenFile` →
     `SaveActiveDocumentPath(<その図面自身のパス>)` で上書き保存すれば、変更の有無に
     関わらず確認の種は消える（上書き保存が通ること、保存で「変更あり」が消えることは
     上記のとおり実測）。**人の変更を黙ってディスクへ書く**ので、明示の指定（`--save`
     など）を要する設計になる。無題の図面には保存先が無いので、この手では消せない。
  2. **捨てて終える**——`CloseAllFilesAndQuitVectorworks(false, …)`（確認なしで閉じる）。
     **人の変更を黙って捨てる**ので、同じく明示の指定（`--force` など）でだけ使う。
  3. **確認を出す前提で呼ぶ**——ダイアログが出うることを受け入れ、キャンセルされたら
     （戻った後も図面が残っていたら）エラーで応える。
  事前確認で拾えるのは無題の図面だけなので、それを「未保存の一覧」として返すなら
  **「保存済みの図面の変更は含まれない」**ことを利用者に言わなければならない。
- **自分で数えて持つ【推定・未検証】。** `kNotifyDocPostSaved` / `kNotifyDocOpen` で「保存
  時点」を記録し、`kNotifyUndoEndEvent` で「変更あり」を立てる作りは考えられる。上の表で
  VW の「変更あり」が立ったのは **undo イベント付きの変更**と **`MarkCurrentDocChanged()`** で、
  **取り消しでは消えない**ので、「保存以降に undo イベントが 1 つでも閉じたか」は表と合う。
  ただし **`MarkCurrentDocChanged()` は通知なしに変更ありにする**ので（他のプラグインが
  呼べば見えない）、**正確な代わりにはならない**。

## 指定した図面を保存する・閉じる（前面に依存せず）

**問い**（[issue #243](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/243)）:
[vectorworks-plugin-command-line-interface](https://github.com/min-nano/vectorworks-plugin-command-line-interface)
の `save` / `close` は、前面の図面ではなく**引数（パス）で指定した図面**を扱う。その図面を
新しいパスへ保存できるか、保存・閉じるの後に前面を元に戻せるか、「閉じる」で保存の確認が
いつ出るか。

**実測**（VW 2026 / macOS arm64。`probes/runtime/doc-save-close/`・`doc-close-confirm/`・
`doc-close-next-tick/`・`doc-open-for-manual/`・`doc-close-front/` をローカルの Claude Code から
MCP ブリッジで回した＝**OS タイマーの刻みの中**から呼んだ。ビルド `f9a1aa1bf5a2` /
`f94a82d23e07` / `4063818092fa` / `392cdb298a31`。保存の確認と警告のボタンは人が押し、
手で開く・手で閉じるの組み合わせは人が操作して目視した。プローブは役目を終えたので削除済み）。

### 手順——`GetOpenFilesList` で引き、`SwitchToOpenFile` で前へ出し、前面を戻す

```cpp
// 1. 前面を覚える（fileRef とカレントレイヤ）
// 2. GetOpenFilesList から、パスが一致する項目の fFileRef を引く
gSDK->SwitchToOpenFile(targetRef);
gSDK->SaveActiveDocumentPath(fileID);   // 保存（新しいパス / 自分のパス）
gSDK->DoMenuName("Close", 0);           // 閉じる（確認が出うる。下記）
// 3. 閉じた後の前面は「元の前面」とは限らない → 覚えた fileRef へ戻す
gSDK->SwitchToOpenFile(originRef);
```

- **前面は戻せる。** 裏の図面へ切り替えて保存し、元の図面へ `SwitchToOpenFile` で戻すと、
  アクティブの `fileRef` も**カレントレイヤのハンドルも**元どおりだった。裏の図面を閉じた後に
  戻しても同じ（カレントレイヤは同じハンドル）。
- **閉じた後に前へ出るのは、元の前面ではない。** 前面の図面を「閉じる」と、アクティブは
  **別の図面**（この実測ではいちばん最近開いた図面）になった。元の前面へ戻すのは呼ぶ側の仕事。
- **図面は「パス」で一意に決まる。** 同じファイル名 `same.vwx` を別のフォルダに保存した
  2 枚は、`GetOpenFilesList` のパスで見分けられた（名前は同じ）。**無題の図面のパスは
  「アプリケーションのフォルダ＋名称未設定 N」**（`/Applications/VW2026/名称未設定 15` /
  `16` …）で、N はセッション全体の連番（上記「カレント文書と…」のとおり）。開いている間は
  重ならないが、**名前はファイルとしては存在しない**ので、無題の図面を指すなら `fileRef`
  のほうが確か。

### `SaveActiveDocumentPath`——新しいパスへは通る。既存のファイルへは通らない

| 保存する図面 | 保存先 | `GSError` | 所要 | ダイアログ | 保存後 |
| --- | --- | --- | --- | --- | --- |
| 無題（未保存） | **まだ無いパス** | **0** | 34 / 25 / 27 / 28 ms | なし | 図面のパスが保存先になり、`fIsInMemoryOnly=no`・`outSaved=yes` |
| 保存済み | **まだ無いパス**（別名保存） | **0** | 21 / 68 ms | なし | **図面のパスが保存先へ移る**。元のファイルはそのまま（大きさ・更新時刻とも不変） |
| 保存済み | 自分のパス（上書き保存） | 0 | 43 ms | なし | パスは変わらない（#240 と同じ） |
| 保存済み | **ディスクにあるが開いていない**ファイル | **50331649**（`0x03000001`） | 5 ms | **なし** | 何も起きない（保存先も図面も不変） |
| 無題 | 同上 | **50331649** | 3 ms | **なし** | 同上 |
| 無題 | **別の図面が開いている**ファイル | **50331649** | （人待ち） | **警告「このファイルはすでに開かれています。」**（OK だけ） | 何も起きない |

- **別名保存は「名前を付けて保存」と同じく、図面ごと保存先へ移る。** 元のファイルは
  保存した時点の中身のまま残り、**別の図面として開き直せた**（図形数も保存した時点の 2 つ。
  開き直した図面には新しい `fileRef` が付く）。
- **既存のファイルを上書きする別名保存はできない。** 開いていないファイルが相手なら、**確認も
  警告も出さずに**エラーを返す（ファイルには触れない）。開いているファイルが相手だと
  **警告のダイアログが出て、人が OK を押すまで戻らない**——SDK の説明文の「ダイアログを
  出さない（エラー時のアラートを除く）」の「アラート」がこれ。**呼ぶ前に `GetOpenFilesList`
  のパスと突き合わせて断る**のが安全（ダイアログなしで避けられるのはこちら側だけ）。
  上書きしたいなら、**呼ぶ前に呼ぶ側がファイルを消す**しかない【推定：消してから保存は試していない】。
- 殻のブリッジの「既にあるファイルへの別名保存は通らなかった」（`plugin/src/McpBridge.cpp`）は
  この 50331649 の場面である。
- 保存先が一時フォルダ（`$TMPDIR` の下）でも通った。
- 親のフォルダはあるが書き込めない場面は、下の「[新しいパスへの保存で、親のフォルダに書き込めないとき（#304）](#新しいパスへの保存で親のフォルダに書き込めないとき304)」。
  **ファイルを足せなければダイアログなしで断られるが、`VW Backup` を作れないだけなら保存は通ってダイアログが出る**（Windows・mac）。

### 「閉じる」（`DoMenuName("Close", 0)`）——**保存した直後なら確認なしに閉じる**。確認の有無は「保存済みか」では決まらない

閉じたかは `GetOpenFilesList` の件数と、対象の `fileRef` が残っているかで見た。戻り値は
**どの回も 0**（閉じても、確認をキャンセルしても）なので、**戻り値で成否は分からない**。

| 閉じた図面 | 保存の確認 | 所要 | 結果 |
| --- | --- | --- | --- |
| 新しいパスへ保存した直後（別名保存した図面・無題から保存した図面） | **出ない** | 154 / 110 ms | 閉じた（件数 −1） |
| 裏から呼び出して保存した直後 | **出ない** | 73 ms | 閉じた |
| **開き直して**、自分のパスへ上書き保存した直後 | **出ない** | 81 ms | 閉じた |
| **保存済みのファイルを `OpenDocumentPath` で開いただけ**（何もしていない） | **出た**（「ファイル『q1-untitled.vwx』で行った変更を保存しますか?」） | （人待ち） | キャンセル → **戻る。図面は残る** |
| 同上（別のファイルで再現） | **出た** | （人待ち） | キャンセル → 戻る。図面は残る |
| 無題・無変更 | **出た** | （人待ち） | キャンセル → 戻る。図面は残る |
| **保存した後に矩形を足した**（undo イベントの外） | **出ない** | **73 ms** | **閉じた——足した矩形は黙って捨てられた** |
| **前の実行で**保存して矩形を足し、制御を返してから閉じた | **出ない** | 75 ms | 閉じた（矩形は捨てられた。#242 と同じ） |

| **前の実行で**保存し、制御を返してから閉じた（対照） | 出ない | 83 ms | 閉じた |

- **刻みの中から呼べる。** 落ちない。確認が出たときは、**人が押すまで呼び出しから戻らない**
  （刻みの中の処理がその間止まる）。**キャンセルされても呼び出しは戻り、図面は残る**
  ——件数が減っていないことで分かる。
- **`OpenDocumentPath` で開いた保存済みの図面は、何もしなくても確認が出る——原因は開き方。**
  3 回とも再現した（別のファイル・別の走行。**開いた実行が返り、Vectorworks に制御が戻った後に
  閉じても出た**——同じ実行の中で閉じたせいではない）。開き方と閉じ方を入れ替えて切り分けた:

  | 開き方 ＼ 閉じ方 | 人が「閉じる」（⌘W） | `DoMenuName("Close", 0)` |
  | --- | --- | --- |
  | 人が「開く」で開いた | **出ない**（人の目視） | **出ない**（182 ms で閉じた） |
  | `OpenDocumentPath(<.vwx>, false)` で開いた | **出た**（人の目視。文言は上と同じ） | **出た**（3 回） |

  **`OpenDocumentPath` で開くと、開いた時点で「変更あり」になっている**。何が変更扱いに
  なっているのかは分からない（開くときの変換や更新が変更として記録されるのかもしれない【推定】）。
  開いた後に**同じパスへ上書き保存してから**閉じると出ない。確かめたのは、そのセッションで
  プローブが保存したばかりの `.vwx` だけ（版の古いファイルでは試していない）。
- **undo イベントの外で足した図形は「変更あり」にしない——そして「閉じる」で黙って消える。**
  保存した後に `CreateRectangle` した図面は、同じ実行の中で閉じても、**制御を返した後の実行で
  閉じても**確認なしに閉じた。上記「[未保存の変更ありは読めない](#未保存の変更ありは読めない)」
  （#242）の「保存済み・undo イベントの外で矩形」と同じ結果である。**「確認が出ないから変更は
  無い」とは読めない**ので、図面に書く道具を持つプラグインは、閉じる前に**呼ぶ側が保存する**か、
  undo イベント付きで書く（または `MarkCurrentDocChanged()` で変更ありにしておく）。後者なら
  人の「閉じる」でも確認が出る（#242）。
- 前面の図面を閉じると、次に前へ出るのは別の図面（上記）。

### CLI の `save` / `close` への帰結

- **`save <パス> --to <新しいパス>`（無題の図面の保存・別名保存）は成り立つ。** 保存先が既に
  あるなら、呼ぶ前に断る（開いているファイルなら警告のダイアログが出てしまうため）。
- **`close` は「保存した直後」でないと確認が出うる**——無題・`OpenDocumentPath` で開いただけ・
  `MarkCurrentDocChanged()` の図面では出る。**人が開いて何もしていない図面なら出ない**。
  CLI に `open` を持たせる（`OpenDocumentPath` で開く）なら、**開いただけの図面でも `close` で
  確認が出る**ことを前提にする（`save` してから `close` すれば出ない）。逆に、**刻みの中で描いただけの変更は確認なしに捨てられる**。確認が出て
  キャンセルされたら、件数が減っていないことで知り、エラーで応える（`quit` と同じ。上記
  「`quit` の事前確認への帰結」）。
- **「保存してから閉じる」の 2 手なら、確認は出ない**（3 例。開き直した図面でも出なかった）。
  呼ぶ側に保存の責任を持たせる設計（#243 の背景）と合う。

#### CLI への帰結（Windows）

- **`save --to` の衝突は、開いている図面のパスと比べても防ぎ切れない。** 既にあるファイルへは
  どの形でも保存できないので、**呼ぶ前に「保存先がディスクにあるか」で断る**（ファイルシステムに
  聞くので大文字と小文字・8.3・`/` を気にしなくてよい）。開いている図面との比較（区切りを
  揃え、NFC、大文字と小文字を区別しない）は、それより先に「どの図面と衝突するか」を
  言うためだけのものになる。**比べ方が文字列の完全一致より緩い分には害が無い**（ダイアログが
  出るのは完全一致だけなので、緩く比べて断れば必ずダイアログの手前で止まる）。
- **`documents` が返すパスは正規化されていない**（`c:\`・8.3 がありうる）。利用者の渡した
  パスと突き合わせるときは、両方を長い名前（`GetLongPathNameW`）に直し、大文字と小文字を
  区別せずに比べる。**自分のパスへ上書き保存するときは、利用者の文字列ではなく
  `GetOpenFilesList` が返した文字列をそのまま `SaveActiveDocumentPath` に渡す**（大小が
  違うだけで断られる）。
- **刻みから `close` を呼ぶ道具は、確認の最中に同じタイマーが入り直すことを前提にする**
  （入れ子の要求を見送る旗。`quit` と同じ）。
- 新規を開く道具は、**開けたかを件数で確かめる**（8 枚の上限で `true` のまま開かない）。
- 260 文字以上の保存先は、呼ぶ前に断ってよい（通らない。境目は上の `MAX_PATH`）。

### 大きな図面でも、呼び出しの中で終わる（#290。mac。Windows は下の節。**実務の図面は測っていない**）

**問い**（[issue #290](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/290)）:
`close` / `save` は戻った直後に `GetOpenFilesList` を読んで成否を決める。大きな図面でも、それは
呼び出しの中で終わっているか。最中にイベントを回すか。どれだけかかるか。応答なしになるか。

**実測**（VW 2026（31.6.0）/ macOS 27.0.1 arm64 の**仮想マシン**・メモリ 8 GB・スワップなし。
`probes/runtime/doc-large/`（役目を終えたので削除済み）を MCP ブリッジで回した＝**OS タイマーの刻みの中**から
呼んだ。ビルド `9f0bc62d52c5` / `406201b53c5d`）。**測った図面は 2 種類で、どちらも実務の図面ではない**:
VW 同梱ライブラリのコピー（270 MB。図形 5 個で、大半はテクスチャなどのリソース）と、プローブが
作った合成の図面（図形は多いが 51 MB まで）。

**結論**

- **呼び出しの中で終わる。** 閉じる・上書き保存・別名保存のすべての回で、戻った直後の
  `GetOpenFilesList` は最終の状態だった（閉じた図面は消え、保存した図面はパスが新しく
  `fIsInMemoryOnly=no`）。保存したファイルの大きさ・更新時刻・ハッシュは、戻った直後と、ランループを
  最長 13 秒回した後とで同じだった。
- **最中はイベントを回さない。** ダイアログが出ない限り、最中に仕掛けた 100 ms のタイマーは、共通モード・

  270 MB のコピー）。**大きな図面を繰り返し保存する呼び方ではディスクを食う。** 環境設定で変わるかは
  確かめていない。

**限界——ここまでで言えないこと**

- **所要は仮想マシンの値**である。実機の絶対値の目安にはしない。

### Windows——同じく呼び出しの中で終わる。入り直すのはダイアログの間だけ（#290。**実務の図面は測っていない**）

- **呼び出しの中で終わる。** 閉じる・上書き保存・別名保存のすべての回で、戻った直後の

- **読むときの罠: ログの `Responding=no` が 5 秒ちょうどに出ている回は、測り方の影響のことがある。** 見張りの
  スレッドの `join` が、送った `WM_NULL` の時間切れまでメインスレッドを止める（1.3 秒の保存の後にも出た）。
  また `IsHungAppWindow` は最後にメッセージを回してからの時間で決まるので、**同じ刻みの中の前の処理の時間も
  含む**。刻みの中で連続して呼ぶ `follow 0` の回の応答なしの列は読まない。

- **上書き保存は `<名前>-VWTMP.swap` へ書いてから置き換える。** 測った回では、パスにファイルが無い時点は

- **実務の図面は mac と同じく測らないまま打ち切った**（参照・レンダリングされたビューポート・数百 MB の図形データ）。
- **所要は 3D アクセラレーションのない ARM の VM でのエミュレーションの値**である。特に描画と描画後の閉じるは、

### CLI の `close` / `save` への帰結（#290）

- **戻った直後に `GetOpenFilesList` を読む作りのままでよい**（mac・Windows）。閉じつつある図面を「残っている」と
  誤読する場面も、書きかけのパスを返す場面も、測った範囲では無かった。
- **最中は何も応えない**（`busy` すら返せない）。mac では刻みが入り直さないので、受け付けの入れ子は
  起きない。**Windows で入れ子になるのはダイアログの間だけ**で、ふつうの保存・閉じるでは起きない。
- **呼ぶ側の 30 秒の上限は、測った範囲の保存・閉じるにはおおむね足りる。** Windows の VM で超えたのは、描画前の
  図面を閉じて確認が出た 1 回（34.6 秒）である。実務の図面では確かめていないので、長くかかる前提で作る。
  **上限を過ぎても処理は続く**ことを道具の説明に書く、という issue の方針はそのまま要る。
- **`close` / `save` より `open` の後を心配する。** 開いた後の描画で次の要求が長く待たされ、**その長さに
  上限は無い**。呼ぶ側のタイムアウトを「失敗」と読まない。Windows の描画前の図面では、その待ちが `close` の
  呼び出しの中へ移ることがある。
- **Windows は約 5 秒を超える `save` / `close` で応答なしの表示になる。** 図面は壊れていないので、失敗と読まない。

## 利用者の図面を上書き保存する——ダイアログが出る場面と、保存先の文字列（#288）

**問い**（[issue #288](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/288)）:
#243・#283 で試したのはプローブが保存したばかりの `.vwx` だけだった。古い版のファイル・読み取り
専用のファイル・ほかで開かれているファイルを、OS タイマーの刻みの中から自分のパスへ上書き保存
すると何が起きるか。保存先 `to` の形と、「すでに開かれています」の比べ方。取り消しの段は
[Undo](Undo.md)。

**この節の表は mac の実測**（VW 2026。保存したファイルのヘッダは `VW31.6.0` / macOS。`probes/runtime/save-dialogs/`
をブリッジの刻みの中から走らせた。ビルド `4bfd53247661` / `ed22904f34e7` / `017577ba80d6`。プローブは役目を終えたので削除済み）。**Windows は測れた範囲を
下の「Windows——測れた範囲」に分けて書いた**（3D アクセラレーションの無い VM で、測れない場面がある）。
保存の呼び出しの間だけ共通モードの `CFRunLoopTimer`（100 ms）を仕掛け、**出た窓の文字をログへ書いて
「OK」を押した**。人が開く場面は `open -a`（Finder で開くのと同じ入口）で開き、開くときの確認は
画面の操作で押した（人の手ではない）。

**結論: 古い版・読み取り専用・使用中のファイルは「ファイルに結び付かないコピー」として開くので、そもそも
上書きにならない（開くときに確認が出るだけ）。見分ける印は `fIsInMemoryOnly=yes`。上書き保存の呼び出しで**
**ダイアログが出るのは、図面のファイルがディスクから消えたときと、開いた後で読み取り専用になったとき**である。

| 古い版・読み取り専用から開いた図面と**無題**の図面（使用中のコピーは試していないが同じ形【推定】） | **`GetOpenFilesList` の自分のパス** | **0** | なし | **`/Applications/VW2026/` にファイルができ、図面がそこへ移る**（`fIsInMemoryOnly=no`）。拡張子も足されない（`ro コピー 1`）。隣に `VW Backup/` もできる |
| 同上 | まだ無いパス | 0 | なし | そのパスへ移る（元のファイルは不変） |
| ふつうの保存済みの図面 | 自分のパス（文字列はそのまま） | 0 | なし（15〜29 ms） | 上書きされる |
| 保存済み・**ファイルをディスクから移した / 消した** | **自分のパス** | 50331649 | **警告「指定したファイルが見つかりません。または間違ったファイル名が指定されています。 （ファイルの終りを確認することができませんでした。）」（OK だけ）**（2 回。押すまで戻らない） | 何もできない（図面は残る。`GetOpenFilesList` のパスも変わらない）。移した先のファイルも不変 |
| 保存済み・**開いた後でファイルを読み取り専用にした**（`chmod a-w`） | **自分のパス** | **0** | **警告「ファイルの保存に失敗しました。ファイル保存中に原因不明のエラーが発生しました。保存操作を再試行してください。」（OK だけ）**（2.1〜2.2 秒後に出る。2 回） | **`GSError` は 0 で、ファイルは置き換わっている**（大きさとハッシュが変わる。読み取り専用のまま） |
| 同上の 2 回目の保存 | 自分のパス | **0** | **同じ警告**（4.1 秒後） | ファイルは置き換わる。**そのうえ図面のパスが `/Applications/VW2026/a.vwx` へ変わり、`outSaved=no`**。次の保存はアプリのフォルダへ書く（試して消した）。元のフォルダの `.a.lck` は閉じても残った。そのファイルを開き直すと、足した図形があった |

- **`GetOpenFilesList` のパスをそのまま保存先に渡すと、無題の図面でもアプリのフォルダへ黙って保存される。**
  プローブがこれで `/Applications/VW2026/` に実際に書いた（確かめて消した）。「自分のパスへ」は
  `fIsInMemoryOnly=no` の図面に限る。
- **上書き保存のダイアログを避けるには、呼ぶ前に自分のファイルがディスクにあること、書き込めることを見る。**
  書き込めないときの `GSError` は 0 なので、**戻り値では失敗も成功も分からない**（文言は「失敗」だが中身は置き換わっている）。
  開いた後で親のフォルダを書き込めなくした場面とロック・ACL は「上書き保存の前に『書き込めない』と判定する（#293）」にある。
- ほかの利用者・ほかの計算機が開いている場面は**試していない**（1 台の Mac で Vectorworks を 2 つ
  起動した）。どちらの計算機名でも確認の文言の括弧の中が変わるだけと読める【推定】。
- 読み取り専用のフォルダの中の、書き込める図面の上書きは、警告が 2 枚出てファイルは変わらない（#293）。

### ロックファイル `.<名前>.lck`

図面を開いている間、**ファイルの隣に隠しファイル `.<拡張子を除いた名前>.lck`** ができ、閉じると消えた。

```xml
<FileLock>
  <FileLockInformation>
    <User>Vectorworks</User>
    <Computer>Vectorworksの仮想マシン</Computer>
    <LockedTime>3876653709</LockedTime>
  </FileLockInformation>
</FileLock>
```

- `LockedTime` は 1904 年起点の現地時刻の秒らしい【推定】（3876653709 が測った日時の JST に合う）。
- **ファイルがあるだけでは「使用中」にならない。** 他人の名前で同じ形の `.lck` を手で置いて開くと、
  **確認なしに開き、中身を自分の名前へ書き換えた**。本物のもう 1 つの Vectorworks が開いていれば
  確認が出たので、生きているかを別の手段（ファイルロックなど）で見ている【推定】。**`.lck` を読んで
  「使用中」と断る判定は当てにならない。**
- SIGTERM で終了させると（保存の確認を「保存しない」で抜けると）`.lck` は消えた。

### 保存先 `to` の形（無題の図面から）

| 保存先 | `GSError` | ダイアログ | どうなるか |
| --- | --- | --- | --- |
| 拡張子なし `noext` | 0 | なし | **そのままの名前で保存**（拡張子は足されない） |
| `name.txt` / `name.sta` / `name.dwg` / `NAME.VWX` | 0 | なし | **その名前で保存。中身はどれも Vectorworks の形式**（先頭に `VW31.6.0`）。`.dwg` に変換はされない |
| 既にある `NAME.VWX` を大小だけ変えた `name.vwx` | 50331649 | なし | 何も起きない（APFS は大小を区別しないので「既にある」） |
| **親のフォルダが無い** `nofolder/x.vwx` | 50331649 | なし | 何も起きない（**フォルダは作られない**） |
| 親が**ファイル** `afile/x.vwx` | 50331649 | なし | 何も起きない |
| 親が**書き込めないフォルダ** | 50331649 | なし | 何も起きない |
| **`/` で終わるパス**（フォルダ） | **50331652**（`0x03000004`） | なし | 何も起きない。`IFileIdentifier::Set` の読み戻しが空になる |
| `bad?name.vwx` / `bad:name.vwx` / `trail.vwx.` | 0 | なし | **その名前のまま保存**（Windows は `%3F`・`%3A` に化ける。下記） |

- `.sta` で保存したファイルをテンプレートとして開けるかは試していない。
- **保存すると、保存先の隣に `VW Backup/<名前>-バックアップ-<年月日時分秒>.<拡張子>` ができる**
  （この機械の環境設定で。拡張子が無いと名前は `.` で終わる）。
- **呼ぶ前に断るなら**: 拡張子は `.vwx` を求める（無いと、Vectorworks で開ける名前にならない）。
  親のフォルダの有無はダイアログに関わらないので、断るのはエラーの文を分かりやすくするためだけ。

### 「このファイルはすでに開かれています。」の比べ方（mac）——**Windows と同じ文字列の完全一致**

別の図面が `…/比較がぎ-a.vwx`（NFC）を開いている状態で、無題の図面から保存した。

| 渡した文字列 | ファイルがディスクにある | **ファイルを移した / 消した後** |
| --- | --- | --- |
| **同じ文字列** | **警告**（OK だけ。50331649） | **警告**（同じ。**ファイルが無くても出る**） |
| 大文字と小文字だけ違う（`…-A.vwx`） | なし（50331649。既にあるため） | **なし。`GSError=0` で保存される** |
| **NFD** | なし（50331649） | **なし。`GSError=0` で保存される** |
| `/private` を付けた `/private/var/…`（同じファイル） | なし（50331649） | 試していない |

- **判定は文字列の完全一致**（ファイルシステムの同一性を見ていない）。ファイルが無くても出るので、
  開いている図面の一覧とだけ比べている【推定】。
- ファイルを移した後に大小違い・NFD 違いで保存すると、**同じファイルを指す図面が 2 枚開いたまま**に
  なる（`GetOpenFilesList` に別の文字列で 2 行並ぶ）。
- **読み戻しの文字列は渡したまま**（NFD は NFD のまま。`GetOpenFilesList` にもそのまま出る）。
- **同じファイルでも入口で文字列が変わる。** `open -a` で開くと `/private/var/folders/…`、
  `SaveActiveDocumentPath` に `/var/folders/…` を渡すと `/var/folders/…`（シンボリックリンクを直さない）。
- **自分のパスの文字列違い**（ファイルあり）: 大小違い・NFD・`/private` 付きは、どれも
  **50331649・ダイアログなしで上書きにならない**。一覧の文字列そのままなら通る（Windows と同じ）。

### CLI の `save` への帰結（mac）

- **`to` を省いた `save` は `fIsInMemoryOnly=no` の図面に限る。** `yes`（無題・古い版・読み取り専用・
  使用中のコピー）は、呼ぶ前に「`to` が要る」と断る。そうしないとアプリのフォルダへ黙って書く。
- **呼ぶ前に、自分のファイルがディスクにあること、書き込めることを確かめて断る。** この 2 つが上書き保存で
  ダイアログが出る場面である。書き込めない場面を見逃すと 2 回目の保存で図面のパスがアプリのフォルダへ移る。
- **`to` と開いている図面の比較は「区切りを揃えて完全一致」で足りる。** 出るのは完全一致だけで、
  ディスクにあれば別に断る。ただし**緩く比べて断っても害は無く**、ファイルを移した後に同じファイルを
  指す 2 枚目ができるのを防げるので、**いまの予定（NFC・大文字と小文字を区別しない）のままでよい**。
- `to` には `.vwx` を求める。親のフォルダの有無も断ってよい（どちらでもダイアログは出ない）。
- **利用者が古い版のファイルを `open`（CLI）で開くと、確認なしにコピーになる。** 開いた後のパスを
  返して、元のファイルには保存されないことが分かるようにする。

### 上書き保存の前に「書き込めない」と判定する（#293）

**問い**（[issue #293](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/293)）: 保存済みの図面を自分のパスへ

**結論（Windows）: 確実にダイアログが出るのは「親のフォルダにファイルを足せない」ときで、呼ぶ前に親のフォルダの `FILE_ADD_FILE` を聞けば当たる。ファイル自身の読み取り専用も書き込み拒否の ACL も 1 回目は断られず、ファイルは置き換わる**（VW は隣に新しいファイルを作って置き換えるので、ファイルの権限が効かない。置き換えの後は属性も ACL も消える）。**ただし読み取り専用にしたファイルは、続く保存で警告が出ることがある（7 回中 2 回。原因不明。下）。**
**`CreateFileW(GENERIC_WRITE)` は判定に使えない**——開いている図面のファイルは書ける場面でも共有違反（32）になる。

| ファイルのロック | **-1（`EPERM`）** | **yes** | 644 | 1 | 0 | no | ok | **1 枚** |
| ファイルに拒否の ACL | **-1（`EACCES`）** | no | 644 | 13 | 0 | no | ok | **なし**（`access` と食い違う唯一の行） |
| 親を `chmod a-w` | 0 | no | 644 | ok | **-1（`EACCES`）**（755→555） | no | 13 | **2 枚** |
| 親に拒否の ACL | 0 | no | 644 | ok | **-1（`EACCES`）**（755 のまま） | no | 13 | **2 枚** |
| 親のロック | 0 | no | 644 | ok | **-1（`EPERM`）** | **yes** | 1 | **2 枚** |

- **`access(W_OK)` は ACL もロックも反映する**（Windows の `_waccess` と違う）。ロックは `EPERM` で、`stat` の `st_flags` を見なくても分かる。
- 親のモードだけでは足りない（ACL の行は 755 のまま）。親のフォルダは `access` で聞く。
- **Windows との違い**: mac はファイル自身の読み取り専用・ロックでもダイアログが出る。Windows は親のフォルダだけである。ACL で ACE が消えるのは同じ。

### CLI の `save` への帰結（書き込めない。mac。#293）

- **`to` を省いた上書き保存の前に、ファイルと親のフォルダの両方へ `access(W_OK)` を聞き、どちらかが -1 なら `internal`（`file_read_only`）で断る。** これでダイアログの出る場面（上の 5 行）を漏らさない。ただし、**sticky のフォルダのほかの利用者のファイルはこれを通ってダイアログが出る**（「sticky ビットのフォルダの上書き保存（mac。#298）」）。
- **ファイルの書き込み拒否の ACL も断ることになるが、断ってよい**（ダイアログは出ないが、利用者が拒否したファイルを黙って置き換えて ACE を消すため）。ACL だけ通したいなら、ファイルの判定を「`st_flags` の `UF_IMMUTABLE` と、自分に書き込みの許可があるモードか」に替える。所有者以外のモードは測っていないので、既定は `access` にする。
- **失敗した保存を繰り返さない。** ロックの 2 回目で図面のパスがアプリのフォルダへ移る（`chmod a-w` も #288 のとおり同じ）。
- 呼んだ後の確かめには戻り値も `outSaved` も使えない。必要ならファイルの更新時刻を比べる（`chmod a-w` の場面は警告が出ても変わる）。

### CLI の `save` への帰結（書き込めない。Windows。#293）

- **`to` を省いた上書き保存の前に、親のフォルダへ `CreateFileW(FILE_ADD_FILE, FILE_FLAG_BACKUP_SEMANTICS)` で聞く。**
  アクセス拒否（5）なら `internal`（`file_read_only`）で断る。これでダイアログの出る場面を漏らさない。
- **`GetFileAttributesW` の `FILE_ATTRIBUTE_READONLY` も見て断る。** 1 回目はダイアログが出ないが、利用者が読み取り専用にした
  ファイルを黙って置き換えて属性を消すうえ、続く保存で警告が出ることがある（上の 7 回中 2 回）。
- **ファイルの書き込み拒否の ACL は断らなくてよい**（ACL の場面の保存 6 回でダイアログは出ていない。ただし ACE ごと消える）。
  見るなら `AccessCheck(FILE_GENERIC_WRITE)`。`_waccess` は ACL を見ないので使わない。
- **ファイルに `CreateFileW(GENERIC_WRITE)` しない**（図面を開いている間は必ず 32）。
- 呼んだ後の確かめには戻り値も `outSaved` も使えない。必要ならファイルの更新時刻を比べる。

### CLI の `save` への帰結（リンク。mac。#298）

- **`to` を省いた上書き保存は #293 の判定のままでよい。図面のパス（一覧の文字列）のファイルと親へ `access(W_OK)` を聞く。** 図面のパスはもうリンクの先なので、追加で解決しない。親のフォルダがリンクの場面も `access` が追うので当たる。Windows の「文字列から切り出す」と同じ書き方で両方に当たる。
- **`to` に渡された文字列を `lstat` で見て、シンボリックリンクなら断る**（Windows の帰結と揃う）。断らないと次のことが起きる。
  - **自分の図面を指すリンクは「開いている図面との比較」をすり抜け**、上書きになる。先のフォルダに足せないと 2 枚のダイアログが出る。リンクの文字列の親へ聞いても当たらない。
  - 実体の無いリンクでは、保存先が渡した文字列と違うフォルダになる。2 段なら中間のリンクが通常のファイルに置き換わる。
- **`open` の結果は渡した文字列でなく、開いた後の図面のパスを返す**（リンクを渡すと先の文字列になる）。2 段のリンクと実体の無いリンクは `false` で断られる。
- 利用者がメニューや Finder からリンクを開いた場面は測っていない。

### sticky ビットのフォルダの上書き保存（mac。#298）

**結論: `chmod +t` のフォルダで、ファイルも親のフォルダも自分のものでないと、#293 の判定を通るのにダイアログで止まる。呼ぶ前に `stat` の持ち主と `S_ISVTX` で当たる。**

### CLI の `save` への帰結（sticky。mac。#298）

- **`to` を省いた上書き保存の前に、#293 の `access(W_OK)` に足して、親のフォルダとファイルを `stat` し、親が `S_ISVTX` で、親の `st_uid` もファイルの `st_uid` も `geteuid()` と違うなら `internal`（`file_read_only`）で断る。** これでダイアログの場面を漏らさず、出ない場面（親かファイルが自分のもの）は断らない。
- `geteuid()` が 0（root）のときは測っていない。root なら規則上消せるので断らないのが自然である【推定】。
- **断らずに通る場面でも、ほかの利用者のファイルの持ち主は黙って自分に変わる**（sticky なしのフォルダと、自分が持ち主の sticky のフォルダ）。#293 の ACL で ACE が消えるのと同じで、VW がファイルを作り直すためと読める【推定】。
- **`.swap` は VW が消さない。** 判定で断れば残らない。

- **`GetFullPathNameW` の答えはファイルの場所と一致する**: `x.\a.vwx` → `x\a.vwx`・`x .\a.vwx` → `x \a.vwx`。`x..\`・`x...\`・`x \`・`x  \`・`x. \` は変わらない。
- **同じ文字列での上書きと「閉じる」は通った**（`GSError=0`・ダイアログなし。`x.\`・`x..\` は 2 回、`x \` は 1 回）。`VW Backup\` と `.a.lck` は実際のフォルダにできる。
- **`x.\` は開いている図面と比べられない。** `…\x.\e.vwx` を開いている状態で（実体は `…\x\e.vwx`）:

  | 操作 | 結果 |
  | --- | --- |
  | 別の図面から `…\x.\e.vwx`（同じ文字列）へ保存 | 警告「このファイルはすでに開かれています。」（OK だけ）→ 50331649 |
  | 別の図面から `…\x\e.vwx`（同じファイル）へ保存 | ダイアログなし・50331649（既にあるため。上書きされない） |
  | `…\x\e.vwx` を `OpenDocumentPath` | `true`・確認なし（3270 ms）で `C:\Program Files\VW2026\e コピー 1`（`fIsInMemoryOnly=yes`） |

- 閉じた後に `…\x.\e.vwx` を `OpenDocumentPath` すると `true` で、**`x.\` が残ったパスで開く**（`fIsInMemoryOnly=no`）。その文字列のまま上書きも通る。
  `…\x\e.vwx` で開いた自分の図面を `…\x.\e.vwx` へ保存すると、ダイアログなし・50331649（上書きにならず、ファイルは変わらない）。
- **末尾の `.`・空白は、パスの末尾に来ると落ちる。** `GetFullPathNameW` は区切りで終わらない `…\x.`・`…\x..`・`…\x...` をどれも `…\x` にする。**親のフォルダの文字列を切り出して OS に聞くと、別のフォルダの答えが返る**:
  - `x..` だけがあるときの `…\x..`、`x ` だけがあるときの `…\x ` への `GetFileAttributesW` は 2（無い）。
  - **足せないフォルダ: `x..` と `x` の両方があり、`x..` にだけ `(WD,AD)` の拒否を付けると、`…\x..` への `CreateFileW(FILE_ADD_FILE)` と `AccessCheck` は `x` を見て「許す」と答えるのに、保存は 2 枚のダイアログ（#293 の親に足せないときと同じ文言）で止まる**（`GSError=0`・ファイルは変わらない）。**#293 の判定はこの形のパスでは当たらない。** 親に一時ファイルを作る手（`…\x..\~名前`）だけは 5 で当たった。
- **無題の図面への上書きは別の話。** 図面のパス（`C:\Program Files\VW2026\名称未設定 9`、`fIsInMemoryOnly=yes`）をそのまま渡すと、書き込める場所なら `GSError=0` で
  `名称未設定 9` というファイルがアプリのフォルダにでき、`fIsInMemoryOnly=no` になる（昇格した VW。手順の誤りで踏んだ）。`to` を省く上書きは無題の図面で呼ばない。

### CLI の `save` への帰結（パスの形。#294）

- **`to` は呼ぶ前に字面で正規化してから VW に渡す（mac・Windows とも）。** `.` の段を落とし、`..` を畳む（VW の処理に任せると、`.` が残るうえ
  `x\.\..\a.vwx`・`x/./../a.vwx` が別のフォルダに黙って保存される）。**`.` を先に落とす**（VW の順に合わせない）。正規化した文字列を比べれば
  `to_is_open` も `.` の違いに左右されない。
- **mac で受ける形**: `/` から始まる絶対パス。`//` は VW も畳むが、比べるために正規化の側でも畳む。シンボリックリンクを段に含むパスは
  測っていない（字面で畳むと OS の解決とずれうる。`/var` と `/private/var` は上の節のとおり直さない）。
- **以下は Windows の形。**
- **断る形**: `\\?\`（VW が受けないので `invalid_args` で理由を言う）・ドライブ相対・ルート相対（どれもダイアログは出ないが
  エラーの文を分かりやすくするため）・`\\.\`（通るが、図面のパスにデバイスの名前空間が残って以後の比較に使えない）。
- **途中の段の末尾が `.` か空白のパスも断る**（`invalid_args`。#299）。正規化では片付かない:
  `x.\` は `x\` に直せるが、`x..\` と `x \` は実在する別のフォルダを指しうるので直せない。残したまま受けると、親のフォルダの判定（#293）が
  別のフォルダを見てダイアログを断れない。**`GetFullPathNameW` では検出できない**（`x..\`・`x \` を変えない）ので、段の末尾を字面で見る。
  `.` と `..` だけの段は正規化で先に片付くので、ここの対象ではない。`\\?\` でしか作れない名前なので、断って困る場面は少ない【推定】。
- **受ける形**: ドライブ文字から始まる絶対パスと UNC。
- UNC と `C:\…` は同じファイルでも別の文字列で、比較では別物になる。既にあるファイルは VW が 50331649 で断るのでダイアログには
  ならず、放っておいてよい。
- 260 文字以上のパスは呼ぶ前に断ってよい（`\\?\` の逃げ道は無い。境目は `MAX_PATH`）。

### CLI の `save` への帰結（Windows）

mac の帰結に次を足す。

- **`to` は呼ぶ前に確かめる。** 区切りを `\` に直し、`< > : " | ? *` を含む名前を断る。VW に渡すと
  `GSError=0` のまま別の名前のファイルになり、成功と見分けが付かない。
- **保存の後は、前面の図面のパスを読み直して返す**（渡した文字列を返さない）。
- 「ファイルが消えた」の確認は Windows でも残す（ドライブが外れた場面でダイアログが出るため）。
- `to` と開いている図面の比較は、いまの予定のままでよい（大小違いは VW が断るが、緩く断っても害は無い）。
  **NFC にそろえて比べると、NFD の別のファイルへの保存も断ることになる**が、見た目が同じ図面が 2 枚並ぶほうが
  困るので断ってよい。

### 新しいパスへの保存で、親のフォルダに書き込めないとき（#304）

**問い**（[issue #304](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/304)）: 無題の図面を
`SaveActiveDocumentPath` で**まだ無いパス**へ保存する。親のフォルダはあるがファイルを足せないとき、ダイアログが出るか。
CLI の `save` は上書き保存を持たず、新しいパスへの保存だけにする（#288・#293・#298 で上書き保存のダイアログを
前もって確かめきれなかったため）。

**実測（Windows）**: VW 2026（31.6.0）/ Windows 11 ARM64 の VM。**アカウントが管理者で VW も昇格して動いている**（#288）。
`probes/runtime/newpath-close/` の `steps-win-304.do` / `steps-win-304b.do` をブリッジで回した（刻みの中から呼んだ）。
ビルド `a188da4237a8`。どれも無題の図面に矩形を 1 つ作ってから保存した。見張りが窓の文言を書き、1 秒見せてから OK を押した。

**結論（Windows）: ファイルを足せないときはダイアログなしで断られる（50331649）。ダイアログが出るのは、ファイルは足せるのに
保存先のフォルダに `VW Backup` フォルダを作れないとき**——そのときは**保存は通り**（`GSError=0`）、OK だけの警告が
保存のたびに出る。

| 場面（保存先の親のフォルダ） | `GSError` | 所要 | ダイアログ | ファイル |
| --- | --- | --- | --- | --- |
| 書ける（基準） | 0 | 109 ms | なし | できる |
| **`Everyone:(WD)` の拒否**（`FILE_ADD_FILE` だけ。フォルダは作れる） | **50331649** | 2 ms | **なし** | できない |
| `Everyone:(WD,AD)` の拒否（#293 と同じ形。#288 の「Write の拒否」もここ） | 50331649 | 5 ms | なし | できない |
| **読み取り専用のボリューム**（64 MB の VHD を `attributes volume set readonly`）の下のフォルダ・根 | 50331649 | 1 / 4 ms | なし | できない |
| **読み取り専用の共有**（`\\localhost\p304ro`。`net share /GRANT:Everyone,READ`。NTFS は書ける） | 50331649 | 4193 ms | なし | できない |
| フォルダに読み取り専用の属性（`attrib +r`。フォルダには効かない） | 0 | 60 ms | なし | できる |
| **`Everyone:(AD)` の拒否**（**サブフォルダの追加**だけを拒む。ファイルは足せる） | **0** | 2365 / 2258 ms | **警告**（下。OK だけ。押すまで戻らない） | **できる**。`VW Backup` はできない |

警告の文言（題 `Vectorworks` の `#32770`、ボタンは OK＝ID 1 だけ）:

> バックアップフォルダを作成することができませんでした: C:\Users\…\p304\ad\VW Backup\

- **`icacls` の `AD` はファイルの追加ではない。** ディレクトリでは `WD`＝`FILE_ADD_FILE`、`AD`＝`FILE_ADD_SUBDIRECTORY`。
  最初の周では `AD` だけを拒否して「`FILE_ADD_FILE` の拒否」のつもりでいたが、保存が通って警告が出たので取り違えに気付いた。
  エクスプローラーの「書き込み」の拒否は両方を含む（#293 の `(WD,AD)`）。
- **警告が出ても `GSError` は 0 で、図面は保存先へ移り（`outSaved=yes`）、ファイルもできている。** 戻り値ではダイアログが
  出たか分からない。警告が出るのは、保存の 1.1〜1.2 秒後（上書き保存では 0.3 秒後）。
- `VW Backup` を作るのは「保存の前のバックアップ」の設定による【推定：設定を切った場合は測っていない】。基準の書けるフォルダでも
  初回の保存で `VW Backup` ができた回がある（新しいパスへの保存でもバックアップを作ろうとする）。
- **呼ぶ前の OS への問い合わせ**（`oscheck`。保存先の親について）:

  | 場面 | `CreateFileW(FILE_ADD_FILE, BACKUP_SEMANTICS)` | `AccessCheck(FILE_ADD_FILE)` | 一時ファイルを作る | 結果 |
  | --- | --- | --- | --- | --- |
  | 書ける | ok | 許す | ok | 保存できる |
  | `(WD)` / `(WD,AD)` の拒否 | **5** | **拒む** | **5** | 断られる（ダイアログなし） |
  | 読み取り専用のボリューム | **ok** | **許す** | **19**（`ERROR_WRITE_PROTECT`） | 断られる |
  | 読み取り専用の共有 | **5** | 許す（NTFS の ACL しか見ない） | 5 | 断られる |
  | `(AD)` の拒否 | ok | 許す | ok | **保存できて警告** |

  - **ファイルを足せるかを当てるのは「一時ファイルを作ってみる」だけ**（読み取り専用のボリュームでは `CreateFileW` も
    `AccessCheck` も「書ける」と答える）。ただし外れても VW がダイアログなしで断るだけなので、**事前の判定は必須ではない**。
  - **警告の場面（`VW Backup` を作れない）は、どの問い合わせにも出ない。** 当てるなら、保存先の `VW Backup` が
    フォルダとしてあるか、無ければその場所にフォルダを作れるか（`FILE_ADD_SUBDIRECTORY`）を聞く。
- 昇格しない利用者では測っていない（#293 の非昇格の測定では、権限の無いフォルダへの新しいパスの保存は 50331649・ダイアログなし）。
**実測（mac）**: VW 2026（31.6.0）/ macOS 27.0.1（Apple M1 Pro の VM）。`steps-mac.do` の #304 の部分を
`vw_run_probe` で回した。ビルド `7961f913f452`。作り方は Windows と同じ（無題の図面に矩形 1 つ、見張りが文言を書いて 1 秒後に OK）。

**結論（mac）: Windows と同じ。** ファイルを足せなければダイアログなしで断られ（50331649）、`VW Backup` を作れないときだけ
保存が通って同じ文言の警告が出る。

| 場面（保存先の親のフォルダ。mac） | `GSError` | 所要 | ダイアログ | ファイル |
| --- | --- | --- | --- | --- |
| 書ける（基準） | 0 | 30 ms | なし | できる。**初回の保存で `VW Backup/new-バックアップ-<時刻>.vwx` もできた** |

| **`chflags uchg`**（Finder のロック） | 50331649 | 0 ms | なし | できない |
| **読み取り専用でマウントしたディスクイメージ**（`hdiutil attach -readonly`）の下のフォルダ・根 | 50331649 | 1 / 1 ms | なし | できない |

| 同上・矩形を足して続けて上書き保存（`save`） | 0 | 1113 ms | **同じ警告**（101 ms 後） | 置き換わる |

警告の文言（`NNADialogWindow`、シートではない。ボタンは OK だけ）:

> バックアップフォルダを作成することができませんでした: /var/folders/…/p304/addsub/VW Backup/

- 断られた場面はどれも、図面は無題のまま（`fIsInMemoryOnly=yes`・`outSaved=no`）、保存先のフォルダは空のまま。
- 所要の 1.1〜1.3 秒の大半は見張りが OK を押すまでの 1 秒で、警告そのものは保存の 0.1〜0.2 秒後に出る（Windows は 1.1〜1.2 秒後）。
- **呼ぶ前の OS への問い合わせ**（`oscheck`。保存先の親について）:

  | 場面 | `access(W_OK)` | 一時ファイルを作る | 結果 |
  | --- | --- | --- | --- |
  | 書ける | 0 | ok | 保存できる |
  | `chmod a-w` | **−1・`EACCES`** | `EACCES` | 断られる（ダイアログなし） |
  | `deny add_file` | **−1・`EACCES`** | `EACCES` | 断られる |
  | `chflags uchg` | **−1・`EPERM`**（`st_flags` に `UF_IMMUTABLE`） | `EPERM` | 断られる |
  | 読み取り専用のディスクイメージ | **−1・`EROFS`** | `EROFS` | 断られる |
  | **`deny add_subdirectory`** | **−1・`EACCES`** | **ok** | **保存できて警告** |

    だから **mac では親への `access(W_OK)` が 0 でなければ断る、で、ダイアログなしで断られる場面と警告の場面（`VW Backup` を作れない）を
    まとめて避けられる**。#293 の上書き保存の判定（mac は `access(W_OK)`）とも同じ道具で揃う。
  - **それでも `VW Backup` という名前のファイルがある場面は通ってしまう**（`access` は 0）。ここだけは別に見る。
- 管理者でない利用者・ネットワークのボリュームは測っていない。

### CLI の `save` への帰結（新しいパスで書き込めない。#304）

mac は、保存先の親に `access(W_OK)` を聞いて −1 なら断る（ファイルを足せない場面と、`VW Backup` を作れない場面がどちらも −1 になる）。
そのうえで、保存先の `VW Backup` が**フォルダ以外のもの**としてあれば断る。Windows は次のとおり。


- **ファイルを足せない保存先は、VW がダイアログなしで断る（50331649）。** 前もって断るなら「一時ファイルを作ってみる」で
  当てられる（`FILE_ADD_FILE` の問い合わせは読み取り専用のボリュームを見逃す）が、見逃しても害は無い。
- **`VW Backup` を作れない保存先では、保存は通るのにダイアログが出る。** 呼ぶ前に、保存先のフォルダの `VW Backup` を見て、
  **フォルダとしてあればよし**、**無ければフォルダを作れるか**（実際に作って消すのが確か。`FILE_ADD_SUBDIRECTORY` の問い合わせで当たるかは測っていない【推定】）、
  **同じ名前のファイルがあれば断る**。作れない保存先は `internal` で断る。

## `CloseAllFilesAndQuitVectorworks`（終了）

```cpp
// ISDK.h:3799
virtual void CloseAllFilesAndQuitVectorworks(bool bAskForSave = true, bool bRestart = false) = 0;
```

SDK の説明文は「Closes all files and then gracefully quits Vectorworks」。`bAskForSave` が
偽なら確認せずに閉じてそのまま終了、`bRestart` が真なら終了後に起動し直す。**戻り値は無く、
キャンセルされたときどうなるかも書かれていない**。SDK 自身のシステムテストは
`CloseAllFilesAndQuitVectorworks(false)` で呼んでいる（`VWFC/Tools/CatchSystemTest.cpp:87`）。

### 呼んだ後の振る舞い（mac / Windows で実測）

詳細と数値は [Timers and Notifications](Timers%20and%20Notifications.md) の 4 の 9。ここには
文書の側から見た要点だけを置く。

- **呼び出しは戻る。** 図面を閉じ終えてから戻り（保存済み・図面 0 枚なら mac 99〜196 ms・
  Windows 711〜1287 ms）、**プロセスはその後に正常に終わる**（`atexit` まで届く。mac は
  4〜8 秒後・Windows は 28〜30 秒後）。
- **保存の確認は「未保存の変更」がある文書にだけ出る**（`bAskForSave=true`）。
  保存済みの文書・図面 0 枚なら確認なしで終わる。
- **確認で「キャンセル」すると、呼び出しはそのまま戻り、図面は開いたまま残る。**
  Vectorworks は動き続け、`gSDK` もふつうに呼べる。**戻り値が無いので、キャンセルされたことは
  `GetOpenFilesList()` の件数（減っていない）か、プロセスが生きていることで知る。**
- **確認の最中にもう一度呼ぶと、確認が 2 つ重なって出る。** 落ちはしない。Windows では
  呼んだタイマー自身が確認の最中に入り直すので、「呼び出しの最中」を旗で持って見送る。
- **`kNotifyBeforeApplicationQuit` は確認の前に届き、キャンセルされても届く。**
  「本当に終わる」合図にはならない。本当に終わるときは、最後に `plugin_module_main` へ
  `kPluginModuleDeinit`（-2）が届く（`atexit` の約 0.1 秒前）。

## 結論（プラグイン開発への示唆）

- **「周ごとにテンプレートから新しい図面を開いて、そこへ描く」は実機で成立する。**
  コマンド実行中に **`OpenDocumentPath(<テンプレートの .sta>, false)`** を呼べばよい。
  **テンプレートの中身を持った無題の新規文書**が開き、カレント文書も描画先も即座に移る。
  当初この筋は「テンプレート専用 API が無いので不可」と結論していたが、**それは誤り**
  だった——`Open` 側に `.sta` の扱いが入っている。
- **前の文書は開いたままにしても、閉じてもよい。** ハンドルは生きていて
  `SwitchToOpenFile` で行き来でき、読みも（名前の書き換えという範囲では）書きもできる。
  閉じたいなら `CloseDocument()` で閉じられる——**未保存でも閉じられる**。
- **【危険】`CloseDocument()` は確認せずに捨てる。** 保存確認ダイアログは出ず、未保存の
  変更は黙って消える。**人が編集中の文書を閉じない**こと——自分が開いた文書だけを対象に
  する（`outSaved` は「ディスクにあるか」でしかなく、**保存済みの文書の変更は見えない**）。
- **「未保存の変更があるか」は SDK から読めない。** 分かるのは「一度もディスクへ保存されて
  いない」（`fIsInMemoryOnly` / `outSaved`）までで、保存済みの文書を変更した状態は
  どちらにも現れない（上記「未保存の変更ありは読めない」）。
- **成否を戻り値で判定しない。** `CloseDocument()` も `SetObjectName()` も、成功しながら
  `false` を返す。**`GetOpenFilesList` の件数**や**読み戻した値**で確かめる。
- **「保存 → そのパスを開く」は続けて書かない。** 保存した時点でその文書自身がその
  ファイルなので、開き直しは `false` になる。閉じてから開く。
