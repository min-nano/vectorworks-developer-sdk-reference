# データタグ

データタグ（`Data Tag` PIO）を SDK から生成し、スタイルを使わずに per-instance で中身（タグ
レイアウト）を組むときの作法と、タグフィールドの式（`#…#` 記法）の文法・高さの綴り
（[#187](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/187)・
[#190](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/190)・
[#194](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/194)・
[#196](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/196)・
[#198](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/198)・
[#245](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/245)）。
断りが無ければ VW 2026 / mac で実測。式ごとの実測の表・舞台・プローブは
[計測記録](../Metrics/Data%20Tags.md)。

- **スタイル無しでもタグは組める。** スタイルを挟むとシンボル定義のサブタイプ
  （`SetSymbolDefSubType`）とパラメータ対応表（`SetAllPluginStyleParameters`）が要り、漏れると
  「タグは出るのに中身が空」になる。per-instance に直接組む方が壊れにくい。
- **タグレイアウトはタグ自身のプロファイルグループ**（`GetCustomObjectProfileGroup` /
  `SetCustomObjectProfileGroup`。VW2020 の `…InAux` の入り口もあるので両方見る）。中身は
  **式を持たせたテキスト**（`IDataTagTextLinkSupport::SetIsLinked` / `SetFormula`）で、
  **フィールドラベルはテキストの名前ではない**。生成直後の既定のロクスは取り除き、手作りと同じ
  並びに揃える。
- **中身を入れてから渡す。** 空のグループを先に渡して後から足すと、VW が複製していた場合に
  テキストが迷子になる。渡した後は実際に持っているものを取り直し、複製されていればこちらを消す。
- **組んだら `IDataTagSupport::UpdateUserDefinedTextsUIDs` をタグへ呼ぶ**（無いと式を拾わず値が空）。
- **関連付けはレイアウトを組むより先。** 相手を決めてから中身を組み、最後に `UpdateDataTag`。
- **タグは指定した挿入点に留まらず、実寸もレイアウトの中身で決まる。** **置いた後に
  `GetObjectBounds` で実位置と実寸を測って動かす**のが唯一確実な手（VW がどこへ落とすかは
  ビューポートによってもばらばら）。
  - **置いて `UpdateDataTag` した直後の外接をそのまま使ってよい**——VW へ戻った後も 1 桁も
    動かなかった（#245。デザインレイヤで測った。ビューポートの注釈に置いたタグは測り直しに
    入っていない。[実測](../Metrics/Data%20Tags.md#データタグ--計測記録)）。
  - **`MoveObject` で動かしたタグは外接が直後から追随する**（`ResetObject` も undo イベントの
    終わりも待たない。[Investigation Techniques](Investigation%20Techniques.md)「いつ読むか」）。
- **「関連付け先からの相対で置く」は成り立たない（打ち切った調査）。** 2 度試して外した——
  実際は「高さは合っていて横だけ一定量ずれる」純粋な平行移動で、「置いた後に測って動かす」が正解。
- **注釈へ後から足した図形のクラスはビューポートで非表示のまま。** 置いた後に全クラスを表示へ
  戻して再更新する。
- **描画属性をクラスに従わせるなら、タグレイアウトの中のテキストにも要る**（`SetObjectClass` ＋
  7 つの `Set*ByClass`。**`SetClassByName` / `SetAllAttributesByClass` は SDK に無い**——
  [Attributes and Classes](Attributes%20and%20Classes.md)）。文字スタイルを当てた**後**にクラスを
  与える（書体・大きさは文字スタイル、色・線の太さはクラス）。
- **図面ラベル（`Drawing Label2`）は式の綴りは同じ**（`#Drawing Label2#.#Title#`）**だが、
  `IDataTagTextLinkSupport` が効かない**（`IsSupported` が `false`）ので、既定のレイアウトの
  テキストを複製するしかない（[Drawing Labels](Drawing%20Labels.md)）。

## タグフィールドの式——文法は 2 系統あり、綴りは SDK に 1 文字も書いていない

- **文法は 2 系統**: `SetFormula` の第 3 引数 `isWorksheetFormula`（既定 `false`。読み戻しは
  `GetIsWorksheetFormula`）で、独自の `#…#` 記法とワークシート式を選ぶ。【ヘッダ根拠】
- **`#…#` 記法の綴りは SDK のどこにも無い。** `IPZL|thsep|#sign#|DataTagField|TagField` を
  SDKLib 961 ファイルへ掛けても `ShowDefineTagFieldDlg()` の 1 行だけ（`sdk-grep` 実測）。
  修飾子も条件式も VW 本体側にあるので**実機で総当たりするしかない**——「ヘッダに無いから無い」と
  読み違えない。
- **`#レコード#.#フィールド#` のレコードは PIO の universal 名、フィールドはパラメータ名**
  （`#StructuralMember#.#StartElevation#`。全件は [Parametric Objects](Parametric%20Objects.md)
  「構造材（`StructuralMember`）のパラメータ表」）。
- **`#IPZL#` はレコードのフィールドではない**（構造材のパラメータ 181 件に無い）——`#…#` が
  1 対の綴りは**別の名前空間**（関数）。

### 式の評価結果は機械で読み戻せる——目視は要らない

- **`IDataTagSupport::GetDataTagExtractedData(hTag, out, txtLabel = "")`** が「ラベル → 値」の対
  （`TXStringSTLPairArray`）で返す【ヘッダ根拠】。
- **タグが描いたテキスト**を `FirstMemberObj` / `NextObject` で走査し、`kTextNode` を
  `VWTextBlockObj::GetText` で読む。
- ワークシート式はタグを介さず `ISDK::CompileCriteriaExpression` ＋ `ExecWSExpression` でハンドルへ
  直接評価でき、**コンパイル誤りが enum で返る**——候補の総当たりは**まずこちら**で
  （[調査の作法](Investigation%20Techniques.md)「ワークシート式は…」）。

### `#…#` 記法の文法——**実測**（VW 2026 / mac）

[#187](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/187)・
[#190](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/190)・
[#196](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/196)・
[#198](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/198) で実機確認済み
（式ごとの表は [計測記録](../Metrics/Data%20Tags.md#-記法の文法実測vw-2026--mac)）。

**演算と括弧**

- **四則演算は効き、空白は効かない。** `/` の結果は図面の単位の書式で出る（`-1349 1/2`）——
  小数を式の側では決められない。
- **括弧が演算の括弧になるのは後ろに演算子が続くときだけ。** 一番外側の括弧は文字として出る
  （`(#…#*1)` → `(1234)`）。値だけ出すなら外側の括弧を書かない。

**文字列と連結**

- **文字列は二重引用符で囲み、連結は並置だけ**（`" (2FL "#IPZL#")"` → ` (2FL -2699)`）。
  **`+` も `&` も連結ではない**（`"a"+"b"` → `a+b`）。
- **引用符なしで括弧を書くと式全体が空になる。** 括弧付きの文字は必ず引用符で囲む。

**修飾子（数値の書式）**

- **修飾子を開くのは `#` 1 つ。** フィールドの閉じ `#` と続くので、**フィールドの直後なら
  `#フィールド##修飾子#`**（式の後ろなら `#修飾子#`——`##` に見えるのはフィールドの閉じ `#` と続くから）、以降は `#` を共有して連ねる（`##thsep#sign#`）。`#` を 1 つ欠くと
  修飾子の名前が文字で出る（`600sign`）。**知らない修飾子は黙って捨てられる。**
- **`#sign#` は正の値に `+` を付ける**（負の値で試しても何も変わらない——**修飾子は正の値で
  確かめる**）。
- **【訂正】`#thsep#` は桁区切りを出す——ただし単位・精度の修飾子の後ろでだけ効く**
  （`#IPZS##thsep#` → `1234`／**`#IPZS##mm_0_1#thsep#` → `1,234mm`**）。当初の「`#thsep#` に
  その働きが無い」は誤り。**教訓: 修飾子には「連ねたときだけ効くもの」がある**——1 つずつ試して
  「効かない」と結論しない。**正しい連ね方は「タグフィールドの定義」ダイアログが持っている**
  （`#StructuralMember#.#MajorBreadth##mm_0_1#usp#thsep#sign#` と綴られる）。
- **単位・精度の修飾子は `#<単位>_<小数桁数>_<単位記号を出すか>#`**（3 つ目は 0 か 1 以上の旗で
  省けば「出す」）。`mm_0_0` → `1234`／`mm_0_1` → `1234mm`／`mm_1_1` → `1234.0mm`／
  **`m_0_1` → `1m`（値が換算される）**。**`#mm#` のように `_` が無いと効かない。** `#usp#`（値と単位の
  間のスペース）も単独では効かない。**ダイアログが生成する連鎖は `##mm_0_1#usp#thsep#sign#`**
  （→ `+1,234 mm`）。
- **単位記号なし・桁区切りありは `##<図面の単位>_0_0#thsep#`**（#198）——旗 0 でも `#thsep#` は効く。
  7 桁（`1,234,567`）・負（`-1,234`）・連結の中（` (2FL 1,234)`）でも区切り、小数と併せれば整数部
  だけ区切る。`usp` は旗 0 では何も出さない（消し忘れても害は無い）。**並び順は結果を変えない。**
  レコードのフィールドでも同じ（[表](../Metrics/Data%20Tags.md#-記法の文法実測vw-2026--mac)）。
- **【落とし穴】旗 0 は単位記号を消すだけで換算は止めない。** mm の図面で `#m_0_0#` を書くと
  1234 が **`1`** になり、単位記号が無いので読み手は気付けない。**桁区切りだけが欲しいなら必ず
  図面の単位と同じ綴り**（mm の図面なら `mm_0_0`）。**精度 0 は四捨五入**（#196 の「切り捨て」は
  誤りで訂正済み）。
- **修飾子が効くのはフィールドの直後だけ。** 式の後ろ・括弧の後ろ・式全体の末尾では、修飾子として
  読まれる（知らない修飾子は消える）のに `#sign#` の働きが現れない。**`#フィールド##sign#` の後ろで
  演算してよく、符号は演算の結果に付く**（`##sign#+1000` → `+2234`）。**数値リテラルの直後の
  `#…#` は式を壊す**（`1234#sign#` → 空）。issue に挙がっていた `#IPZL#-872##sign#` は誤り。

**条件式**

- **`値@条件:代替` は効き、入れ子にもできる。** 比較は `<>` `>` `>=` `<` が効き、**条件の中に演算も
  綴り同士の比較も書ける**。
- **`#sign#` が使えない位置で `+` を足すなら `"+"@<式>>0:""<式>`**（式を 2 度書く。唯一の手）。
- **知らない `#…#` は空文字列になる**（エラーにならない）。

### ワークシート式モードは効く——ただし高さを返す関数は見つからない

- **`SetFormula(hText, 式, true)` はそのまま効き**、先頭に `=` を付けて保存される。レコード参照
  （`'StructuralMember'.'StartElevation'`）と演算を混ぜられる。
- **`#IPZL#` は `#…#` 記法だけの綴り**で、ワークシート式では使えない。
- `HEIGHT` / `LENGTH` / `TOPBOUND` / `BOTBOUND`・`CONCAT` / `ROUND` / `IF` / `ABS` は実在し、
  `LAYER` / `STORY` は**名前**を返す。**レイヤ・ストーリ・レベルの高さを数値で返す関数は、
  総当たり（37 本）では 1 つも見つからなかった**（[表](../Metrics/Data%20Tags.md#ワークシート式モードは効くただし高さを返す関数は見つからない)）。

## 式から読める高さ——**末尾 1 文字が基準を決める。どれも連動する**

[#187](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/187) で実機確認済み
（舞台は伏図レイヤの構造材を別の階のレベルへバウンドしたもの。
[舞台と表](../Metrics/Data%20Tags.md#式から読める高さ末尾-1-文字が基準を決めるどれも連動する)）。

### 読める / 読めないの一覧

- **`#IPZL#` ＝ 部材の絶対Z − そのレイヤの高さで、動かすと追随する。** **素のデザインレイヤでも
  成り立つ**（#194）——レイヤ面上の部材で `0` が返るのは正しく、`#IPZ#` を併せて読めば分かる。
  - 【訂正の記録】当初の「`SetElevation` で与えた高さを `#IPZL#` は拾っていない」は誤り。
    **教訓: 差が 0 のときは、引かれる側（絶対Z）も同じ走行で読む。**
- **`Dialog*Elevation` は「書いた値がそのまま残る保管箱」で高さに連動しない**（部材を動かしても
  バウンドを変えても、VW へ戻った後も古い値のまま。#245）。**計算済みの数値を書いてはいけない**
  ——黙って古い数字を出し続け、オブジェクトの欄に入っているぶん嘘だと気付きにくい。
- **`SetObjectStoryBound` のバウンドは `Dialog*Elevation` の数値へは流れないが、レベル名は流れる**
  （`#DialogStartElevationReference#` → `T187-FL [上階]`）。両方欲しければバウンドとパラメータの
  両方を書く。
- **推測した綴りは全部外れた**（`#LAYERELEVATION#` / `#STORYELEVATION#` / `#LAYERNAME#` / `#Z#`
  の 4 本＋ワークシート式 37 本）——ただし**「口は無い」と書いたのは行き過ぎ**
  （#187 再開で訂正）。「タグフィールドの定義」ダイアログ（`ShowDefineTagFieldDlg`）には
  `#IPZS#`・`#IPZL#`・`#ZTBBS#` / `#ZTBBL#` / `#ZTBBG#`（上面）・`#ZBBBS#` / `#ZBBBL#` /
  `#ZBBBG#`（底面）が並んでいる（それらの実測は下記）。**教訓: 正式な綴りは SDK ではなく
  ダイアログが持つ——推測で総当たりする前にそこを見る**（利用者に開いてもらえばその場で一覧が取れる）。

### 高さの綴りは「量 × 基準」——**末尾の 1 文字が基準を決める**

階とレイヤの高さを 40 ずらした舞台で実測
（[表](../Metrics/Data%20Tags.md#高さの綴りは量--基準末尾の-1-文字が基準を決める)）。

| 末尾 | 基準 | 挿入点 / 上面 / 底面 |
| --- | --- | --- |
| **`G`** | 基準平面＝**絶対Z** | `#IPZ#` / `#ZTBBG#` / `#ZBBBG#` |
| **`L`** | **レイヤ**（絶対Z − レイヤの絶対Z） | `#IPZL#` / `#ZTBBL#` / `#ZBBBL#` |
| **`S`** | **階の高さ**（絶対Z − 階の高さ） | `#IPZS#` / `#ZTBBS#` / `#ZBBBS#` |

- **`S` が引くのは階の高さで、レベルの絶対Z ではない**（階内相対Z は引かれない）。
- **どれも連動する**（動かすと同じだけ動く）。
- **`#ZTBB…#` / `#ZBBB…#` が `±1.7976931348623e308`（`DBL_MAX`）なら「図形が無い」**——巨大な数と
  読まない（[調査の作法](Investigation%20Techniques.md)）。構造材はパスとバウンドだけでは描かれない
  （3D パスの構造材は VW へ戻った後も同じで、**実体が無い**。#245）ので、実体を先に確かめる。
- **`#ST#` は部材が居る階**（バウンド先ではない）。`#ST#` / `#STLT#` / `#L#` / `#C#` は名前を返す。
- **数値に単位が付く綴りがある**（`#AREA#` → `0m2`、`#ROTATIONX#` → `0°`）。空が返った綴りの
  一覧は計測記録。

### 【訂正】連結と演算は素直には混ざらない——**括弧で括れば通るが、括弧が出力に出る**

- **`" (2FL "#IPZL#-872")"` は空になる**（当初は「連動する注記が作れる」と書いていた——連結と演算を
  別々に確かめて組み合わせを確かめなかった誤り）。
- **`(…)` で括れば通るが括弧が印字される**（` (2FL (-2531))`）。`(2FL -872)` の体裁はこの道では作れない（`(2FL (-872))` になる）。全体を括る・演算を先にする等は空
  （[12 通りの表](../Metrics/Data%20Tags.md#連結と演算を混ぜた式の実測括弧で括った場合を含む)）。
- **演算を避けられる綴りを選ぶのが本筋**——`#IPZS#` なら引き算が要らない（下記）。

### 連動する注記の作り方——**`" (2FL "#IPZS#")"`**（実測）

- **`" (2FL "#IPZS#")"` → ` (2FL -872)`、部材を +1000 で ` (2FL 128)`**（推奨する式そのものを
  走らせた。[表](../Metrics/Data%20Tags.md#連動する注記の作り方-2fl-ipzs実測)）。`#IPZS#` は階の高さを
  基準に済んでいるので、**引き算もレイヤごとの定数も要らず**、
  [連結と演算の問題](#訂正連結と演算は素直には混ざらない括弧で括れば通るが括弧が出力に出る)にも
  掛からない。
- **効く条件は「部材の載るレイヤが基準にしたい階に属していること」**（同じ階に属していれば伏図を
  何枚に分けても同じ基準）。
- **【落とし穴】階に属さないレイヤでは `#IPZS#` が黙って絶対Z を返す**（`#ST#` は空）。エラーにも
  空にもならない——**伏図のレイヤが階に属していることを取り込み側で確かめる**（`#ST#` をタグに
  出せば一目で分かる）。
- **天端は `#ZTBBS#`**（実体が要る。下記の傾斜材で実測済み）。
- **階の名前は式に文字列で埋め込む**（`#ST#` の名前が注記の体裁（`2FL`）と一致するとは限らない）。
- **【落とし穴】`AddObjectToContainer` で移した部材は移した先のレイヤ高さに追随しない**（#194）——
  `#IPZL#` / `#ZTBBL#` が狂う。**`gSDK->SetCurrentLayer` してから作る**（[Layers and
  Stories](Layers%20and%20Stories.md)「レイヤの高さ」）。`#IPZS#` は掛からない——推奨の式を使う理由が
  もう 1 つある。

### 傾斜材の両端の天端——**`#IPZS#` が始端、`#ZTBBS#` が高い端。連結だけで `(2FL -872~-40)` が出る**

[#196](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/196) で実機確認済み
（プラグインが作る形の構造材。[舞台と表](../Metrics/Data%20Tags.md#傾斜材の両端の天端ipzs-が始端ztbbs-が高い端連結だけで-2fl--872-40-が出る)）。

- **`#IPZS#` は始端の天端、`#ZTBBS#` は高い端の天端（階基準）。** `#ZTBBG#` は `GetObjectCube` の
  上面と一致し、**断面の角は天端より上に出ない**（勾配を変えても成り立つ）。
- 外接の底面は「低い端の天端 − せい ÷ cos(勾配)」（端が鉛直に切られている）。天端の読みには
  影響しない。
- **傾斜材と水平材の両方を 1 本でまかなう注記**（条件の中に綴り同士の比較を書ける）:

  ```
  " (2FL "#IPZS#"~"@#ZTBBS#<>#IPZS#:""#ZTBBS#@#ZTBBS#<>#IPZS#:""")"
  ```

  傾斜材 → ` (2FL -872~-40)`、水平材 → ` (2FL -872)`（`~` 以降が畳まれる）。
- **始端は必ず低い端にする。** 始端が高い端の材では**低い端が黙って消える**（` (2FL -40)`）——
  取り込み側でパスの向きを揃える（バウンド **ID 0 がパスの始点**。[Parametric Objects](Parametric%20Objects.md)）。
- **【訂正】`#StructuralMember#.#StartElevation#` / `#EndElevation#` は「常に 0」ではない**——高さの
  入った部材では**両端の天端の絶対Z**を返す（#187 の部材は 3D パスで高さが入っていなかった。
  [Parametric Objects](Parametric%20Objects.md)「構造材のパスは 2D で渡す」）。ただし絶対Z なので
  `(2FL …)` の注記には引き算が要り使えない。**注記に使うのは `#IPZS#` ＋ `#ZTBBS#` の組。**
- `#DialogStartElevation#` / `#DialogEndElevation#` は高さが入っても `0` のまま。
- この舞台は相対Z 0 なので `S` と `L` の違いはここでは測っていない（#187 の 40 ずらした舞台で確定済み）。

### `#sign#` は `#IPZS#` の直後でも効く——**ただし 0 では `±0` と出る**

[#196](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/196) で実機確認済み
（+128 / 0 / −872 の 3 本。[表](../Metrics/Data%20Tags.md#sign-は-ipzs-の直後でも効くただし-0-では-0-と出る)）。

- **`#sign#` はレコードのフィールドでない綴り（`#IPZS#`）の直後でも効く**（正で `+128`）。綴りの
  規則も同じ（`#` 1 つでは文字が出る）。
- **0 では `±0`**（`+0` でも `0` でもない。単位・精度の修飾子を挟んでも消えない）。**素の `0` が欲しければ条件式
  `"+"@#IPZS#>0:""#IPZS#`**——正・負では両者は 1 文字も違わないので、選び分ける理由はこの 1 点だけ。
- **注記に入れる形は 2 つ**（推奨する式そのものを走らせて実測）:

  ```
  符号なし: " (2FL "#IPZS#"~"@#ZTBBS#<>#IPZS#:""#ZTBBS#@#ZTBBS#<>#IPZS#:""")"
  符号あり: " (2FL "#IPZS##sign#"~"@#ZTBBS#<>#IPZS#:""#ZTBBS##sign#@#ZTBBS#<>#IPZS#:""")"
  ```

- **`#sign#` は各項に個別に付ける**（`#IPZS##sign#` と `#ZTBBS##sign#` の両方。式全体の末尾では効かない）。**単位の修飾子は入れない**
  （項ごとに `mm` が付く）。
