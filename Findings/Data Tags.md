# データタグ

データタグ（`Data Tag` PIO）を SDK から生成し、スタイルを使わずに per-instance で
中身（タグレイアウト）を組むときの実測。

- **スタイル無しでもタグは組める**が、間接段（スタイル）を挟む場合はシンボル定義の
  サブタイプ（`SetSymbolDefSubType`）とパラメータ対応表（`SetAllPluginStyleParameters`）が
  要り、そのどれかが漏れると実機で「タグは出るのに中身が空」になる。per-instance に直接
  組む方が壊れにくい。
- **タグレイアウトはタグ自身のプロファイルグループ**（`GetCustomObjectProfileGroup` /
  `SetCustomObjectProfileGroup`。VW2020 で足された `…InAux` の入り口もあるので両方見る）。
  中身は**式を持たせたテキスト**（`IDataTagTextLinkSupport::SetIsLinked` / `SetFormula`）で、
  **フィールドラベルはテキストの名前ではない**（手で作ったタグのテキストには名前が無い）。
  生成直後のタグが既定で持っているロクスは取り除き、手作りと同じ並びに揃える。
- **中身を入れてから渡す。** 空のグループを先に `SetCustomObjectProfileGroup` へ渡して
  後から足すと、VW が渡した時点でグループを複製していた場合に足したテキストが迷子になる
  （実機で「オブジェクトは出るのにタグレイアウトが空」として現れた）。渡した後は実際に
  持っているものを取り直し、複製されていればこちらのグループを消す。
- **組んだら `IDataTagSupport::UpdateUserDefinedTextsUIDs` をタグへ呼ぶ**（SDK のコメント
  どおり「データタグ**または**データタグスタイル」に使える）。これが無いとタグが式を拾わず、
  値が空のまま出る。
- **関連付けはレイアウトを組むより先。** タグの本文は関連付け先のレコードから来るので、
  相手を決めてから中身を組み、最後に `UpdateDataTag` で流し込む。
- **タグは指定した挿入点に留まらない。** しかも**タグの実寸はレイアウトの中身が決めるので、
  逃がす量も描くまで分からない**。したがって**置いた後に `GetObjectBounds` で実位置と実寸を
  測って動かす**のが最終位置を決める唯一確実な手。VW がどこへ落とすかはビューポートに
  よってもばらばらで、当てにできない。
- **「関連付け先からの相対で置く」は成り立たない（打ち切った調査）。** 「VW がタグを
  関連付け先へ吸着させるので、そこからの相対で置けば座標系を知らなくてよい」という方式を
  2 度試して外した（基準点の当て推量 → 実測からの較正）。較正の残差が大きく、どの基準点
  候補も当てはまらない＝**前提そのものが成り立っていない**。実際の挙動は「高さは合っていて
  横だけ一定量ずれ、タグ同士の間隔は対象の間隔に比例」（＝純粋な平行移動）で、上記の
  「置いた後に測って動かす」が正解だった。
- **注釈へ後から足した図形のクラスはビューポートで非表示のまま。** ビューポートの設定は
  タグを置く前に走っているので、置いた後に全クラスを表示へ戻して再更新する。
- **描画属性はクラス属性に従わせる場合、タグ本体だけでは足りない**（`SetObjectClass` ＋ 7 つの
  `Set*ByClass`。**`SetClassByName` / `SetAllAttributesByClass` という名前は SDK に無い**——一括で
  済ませる口も無い。[Attributes and Classes](Attributes%20and%20Classes.md)）。**タグレイアウトの中のテキストにも要る**——レイアウトの中身は
  本体のクラスを継がないので、本体だけに与えると文字が既定クラスのまま残る。文字スタイルを
  当てた**後**にクラスを与える（書体・大きさは文字スタイル、色・線の太さはクラスが受け持つ）。
- **図面ラベル（`Drawing Label2`）のレイアウトは、置き場も式の綴りも同じだが組み方が違う。**
  式は `#Drawing Label2#.#Title#` のように同じ `#レコード#.#フィールド#` だが、
  **`IDataTagTextLinkSupport` が効かない**（`IsSupported` が `false`）ので `SetFormula` で
  持たせられず、**既定のレイアウトのテキストを複製する**しかない
  （[Drawing Labels](Drawing%20Labels.md)）。

## タグフィールドの式——文法は 2 系統あり、綴りは SDK に 1 文字も書いていない

タグレイアウトのテキストが持つ式（`IDataTagTextLinkSupport::SetFormula` / `GetFormula`）に
ついて、**先に押さえること**。

- **文法は 2 系統ある。** `SetFormula` の第 3 引数が `isWorksheetFormula`（既定 `false`）で、
  読み戻しは `GetIsWorksheetFormula`。つまり同じ 1 本のテキストを、**独自の `#…#` 記法**と
  **ワークシート式**のどちらでも持たせられる。【ヘッダ根拠】
- **`#…#` 記法の綴りは SDK のどこにも無い。** `IPZL|thsep|#sign#|DataTagField|TagField` を
  SDKLib（ヘッダ＋同梱の VWFC 実装ソース、961 ファイル全部）へ掛けたときのヒットは
  **`ShowDefineTagFieldDlg()` の 1 行だけ**だった（`sdk-grep` 実測）。**数値の修飾子の一覧も
  条件式の形も VW 本体側**にあるので、**`sdk-grep` では 1 件も出ない**——ここは実機で
  総当たりするしかない。「ヘッダに無いから無い」と読み違えないこと。
- **`#レコード#.#フィールド#` のレコードは PIO の universal 名、フィールドはその
  パラメータ名。** 構造材なら `#StructuralMember#.#StartElevation#`。パラメータの全件は
  [Parametric Objects](Parametric%20Objects.md)「構造材（`StructuralMember`）のパラメータ表」
  にある（始端・終端の高さらしい欄は索引 28〜33 の
  `DialogStartElevationReference` / `DialogStartElevation` /
  `DialogEndElevationReference` / `DialogEndElevation` / `StartElevation` / `EndElevation`）。
- **`#IPZL#` はレコードのフィールドではない。** 構造材のパラメータ**181 件の表に `IPZL` は
  無い**。`#…#` が 1 対しか無い綴りは、レコード参照とは**別の名前空間**（関数）である。

### 式の評価結果は機械で読み戻せる——目視は要らない

式を入れて「何が出たか」を確かめるのに、結果ダイアログの絵は要らない。**文字列で読み戻す
口が 2 つある**ので、プローブのログだけで判定できる。

- **`IDataTagSupport::GetDataTagExtractedData(hTag, outArrExtractedData, txtLabel = "")`**
  ——タグが抽出した結果を「ラベル → 値」の対
  （`TXStringSTLPairArray` ＝ `std::vector<std::pair<TXString, TXString>>`）で返す。【ヘッダ根拠】
- **タグが描いたテキスト**——`FirstMemberObj` / `NextObject` でタグの生成物を走査し、
  型が `kTextNode` のものを `VWFC::VWObjects::VWTextBlockObj::GetText` で読む。
- ワークシート式のほうは、タグを介さずに**ハンドルへ直接**評価できる
  （`ISDK::CompileCriteriaExpression` ＋ `ISDK::ExecWSExpression`。
  [調査の作法](Investigation%20Techniques.md)「ワークシート式は…」）。**コンパイル誤りが
  enum で返る**ので、候補の識別子を総当たりするときは**まずこちらで引く**。

### `#…#` 記法の文法——**実測**（VW 2026 / mac）

[issue #187](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/187) で
**実機確認済み**（`probes/runtime/datatag-formula-grammar/`。値は実行ログそのまま。
この走行では `#IPZL#` が **−2699**、`#StructuralMember#.#MajorDepth#` が **600**）。

**四則演算は効く。括弧も演算の括弧として読まれる。**

| 入れた式 | 出た値 |
| --- | --- |
| `#IPZL#` | `-2699` |
| `#IPZL#+872` | `-1827` |
| `#IPZL# + 872`（空白付き） | `-1827`（**空白は効かない**＝同じ） |
| `#IPZL#-872` | `-3571` |
| `#IPZL#*2` | `-5398` |
| `#IPZL#/2` | **`-1349 1/2`**（**分数で出る**。下記） |
| `(#IPZL#+872)*2` | `-3654`（＝ `-1827 × 2`。**括弧が効いている**） |
| `872+40`（フィールドを含まない定数式） | `912` |

- **`/` の結果は図面の単位設定の書式で出る**（この走行では `-1349 1/2`）。
  **小数が欲しければ式の側では決められない**ので、割り算を式に入れるときは
  この見え方を前提にする。
- **括弧が「演算の括弧」になるのは、後ろに演算子が続くときだけ。**【実測】
  [issue #190](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/190)
  で `(#…#MajorDepth#*1)`（`MajorDepth` = 1234）を引いたら **`(1234)`** が出た——
  **一番外側の括弧が文字として出る**（中は評価される）。上の `(#IPZL#+872)*2` が
  `-3654` になったのは `*2` が続いていたから。**値だけを出したいなら外側の括弧を
  書かない。** 括弧付きの文字が欲しいなら引用符で囲む（下記「文字列」）。

**文字列は二重引用符で囲む。連結は「並置」だけで、`+` も `&` も連結ではない。**

| 入れた式 | 出た値 |
| --- | --- |
| `" (2FL "` | `` (2FL `` |
| `" (2FL "#IPZL#")"` | `` (2FL -2699)``（**並置で連結される**） |
| `(2FL )`（引用符なし・括弧を含む） | **空文字列**（式全体が値を出せなくなる） |
| `× #IPZL#`（引用符なし・演算子でない文字） | `× -2699`（**通る**） |
| `"a"+"b"` | **`a+b`**（`+` が文字として出る＝連結ではない） |
| `"a"&"b"` | **`a&b`**（同じ。`&` も連結ではない） |

- **引用符なしで括弧を書くと、その式は空になる。** issue の見立て（「本文のまま出る」）
  とは違い、**何も出ない**。括弧付きの文字を出したいなら**必ず引用符で囲む**。

**数値の書式（修飾子）は `#フィールド##修飾子#` と二重の `#` で始め、以降は `#` を
共有して連ねる。**【実測】（`MajorDepth` = 600 で引いた）
**この「二重」はフィールドの直後に置く場合の綴り**で、`#` が常に 2 つ要るという話ではない
（**修飾子を開くのは `#` 1 つ**。下記「修飾子が効くのは『フィールドの直後』だけ」）。

| 入れた式 | 出た値 | 読み |
| --- | --- | --- |
| `#…#MajorDepth#` | `600` | 基準 |
| `#…#MajorDepth##sign#` | **`+600`** | **`#sign#` は効く**（`#` が 2 つ要る） |
| `#…#MajorDepth#sign#` | **`600sign`** | `#` が 1 つだと**修飾子として読まれず文字が出る** |
| `#…#MajorDepth##thsep#sign#` | **`+600`** | **`#` を共有して 2 つ連ねられる**（issue に挙がっていた綴りはこれ） |
| `#…#MajorDepth##t187nosuch#` | `600` | **知らない修飾子は黙って捨てられる**（エラーにならない） |
| `#…#MajorDepth#t187nosuch#` | `600t187nosuch` | 同じく `#` が 1 つだと文字が出る |
| `#…#MajorDepth##thsep#` | `600` | 3 桁なので区切る桁が無い（下記） |
| `#…#MajorDepth#*10#thsep#` | `6000` | **コンマが入らない**（ただしこれは「式の後ろ」なので、そもそも修飾子が効かない位置。下記） |
| `#…#MajorDepth#/7` | `85.71` | 演算の結果は小数で出る（`#IPZL#/2` が `-1349 1/2` になったのは元の値の単位の書式） |

- **`#sign#` は正の値に `+` を付ける。** 1 巡目に「修飾子はどれも効かない」と読んだのは、
  試した値（−2699）が既に `-` を持っていたから——**負の値で `#sign#` を試しても何も
  変わらない**。修飾子を確かめるときは**正の値で引く**こと。
- **`#` を 1 つにすると修飾子ではなく文字になる。** `#IPZL#thsep#` は `…thsep` と出る。
  **フィールドの閉じ `#` と修飾子の開き `#` が続いて `##` になる**のが正しい綴り。
- **`#thsep#` は単独では 3 桁のコンマを出さない。**【実測】`MajorDepth` を **1234** にして
  （`SetParamReal` の読み戻しで 1234 を確かめた上で）引いたとき、`##thsep#` は `1234`、
  無印も `1234`、**知らない修飾子も `1234`** で、3 つが 1 文字も違わなかった。同じ値で
  `##sign#` は `+1234` を出すので、**修飾子が無視されているのではなく `#thsep#` が
  単独では働かない**のである（下記の訂正）。
- > **【訂正】`#thsep#` は桁区切りを出す——ただし「単位・精度の修飾子」を前に置いたときだけ。**
  > ここには当初 **「`#thsep#` にその働きが無い」「式の側から桁区切りを付ける手は
  > 見つかっていない」** と書いていた。**誤りである。**【実測】
  > [issue #196](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/196)
  > で `#IPZS#`＝**1234** / `MajorDepth`＝**1234** に対して引いた:
  >
  > | 入れた式 | 出た値 |
  > | --- | --- |
  > | `#IPZS##thsep#` | `1234`（**これまでの綴り。区切らない**） |
  > | **`#IPZS##mm_0_1#thsep#`** | **`1,234mm`**（**区切る**） |
  > | `#…#MajorDepth##thsep#` | `1234` |
  > | **`#…#MajorDepth##mm_0_1#thsep#`** | **`1,234mm`** |
  >
  > **`#thsep#` は単独では働かず、単位・精度の修飾子の後ろでだけ効く**（下記
  > 「単位・精度の修飾子」）。#187 / #190 が取り逃がしたのは、**修飾子を 1 つずつ
  > 単独で置いて試していた**からである。
  > **教訓: 修飾子は「連ねたときだけ効くもの」がある**——1 つずつ試して「効かない」と
  > 結論しない。**正しい連ね方は VW の「タグフィールドの定義」ダイアログが持っている**
  > （そこで単位・精度・3 桁位取り・符号を設定すると、定義欄に
  > `#StructuralMember#.#MajorBreadth##mm_0_1#usp#thsep#sign#` と綴られる）。

**単位・精度の修飾子——`#<単位>_<小数桁数>_<単位記号を出すか>#`**【実測】
（[issue #196](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/196)。
`#IPZS#`＝**1234**（mm）で引いた。値は実行ログそのまま）:

| 入れた式 | 出た値 | 読み |
| --- | --- | --- |
| `#IPZS##mm_0_0#` | **`1234`** | 3 つ目が `0` なら**単位記号を出さない** |
| `#IPZS##mm_0_1#` | `1234mm` | 3 つ目が `1` で出す |
| `#IPZS##mm_0_2#` / `#mm_0_3#` | `1234mm` | `1` 以上は同じ（旗） |
| `#IPZS##mm_1_1#` | **`1234.0mm`** | 2 つ目は**小数の桁数** |
| `#IPZS##mm_2_1#` | **`1234.00mm`** | 同 |
| `#IPZS##m_0_1#` | **`1m`** | 1 つ目は**単位**。**値が換算される** |
| `#IPZS##cm_0_1#` | **`123cm`** | 同（**四捨五入**。[#198](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/198) で確定） |
| `#IPZS##mm_0#` | `1234mm` | 3 つ目は省ける（既定は「出す」） |
| `#IPZS##mm#` | `1234` | **`_` が無いと効かない**（修飾子として読まれない） |
| `#IPZS##t196nosuch_0_1#` | `1234` | 知らない単位は黙って捨てられる |
| `#IPZS##usp#` | `1234` | **単独では効かない** |
| `#IPZS##mm_0_1#usp#` | **`1234 mm`** | `usp` ＝ **値と単位の間にスペース** |
| `#IPZS##mm_0_1#usp#thsep#sign#` | **`+1,234 mm`** | **ダイアログが生成する連鎖そのもの** |

- **単位の修飾子は値を換算する。** `#m_0_1#` は 1234mm を `1m` にした（図面の単位が mm の
  とき）。**桁区切りだけが欲しくて単位を変えるつもりが無いなら、図面の単位と同じ綴りを
  使う。**

**単位記号を出さずに桁区切りだけ出せる——`##<図面の単位>_0_0#thsep#`。**【実測】
（[issue #198](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/198)。
`probes/runtime/datatag-thsep-without-unit/`。図面の単位は **mm**。`#IPZS#` を
**1234** / **1234567** / **−1234** / **0** の 4 本の部材で振って引いた。値は実行ログそのまま）。
**旗（3 つ目の数）を 0 にしたまま `#thsep#` は効く**ので、上の表の `#mm_0_0#`（単位記号を
落とす）と `#mm_0_1#thsep#`（区切る）は**組み合わせられる**。

| 入れた式 | 1234 | 1234567 | −1234 | 0 |
| --- | --- | --- | --- | --- |
| `#IPZS#` | `1234` | `1234567` | `-1234` | `0` |
| `#IPZS##thsep#` | `1234` | `1234567` | `-1234` | `0` |
| `#IPZS##mm_0_0#` | `1234` | `1234567` | `-1234` | `0` |
| `#IPZS##mm_0_1#thsep#` | `1,234mm` | `1,234,567mm` | `-1,234mm` | `0mm` |
| **`#IPZS##mm_0_0#thsep#`** | **`1,234`** | **`1,234,567`** | **`-1,234`** | `0` |
| `#IPZS##mm_0_0#sign#` | `+1234` | `+1234567` | `-1234` | `±0` |
| **`#IPZS##mm_0_0#thsep#sign#`** | **`+1,234`** | **`+1,234,567`** | `-1,234` | `±0` |
| `#IPZS##mm_0_0#usp#` | `1234` | `1234567` | `-1234` | `0` |
| `#IPZS##mm_0_0#usp#thsep#sign#` | `+1,234` | `+1,234,567` | `-1,234` | `±0` |
| `#IPZS##mm_0_0#thsep#usp#sign#` | `+1,234` | `+1,234,567` | `-1,234` | `±0` |
| `#IPZS##mm_2_0#thsep#` | `1,234.00` | `1,234,567.00` | `-1,234.00` | `0.00` |
| `" (2FL "#IPZS##mm_0_0#thsep#")"` | `` (2FL 1,234)`` | `` (2FL 1,234,567)`` | `` (2FL -1,234)`` | `` (2FL 0)`` |

- **`#thsep#` が要求しているのは「単位・精度の修飾子が前にあること」だけで、単位記号が
  実際に出ることではない。** だから**単位記号なし・桁区切りありは
  `##<図面の単位>_0_0#thsep#` で出せる**（mm の図面なら `##mm_0_0#thsep#`）。
- **群が 2 つ以上でも区切る**（`1,234,567`）。**負でも区切る**（`-1,234`）。**小数と併せると
  整数部だけを区切る**（`#mm_2_0#thsep#` → `1,234.00`）。**連結の中でも効く**
  （` (2FL 1,234)`）——修飾子はフィールドの直後にあるので、下記「修飾子が効くのは
  『フィールドの直後』だけ」の制約にも掛からない。
- **`usp` は旗 0 のとき何も出さない。** `#mm_0_0#usp#` は `1234` で、**末尾に空白は
  残らない**（プローブは値を `'…'` で括ってログへ出しているので、残れば `'1234 '` と
  見える）。単位記号が出ないので置き場が無く、黙って消える——**`usp` を消し忘れても
  害は無い。**
- **修飾子の並び順は結果を変えない。** `#mm_0_0#thsep#usp#sign#` は、ダイアログが生成する
  順（`#mm_0_0#usp#thsep#sign#`）と**1 文字も違わなかった**。綴りを組むときに順序を
  気にしなくてよい。
- **0 で `#sign#` が `±0` を出すのは旗 0 でも同じ。** 素の `0` が欲しければ下記の条件式を
  使う（ここは桁区切りと関係が無い）。
- **答えは綴りの種類に依らない。** レコードのフィールド
  `#StructuralMember#.#MajorDepth#`（＝1234）でも `##mm_0_0#thsep#` → **`1,234`**、
  `##mm_0_0#usp#thsep#sign#` → **`+1,234`** だった。
- > **【落とし穴】旗 0 は単位記号を消すだけで、換算は止めない——図面の単位と違う綴りを
  > 書くと、黙って 1000 分の 1 の数が出る。**【実測】同じ部材（**1234mm** と
  > **1234567mm**）に単位だけ変えて当てた:
  >
  > | 入れた式 | 1234mm の材 | 1234567mm の材 |
  > | --- | --- | --- |
  > | `#IPZS##mm_0_0#` | `1234` | `1234567` |
  > | `#IPZS##m_0_1#` | `1m` | `1235m` |
  > | **`#IPZS##m_0_0#`** | **`1`** | **`1235`** |
  > | `#IPZS##m_3_0#` | **`1.234`** | **`1234.567`** |
  > | `#IPZS##m_3_1#` | `1.234m` | `1234.567m` |
  > | **`#IPZS##m_0_0#thsep#`** | **`1`** | **`1,235`** |
  > | `#IPZS##cm_0_0#` | `123` | `123457` |
  > | `#IPZS##cm_1_0#` | `123.4` | `123456.7` |
  > | **`#IPZS##mm_0_0#thsep#`** | **`1,234`** | **`1,234,567`** |
  >
  > - **`#m_0_0#` は「換算した値から単位記号だけ落とした数」である。** `#m_3_0#` が
  >   `1.234` / `1234.567` を出すので、**値が m へ換算されていること**は確定している
  >   （精度 0 がそれを丸めて `1` / `1235` にしている）。
  > - **単位記号が出ないので、読み手は換算に気付けない。** 旗 1 なら `1m` と出て単位が
  >   見えるが、旗 0 では `1`——**1234 のはずが `1` になっても、式を見るまで分からない。**
  >   表の最後の 2 行がそれで、**同じ `#…_0_0#thsep#` が `1,235` と `1,234,567` に
  >   化けている。**
  > - **だから「桁区切りだけが欲しい」ときは、必ず図面の単位と同じ綴りを書く。**
  >   `#thsep#` を効かせるために単位を借りてくるのではなく、**mm の図面なら `mm_0_0`。**
  > - **精度 0 は四捨五入**（切り捨てではない）。1234567mm を `#m_0_0#` で引くと
  >   1234.567 → **`1235`**、`#cm_0_0#` で引くと 123456.7 → **`123457`** と**繰り上がった**。
  >   上の表（#196）の `#cm_0_1#` → `123cm` に「切り捨て」と書いたのは**誤りで、訂正した**
  >   ——123.4 は丸めても切り捨てても `123` なので、あの 1 行だけでは区別が付かなかった。

**修飾子が効くのは「フィールドの直後」だけ。ただしその後ろで演算してよく、符号は
演算の結果に付く。**
[issue #190](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/190)
で**実機確認済み**（VW 2026 / mac。`probes/runtime/datatag-formula-modifier-placement/`。
`MajorDepth` = **1234**、`DialogStartElevation` = **−872** で引いた。値は実行ログそのまま）。

| 入れた式 | 出た値 | 読み |
| --- | --- | --- |
| `#…#MajorDepth#` | `1234` | 基準 |
| `#…#MajorDepth##sign#` | **`+1234`** | フィールドの直後＝**効く** |
| `#…#MajorDepth##sign#*1` | **`+1234`** | **直後に置けば、その後ろで演算してよい** |
| `#…#MajorDepth##sign#+1000` | **`+2234`** | **符号は演算の結果に付く**（1234 ＋ 1000 に `+`） |
| `#…#MajorDepth##sign#" mm"` | **`+1234 mm`** | 後ろに文字列を並べてもよい |
| `#…#MajorDepth#*1` | `1234` | 基準（演算だけ） |
| `#…#MajorDepth#*1#sign#` | `1234` | **式の後ろでは効かない**（`+` が付かない） |
| `#…#MajorDepth#*1#t190nosuch#` | `1234` | **知らない修飾子と 1 文字も違わない** |
| `#…#MajorDepth#*1##sign#` | **`1234sign`** | 式の後ろで `#` を 2 つにすると**文字が出る** |
| `#…#MajorDepth#*1##t190nosuch#` | `1234t190nosuch` | 同じ |
| `#…#MajorDepth#+1000#sign#` | `2234` | 加算でも同じ（効かない） |
| `#…#DialogStartElevation#*-1` | `872` | 基準（**負を演算で正に変えた**） |
| `#…#DialogStartElevation#*-1#sign#` | `872` | **効かない**（正の値なのに `+` が付かない） |
| `#…#DialogStartElevation#+2000#sign#` | `1128` | 同じ |
| `#IPZL#-872##sign#` | **`-872sign`** | **issue に挙がっていた綴りは誤り**（`sign` が文字で出る） |
| `(#…#MajorDepth#*1)#sign#` | `(1234)` | 括弧の後ろでも効かない |
| `" ("#…#MajorDepth#")"#sign#` | `` (1234)`` | **式全体の末尾**に置いても効かない |
| `1200+34#sign#` | `1234` | フィールドを含まない式でも効かない |
| `1234#sign#` | **空文字列** | **数値リテラルの直後に `#…#` を置くと式が壊れる** |

- **修飾子を開くのは `#` 1 つで、「フィールドの閉じ `#`」と続くから `##` に見える。**
  だから修飾子として読まれる綴りは、**フィールドの直後なら `##修飾子#`、式の後ろなら
  `#修飾子#`** である。綴りを間違えた側（フィールドの直後で `#` 1 つ／式の後ろで `#` 2 つ）は
  **修飾子の名前が文字として出る**。上の「二重の `#` で始める」は
  **フィールドの直後に置く場合の言い方**であって、`#` が 2 つ要るわけではない。
- **式の後ろで `#sign#` が効かないのは、綴りの間違いではない。** その位置でも
  **知らない修飾子（`#t190nosuch#`）は消える**ので、**修飾子としては読まれている**。
  読まれた上で **`#sign#` の働きだけが現れない**——出た値が無印・知らない修飾子と
  1 文字も違わない。
- **正の値に `+` を付けたいなら、修飾子をフィールドの直後へ寄せて演算を後ろへ回す。**
  `#…#MajorDepth##sign#+1000` が **`+2234`** を出す（＝符号は**演算後の値**に付く）ので、
  **`#フィールド##sign#` ＋ 演算**の順に書けば用は足りる。式の形がそれを許さないとき
  （先頭が定数・括弧で始まる・複数のフィールドを足すなど）は、下記の条件式を使う。

**条件式 `値@条件:代替` は効く。入れ子にもできる。**

| 入れた式 | 出た値 |
| --- | --- |
| `#IPZL#@#IPZL#<>0:"ゼロ"` | `-2699`（条件が真なので左の値） |
| `" ("@#IPZL#<>0:""#IPZL##thsep##sign#@#IPZL#<>0:""")"@#IPZL#<>0:""` | `` (-2699)`` |

**条件式で `+` を足せる——`#sign#` が式の後ろで効かないときの代わり。**
[issue #190](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/190)
で**実機確認済み**（同じ走行。`MajorDepth` = 1234、`DialogStartElevation` = −872）。

| 入れた式 | 出た値 |
| --- | --- |
| `"+"@#…#MajorDepth#>0:""` | `+`（条件が真なので左の値） |
| `"+"@#…#MajorDepth#>0:""#…#MajorDepth#` | **`+1234`** |
| `"+"@#…#DialogStartElevation#>0:""#…#DialogStartElevation#` | **`-872`**（負には付かない） |
| `"+"@#…#DialogStartElevation#+2000>0:""#…#DialogStartElevation#+2000` | **`+1128`**（**条件にも式が書ける**） |
| `"+"@(#…#DialogStartElevation#+2000)>0:""(#…#DialogStartElevation#+2000)` | `+(1128)`（括弧は文字で出る。上記） |
| `"+"@#…#MajorDepth#>=0:""` | `+`（`>=` も効く） |
| `"-"@#…#DialogStartElevation#<0:""` | `-`（`<` も効く） |

- **比較演算子は `>` `>=` `<` が効く**（`<>` は上記のとおり）。
- **条件の中に演算を書ける。** だから「**演算の結果**が正なら `+` を付ける」は
  `"+"@<式>>0:""<式>` と書ける。**式を 2 度書く**ことになるが、`#sign#` を式の後ろへ
  置けないぶん、これが唯一の手である。

**知らない `#…#` は空文字列になる**（エラーにはならない）。`#LAYERELEVATION#` /
`#STORYELEVATION#` / `#LAYERNAME#` / `#Z#` は**どれも空**だった。
**`#IPZL#` だけが「レコードのフィールドでない綴り」として実際に値を返した。**

### ワークシート式モードは効く——ただし高さを返す関数は見つからない

`SetFormula(hText, 式, /*isWorksheetFormula=*/true)` は**そのまま効く**。書いた式は
**先頭に `=` を付けられて**保存される（`GetFormula` の読み戻しが `=1+1` になる）。

| 入れた式（ws=1） | 出た値 |
| --- | --- |
| `1+1` | `2` |
| `=1+1`（自分で `=` を付けても同じ） | `2` |
| `'StructuralMember'.'StartElevation'` | `0` |
| `'StructuralMember'.'StartElevation'+872` | `872`（**レコード参照と演算が混ぜられる**） |
| `Z` / `IPZL` / `LAYERELEVATION` | **入れた綴りがそのまま**（＝そんな関数は無い） |

- **ワークシート式では `#IPZL#` は使えない。** `IPZL` は**データタグの `#…#` 記法だけの
  綴り**で、ワークシート式の関数ではない（裸の `IPZL` は文字列 `IPZL` に評価される）。
- **`ISDK::ExecWSExpression` で引いた結果も同じ**（[調査の作法](Investigation%20Techniques.md)
  「ワークシート式は…」）。タグを組まずに同じ問いを引けるので、候補の総当たりは
  そちらが速い。実在すると分かった関数と、外れた候補:

  | 引いたもの | 結果 |
  | --- | --- |
  | `HEIGHT` / `Height` / `HEIGHT()` / `LENGTH` / `Length` / `TOPBOUND` / `BOTBOUND` | **数値を返す（実在）** |
  | `LAYER` | **レイヤ名**を返す（`T187-TPL-PLAN-T187B`） |
  | `STORY` | **階名**を返す（`T187-PLAN`） |
  | `CONCAT('a','b')` → `ab` / `ROUND(872.4)` → `872` / `IF(1=1,'a','b')` → `a` / `ABS(-872)` → `872` | **実在** |
  | `'レコード'.'フィールド'` | 値を返す（`'StructuralMember'.'MemberID'` → `B14`） |
  | `Z` `ZHEIGHT` `ELEVATION` `TOPELEVATION` `BOTELEVATION` `BOTTOMELEVATION` `IPZL` `IPZ` `IPX` `IPY` `LAYERNAME` `LAYERELEVATION` `LAYERZ` `LAYERDELTAZ` `LAYERCUTPLANE` `STORYNAME` `STORYELEVATION` `LEVELNAME` `LEVELELEVATION` `TOPBOUNDOFFSET` `BOTBOUNDOFFSET` | **すべて自分自身の文字列＝存在しない** |
  | `Z()` / `NUMTOSTR(0,872)` | コンパイルが通らない（`InvalExpr`） |
  | `OBJECTDATA('StructuralMember','StartElevation')` | コンパイルは通るが**実行が `false`** |

- **したがって「レイヤの高さ」「ストーリの高さ」「レベルの高さ」を数値で返す関数は、
  ここまでの総当たりでは 1 つも見つかっていない。** 取れるのは**名前**（`LAYER` / `STORY`）
  までである。

## 式から読める高さ——**末尾 1 文字が基準を決める。どれも連動する**

[issue #187](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/187) で
**実機確認済み**（VW 2026 / mac。プローブ 2 本・計 8 回走らせた
——`probes/runtime/datatag-formula-grammar/` を 5 版、`probes/runtime/datatag-height-tokens/` を
3 版。以下の値は実行ログそのまま）。舞台は**現場の形**——伏図レイヤ（高さ **2699**）に
置いた構造材を、**別の階**のレベル `T187-FL`（絶対Z **3571**）へストーリバウンドで
繋いだもの。欲しい注記は `(2FL -872)` で、**−872 ＝ 2699 − 3571**。

### 読める / 読めないの一覧

| 引いたもの | 出た値 | 動かすと（+1000） |
| --- | --- | --- |
| **`#IPZL#`** | **−2699** | **−1699**（**追随する**） |
| `#StructuralMember#.#StartElevation#` / `#EndElevation#` | `0` | `0`（**この舞台では**常に 0。[訂正](#傾斜材の両端の天端ipzs-が始端ztbbs-が高い端連結だけで-2fl--872-40-が出る)） |
| `#StructuralMember#.#DialogStartElevation#`（バウンドだけ書いた本） | **`0`** | `0` |
| `#StructuralMember#.#DialogStartElevation#`（**パラメータへ書いた本**） | **−872** | **−872 のまま（追随しない）** |
| `#StructuralMember#.#DialogStartElevationReference#`（バウンドを書いた本） | **`T187-FL [上階]`** | 同じ（保たれる） |
| 同（パラメータへ書いた本） | **空** | 空 |
| `#LAYERELEVATION#` / `#STORYELEVATION#` / `#LAYERNAME#` / `#Z#` | **すべて空** | — |
| ワークシート式の高さ関数（候補 **37 本**） | **すべて自分自身の文字列＝存在しない** | — |

- **`#IPZL#` ＝ 部材の絶対Z − そのレイヤの高さ。** 挿入点の絶対Z が 0 でレイヤが 2699 なら
  **−2699**。+1000 動かすと **−1699** になる。**式から読める高さで、オブジェクトに
  連動するのはこれ 1 つだけ**である。
  - **素のデザインレイヤでも成り立つ。**
    [issue #194](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/194)
    で**実機確認済み**。`CreateLayer` で作った素のデザインレイヤに
    `VWFC::VWObjects::VWLayerObj::SetElevation(872)` を与え、そこで作った部材
    （ローカルZ 0）で引くと `#IPZL#` は **`0`** になるが、**これは正しい答えである**
    ——`#IPZ#`（絶対Z）を同じ走行で引くと **`872`** で、**レイヤの高さが部材の絶対Z も
    同じだけ持ち上げている**。差が 0 なのは「拾っていない」のではなく
    「**レイヤ面から測って 0**」だからで、部材を +300 持ち上げれば `#IPZ#`=`1172` /
    `#IPZL#`=**`300`** になる（実測）。**ストーリのレベルから作ったレイヤに限られない。**
    - > **【訂正の記録】** ここには当初「**`SetElevation` で与えた高さを `#IPZL#` は
      > 拾っていない**」と書いていた（[#190](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/190)
      > の走行で `#IPZL#` が `0` だったため）。**`#IPZL#` だけを見て `#IPZ#` を
      > 見なかったのが誤り**で、0 は正しい値だった。
      > **教訓: 差が 0 のときは、引かれる側（絶対Z）も同じ走行で読む。**
      > 「効いていない」と「差が無い」は、片方だけでは見分けられない。
- **`Dialog*Elevation` は「書いた値がそのまま残る保管箱」で、高さには連動しない。**
  `VWParametricObj::SetParamReal` で −872 を書けばタグは **−872 を描く**が、
  **部材を +1000 動かしても −872 のまま**、**バウンドの `fOffset` を −1872 へ書き換えて
  解決Zが 2699 → 1699 に変わっても −872 のまま**だった（実測）。
  - **だからここへ計算済みの数値を書くのは、やってはいけない。** 取り込み後に高さを
    変えると**黙って古い数字を出し続ける**。しかも値が「オブジェクトの欄」に入っている
    ので、**固定の文字列より嘘だと気付きにくい**。
- **`SetObjectStoryBound` で書いたバウンドは、レコードの `Dialog*Elevation` へは流れない**
  （`fOffset=−872` なのに式は `0`）。逆に**レベル名は流れる**
  （`#DialogStartElevationReference#` → `T187-FL [上階]`。**どの階のレベルかまで出る**）。
  **名前と数値で出どころが逆**なので、両方欲しければ**バウンドとパラメータの両方を書く**
  （実測。部材 H で名前 `T187-FL [上階]` と数値 −872 が同時に出た）。
- > **訂正（[#187](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/187) 再開）。**
  > ここには当初 **「レイヤ高さ・ストーリ高さ・レベル高さを数値で返す口は、式にも
  > ワークシート式にも無い」** と書いていた。**行き過ぎだった。** 測ったのは
  > **こちらが推測した綴り**（`#…#` 記法 4 本＋ワークシート式 37 本）だけで、
  > **正式な一覧を持っていなかった**。VW の「タグフィールドの定義」ダイアログ
  > （`IDataTagSupport::ShowDefineTagFieldDlg` が開くもの）には、**ストーリ基準・
  > レイヤ基準・基準平面基準の高さがはっきり並んでいる**:
  >
  > | 見えている名前 | 綴り |
  > | --- | --- |
  > | 挿入点の高さ (Z)_**ストーリの高さ** | **`#IPZS#`** |
  > | 挿入点の高さ (Z)_レイヤの高さ | `#IPZL#` |
  > | バウンディングボックス**上面**の高さ (Z)_ストーリ / レイヤ / 基準平面 | **`#ZTBBS#` / `#ZTBBL#` / `#ZTBBG#`** |
  > | バウンディングボックス底面の高さ (Z)_ストーリ / レイヤ / 基準平面 | **`#ZBBBS#` / `#ZBBBL#` / `#ZBBBG#`** |
  >
  > **`#IPZS#` と `#ZTBBS#` は一度も試していない**（`#ZTBB…#` は「上面の高さ」＝
  > まさに欲しかった**天端の高さ**）。何を返すかは #187 で測り直し中。**それまで
  > この節の「読める / 読めない」は、推測した綴りについてのみ読むこと。**
- **推測した綴りは全部外れた**——`#…#` 記法で `#LAYERELEVATION#` / `#STORYELEVATION#` /
  `#LAYERNAME#` / `#Z#` の 4 本、ワークシート式で 37 本。ワークシート式で取れるのは
  **名前**（`LAYER` / `STORY`）だけだった（上記「ワークシート式モードは効く」）。
  **教訓: `#…#` 記法の正式な綴りは VW のダイアログが持っている**——SDK のヘッダにも
  同梱の実装ソースにも 1 件も無いので、**推測で総当たりする前にそこを見る**
  （`ShowDefineTagFieldDlg`。利用者に開いてもらえばその場で一覧が取れる）。

### 高さの綴りは「量 × 基準」——**末尾の 1 文字が基準を決める**

**実機確認済み**（VW 2026 / mac。`probes/runtime/datatag-height-tokens/`。
**階とレイヤの高さをわざと 40 ずらした舞台**で測った——階 `T187-PLAN` の高さ **2699**、
その中のレベルの階内相対Z **−40** ＝ **レイヤの絶対Z 2659**。この 40 が無いと
`#IPZS#` と `#IPZL#` が同じ値を返して見分けられない）。

| 末尾 | 基準 | 実測（押し出し。絶対Zで上面 **700** / 底面 **100**） |
| --- | --- | --- |
| **`G`** | **基準平面＝絶対Z そのもの** | `#ZTBBG#` → **`700`** / `#ZBBBG#` → **`100`** |
| **`L`** | **レイヤ**（絶対Z − レイヤの絶対Z 2659） | `#ZTBBL#` → **`-1959`** / `#ZBBBL#` → **`-2559`** |
| **`S`** | **ストーリ**（絶対Z − **階の高さ** 2699） | `#ZTBBS#` → **`-1999`** / `#ZBBBS#` → **`-2599`** |

同じ規則が挿入点の側にもそのまま効く（部材の絶対Z **0**、同じレイヤ）:

| 綴り | 意味 | 出た値 | +1000 動かすと |
| --- | --- | --- | --- |
| `#IPZ#` | 挿入点 Z（**絶対Z**） | `0` | **`1000`** |
| **`#IPZS#`** | 挿入点の高さ (Z)_**ストーリの高さ** | **`-2699`**（＝0 − 2699） | **`-1699`** |
| `#IPZL#` | 挿入点の高さ (Z)_レイヤの高さ | `-2659`（＝0 − 2659） | `-1659` |

- **`S` が引くのは「階の高さ」であって、レベルの絶対Zではない。** レベルの階内相対Z
  （この舞台では −40）は**引かれていない**。`#IPZS#` は `2699` を引いており、
  レベルの絶対Z `2659` ではなかった。
- **どれも生きている。** 部材を動かすと 3 つとも同じだけ動く（差は一定）。
- **`#ZTBB…#` / `#ZBBB…#` が `±1.7976931348623e308` なら「図形が無い」。**
  `DBL_MAX` で、**何も描いていない PIO の反転した空矩形**である
  （[調査の作法](Investigation%20Techniques.md)）。**巨大な数として読まない。**
  構造材はパスとバウンドだけでは描かれないので、この綴りを使うなら**実体がある**ことを
  先に確かめる。
- **`#ST#` は「部材が居る階」を返す。** 他階のレベルへバウンドしていても、返るのは
  自分のレイヤが属する階の名前（`T187-PLAN`）である。バウンド先は返らない。
- **`#ST#` / `#STLT#` / `#L#` / `#C#` は名前を返す**（`T187-PLAN` / `T187-PLAN-L` /
  `T187-TPL-PLAN-T187B` / `一般`）。
- **数値に単位が付く綴りがある**（`#AREA#` → `0m2`、`#ROTATIONX#` → `0°`）。
- 空が返った綴り（読み取り違いか、値が無い）: `#BX#` `#BY#` `#BZ#` `#LD#` `#CD#` `#N#`
  `#SUBFAREA#` `#MATERIAL#` `#OSTYLE#` `#SYMBOL#`。対照の `#T187NOSUCHTOKEN#` も空。

### 【訂正】連結と演算は素直には混ざらない——**括弧で括れば通るが、括弧が出力に出る**

> ここには当初 **`" (2FL "#IPZL#-872")"` で連動する注記が作れる**と書いていた。
> **実機で引いたら空文字列だった。** 連結と演算を**別々に**確かめて、**組み合わせを
> 確かめずに推奨へ書いた**のが誤りである。

実測（12 通り引いた）:

| 入れた式 | 出た値 |
| --- | --- |
| `#IPZL#` | `-1659` |
| `#IPZL#-872` | `-2531`（**演算だけなら通る**） |
| `" (2FL "#IPZL#")"` | `` (2FL -1659)``（**連結だけなら通る**） |
| **`" (2FL "#IPZL#-872")"`** | **空**（混ぜると壊れる） |
| **`" (2FL "(#IPZL#-872)")"`** | **`` (2FL (-2531))``**（**括弧で括れば通る。ただし括弧が出る**） |
| `(" (2FL "#IPZL#-872")")` | 空（全体を括ってもだめ） |
| `#IPZL#-872" (2FL)"` | 空（演算を先にしてもだめ） |
| `"("#IPZL#-872")"` | 空 |
| `" (2FL "#IPZL#"-872)"` | `` (2FL -1659-872)``（**`-872` が文字として出る**） |

- **演算の結果を文字列と連結したいなら `(…)` で括る**。**括弧はそのまま印字される**ので、
  `(2FL -872)` のような体裁は**この道では作れない**（`(2FL (-872))` になる）。
- **だから演算を避けられる綴りを選ぶのが本筋**である——`#IPZS#` は**階の高さを基準に
  済んでいる**ので、**引き算そのものが要らない**（下記）。

### 連動する注記の作り方——**`" (2FL "#IPZS#")"`**（実測）

**実機確認済み**（VW 2026 / mac。**推奨する式そのものを走らせた**実行ログ。
階 `T187-2F` の高さ **3571**、その階のレイヤに**絶対Z 2699** で置いた構造材）。

| 入れた式 | 出た値 | +1000 動かすと |
| --- | --- | --- |
| `#IPZ#` | `2699`（絶対Z） | `3699` |
| **`#IPZS#`** | **`-872`**（＝2699 − 3571） | **`128`**（＝3699 − 3571） |
| `#ST#` | `T187-2F` | 同じ |
| **`" (2FL "#IPZS#")"`** | **`` (2FL -872)``** | **`` (2FL 128)``** |

**これが答えである。** `#IPZS#` は**階の高さを基準に済んでいる**ので、
**引き算も、レイヤごとの定数も要らない**——だから
[上記の「連結と演算は混ざらない」](#訂正連結と演算は素直には混ざらない括弧で括れば通るが括弧が出力に出る)
にも引っ掛からず、`(2FL -872)` の体裁がそのまま出る。**部材の高さを変えれば注記も動く。**

- **効く条件は「部材の載るレイヤが、基準にしたい階に属していること」。** 伏図を
  横架材の高さごとに何枚に分けても、**それらが同じ階に属していれば全部同じ基準**に
  なる。レイヤごとに式を変える必要は無い。
- > **落とし穴: 階に属さないレイヤでは、`#IPZS#` は黙って絶対Z を返す。**【実測】
  > 同じ部材を**階に属さないデザインレイヤ**（`GetStoryOfLayer` が `nil`）へ置くと、
  > `#IPZS#` は **`2699`**（＝絶対Z そのもの）を返し、動かすと `3699` になった。
  > `#ST#` は**空**。**エラーにも空にもならず、「引くものが無いので引かない」**
  > という振る舞いなので、**注記は黙って違う数を出し続ける**。
  > **伏図のレイヤが階に属していることを、取り込みの側で確かめること**
  > （`#ST#` が空でないかをタグに出してみれば、実機でも一目で分かる）。
- **天端が欲しいなら `#ZTBBS#`**（バウンディングボックス上面の高さ_ストーリ基準）。
  ただし**実体が描かれている**ことが前提で、この調査で作った構造材は
  （パスとバウンドだけでは）描かれず `±1.79e308` のままだった。**実体のある部材で
  改めて確かめること。**
- **階の名前は式に文字列で埋め込む。** `#ST#` は階の名前を返すが、取り込みが付けた
  名前（`T187-2F` など）が注記の体裁（`2FL`）と一致するとは限らない。
- > **落とし穴: `AddObjectToContainer` で別のレイヤへ移した部材は、移した先のレイヤの
  > 高さに追随しない。**【実測】[#194](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/194)。
  > 高さ 900 のレイヤで作った部材を高さ 1100 のレイヤへ移すと、**絶対Z は 900 のまま**で
  > `#IPZL#` は **`-200`**。その後そのレイヤを 1300 にしても絶対Z は 900 のままで
  > `#IPZL#` は **`-400`** になった。**部材が「そのレイヤの面の上」に居る前提が崩れる**
  > ので、`#IPZL#` も `#ZTBBL#` も意図した値を返さない。
  > **レイヤ面を基準にしたいなら、`gSDK->SetCurrentLayer` でそのレイヤをアクティブに
  > してから作ること**（詳細は [Layers and Stories](Layers%20and%20Stories.md)
  > 「レイヤの高さ」）。`#IPZS#` は階の高さを引くだけなので、この落とし穴には
  > 掛からない——**推奨の `" (2FL "#IPZS#")"` を使う理由がもう 1 つある。**

### 傾斜材の両端の天端——**`#IPZS#` が始端、`#ZTBBS#` が高い端。連結だけで `(2FL -872~-40)` が出る**

**実機確認済み**（VW 2026 / mac。[issue #196](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/196)。
`probes/runtime/datatag-slope-top-elevation/` を **3 版・計 3 回**走らせた。舞台は**プラグインが実際に
作る形**——パスは平面（Z=0）の 2 点、高さは始端・終端とも `SetObjectStoryBound` だけ、
断面は **105 × 240** の**天端中央基準**（`AxisAlign`=`1`）、端は直切り
（`StartCondition` / `EndCondition`=`3`）、材はストーリのレベルから作ったレイヤ。
階 `T196-2F` の高さ **3571**、レベルの階内相対Z **0**。以下の値は実行ログそのまま）。

部材 S（**始端が低い端**。バウンド offset −872 → −40 ＝ 解決Z **2699 → 3531**）:

| 綴り | 出た値 | 何を指しているか |
| --- | --- | --- |
| `#IPZ#` | `2699` | **始端**の天端の絶対Z |
| **`#IPZS#`** | **`-872`** | **始端**の天端（階基準）＝この材では**低い端** |
| **`#ZTBBS#`** | **`-40`** | **高い端**の天端（階基準） |
| `#ZTBBG#` | `3531` | 同・絶対Z。**`GetObjectCube` の上面と一致** |
| `#ZBBBG#` | `2453.86` | 外接の底面（絶対Z）。低い端の天端 − **245.14** |
| `#ZBBBS#` | `-1117.14` | 同・階基準 |

- **`#ZTBBS#` は高い端の天端そのもの——断面の角が天端より上に出ることはない。**
  バウンドの解決Z（**3531**）・`GetObjectCube` の上面（**3531**）・`#ZTBBG#`（**3531**）の
  3 つが一致した。**勾配を変えても成り立つ**——両端 −1000 で `#ZTBBS#`=**−1040**、
  片端だけ +128 へ変えて `#ZTBBS#`=**`128`**（どちらもそのときの高い端の天端）。
- **底面だけは「せい」ぶんでは下がらない。** 外接の底面は
  **低い端の天端 − せい ÷ cos(勾配)** だった（＝**端が鉛直に切られている**ことの現れ。
  断面そのものは材軸に直角）:

  | 水平距離 | 高低差 | cos | せい ÷ cos | 低い端の天端 | 外接の底面（実測） |
  | --- | --- | --- | --- | --- | --- |
  | 4000 | 832 | 0.97905 | **245.1367** | 2699 | **2453.8633** |
  | 4000 | 2000 | 0.89443 | **268.3282** | 1699 | **1430.6718** |

  水平材では cos = 1 なので素直に せい ぶん下がる（2699 → **2459**、実測）。
  **天端を読むぶんにはこの差は出ない**（上面は必ずパスの高い端に一致する）ので、
  注記には影響しない。

**欲しい注記はこれで出る。** 連結だけで**演算を混ぜない**ので、
[上記の「連結と演算は混ざらない」](#訂正連結と演算は素直には混ざらない括弧で括れば通るが括弧が出力に出る)
（括弧が印字される）にも掛からない:

| 入れた式 | 傾斜材 S | 水平材 N |
| --- | --- | --- |
| `" (2FL "#IPZS#"~"#ZTBBS#")"` | `` (2FL -872~-40)`` | `` (2FL -872~-872)``（**同じ値が 2 度出る**） |
| **下の 1 本**（条件で畳む） | **`` (2FL -872~-40)``** | **`` (2FL -872)``**（**畳まれる**） |

```
" (2FL "#IPZS#"~"@#ZTBBS#<>#IPZS#:""#ZTBBS#@#ZTBBS#<>#IPZS#:""")"
```

- **条件の中に綴り同士の比較を書ける。** `"~"@#ZTBBS#<>#IPZS#:""` は傾斜材で `~`、
  水平材で**空**を返した（それまで条件に書いたのは定数との比較だけだった。上記「条件式」）。
  だから**水平材と傾斜材で式を分ける必要は無い**——**上の 1 本で両方まかなえる。**
- **始端は必ず低い端にする。** 始端が高い端の材（offset −40 → −872）では `#IPZS#` が
  **`-40`**（高い端）になり `#ZTBBS#` も `-40` なので、**注記は `` (2FL -40)`` になって
  低い端が消える**。エラーにも空にもならないので、**取り込みの側でパスの向きを揃える**
  しかない（バウンド **ID 0 がパスの始点**。[Parametric Objects](Parametric%20Objects.md)）。
- > **【訂正】`#StructuralMember#.#StartElevation#` / `#EndElevation#` は「常に 0」ではない。**
  > 上記「読める / 読めない」に `0`（常に 0）と書いたのは、**測った部材に高さが無かった
  > から**である（[#187](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/187)
  > の走行は 3D のパスで作っており、実体も高さも入っていなかった。
  > [Parametric Objects](Parametric%20Objects.md)「構造材のパスは 2D で渡す」）。
  > 高さの入った部材では**両端の天端の絶対Z**を返した——S で `2699` / `3531`、
  > 始端が高い材で `3531` / `2699`、offset を動かすと追随する。
  > **「もう一方の端」を読む口はこれである。** ただし返るのは**絶対Z**で階基準ではない
  > ので、`(2FL …)` の体裁にするには引き算が要り、**連結と混ざらない**。
  > **注記に使えるのは `#IPZS#` ＋ `#ZTBBS#` の組**である。
- `#DialogStartElevation#` / `#DialogEndElevation#` は**高さが入っても `0` のまま**だった
  （バウンドはレコードへ流れない。上記）。
- この舞台は**レベルの階内相対Zが 0** なので、`#ZTBBS#` と `#ZTBBL#`（`#IPZS#` と
  `#IPZL#` も）が同じ値を返している。**`S` と `L` の違いはここでは測っていない**
  ——その区別は [#187](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/187)
  の 40 ずらした舞台で確定済み（上記「高さの綴りは『量 × 基準』」）。

### `#sign#` は `#IPZS#` の直後でも効く——**ただし 0 では `±0` と出る**

**実機確認済み**（VW 2026 / mac。[issue #196](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/196)。
同じ走行。水平材を 3 本、バウンドの offset で **+128 / 0 / −872** に置いて同じ綴りを
引いた。**正の値で引く**——負の値では `#sign#` の効き目が見えない）。

| 入れた式 | 正（+128） | 0 | 負（−872） |
| --- | --- | --- | --- |
| `#IPZS#` | `128` | `0` | `-872` |
| **`#IPZS##sign#`** | **`+128`** | **`±0`** | `-872` |
| `#IPZS#sign#`（`#` 1 つ） | `128sign` | `0sign` | `-872sign` |
| `#IPZS##t196nosuch#`（知らない修飾子） | `128` | `0` | `-872` |
| **`" (2FL "#IPZS##sign#")"`** | **`` (2FL +128)``** | `` (2FL ±0)`` | `` (2FL -872)`` |
| `"+"@#IPZS#>0:""#IPZS#`（条件式） | **`+128`** | **`0`** | `-872` |
| `" (2FL ""+"@#IPZS#>0:""#IPZS#")"` | **`` (2FL +128)``** | **`` (2FL 0)``** | `` (2FL -872)`` |

- **`#sign#` が効くのは「レコードのフィールドの直後」だけではない。** `#IPZS#` のような
  **レコードのフィールドでない綴り**の直後でも同じように効く（[#190](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/190)
  で測ったのはレコードのフィールドだけだった）。綴りの規則も同じで、**`#` 1 つでは
  修飾子として読まれず文字が出る**（`128sign`）。知らない修飾子は黙って消える。
- **0 のときは `+0` でも `0` でもなく `±0`。** 注記に `±0` を出したくないなら
  **条件式のほうを使う**（`"+"@#IPZS#>0:""#IPZS#` は 0 で素の `0` を出す）。
  **正・負では両者は 1 文字も違わない**ので、**選び分ける実質的な理由はこの 1 点だけ**である。
- **`±0` は単位・精度の修飾子を挟んでも消えない。**【実測】`#IPZS##mm_0_1#sign#` は 0 で
  **`±0mm`**、`#IPZS##mm_0_1#usp#thsep#sign#` は **`±0 mm`** だった（上記「単位・精度の
  修飾子」）。**`#sign#` を使うかぎり 0 は `±0` になる**ので、**0 を素の `0` で出したい
  注記では条件式のほうを使う**。

**したがって注記に入れる形は 2 つ。**【実測】（傾斜材 S は −872 → −40、水平材 P は +128、
水平材 N は −872。どれも**推奨する式そのものを走らせた**実行ログ）:

| 入れた式 | 傾斜材 S | 水平材 P（正） | 水平材 N（負） |
| --- | --- | --- | --- |
| **符号なし**（下） | `` (2FL -872~-40)`` | `` (2FL 128)`` | `` (2FL -872)`` |
| **符号あり**（下） | `` (2FL -872~-40)`` | **`` (2FL +128)``** | `` (2FL -872)`` |

```
符号なし: " (2FL "#IPZS#"~"@#ZTBBS#<>#IPZS#:""#ZTBBS#@#ZTBBS#<>#IPZS#:""")"
符号あり: " (2FL "#IPZS##sign#"~"@#ZTBBS#<>#IPZS#:""#ZTBBS##sign#@#ZTBBS#<>#IPZS#:""")"
```

- **`#sign#` は各項に個別に付ける**（`#IPZS##sign#` と `#ZTBBS##sign#` の両方）。
  式全体の末尾に置いても効かない（上記「修飾子が効くのは『フィールドの直後』だけ」）。
- **単位の修飾子は入れない。** 入れると `` (2FL -872mm~-40mm)`` のように**項ごとに
  `mm` が付く**（実測）。
