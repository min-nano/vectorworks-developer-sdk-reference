# グラフィック凡例

`GraphicLegend` PIO を SDK から生成・制御するときの実測。**公開 API がほとんど無く**、
実機のダンプで内部構造を割って初めて制御できた部分が多い。タグ付きデータの一般的な
読み書きの癖は [Tagged Data](Tagged%20Data.md) にある。

## 基本の作法

- **点で生成すると幅 0 に潰れる**（矩形モードの PIO）。`BoxWidth` を与える。
- 見た目（枠線・セル）は**クラスでは制御できない**ので属性として直接与える。
- スタイルを当てない場合は `SetPluginObjectStyle` も `UpdateStyledObjects` も呼ばない
  （中身は置いた時点の `ResetObject` で決まる）。
- **スタイルを当てる場合、スタイルの無い文書では凡例が空の箱**になる（名前が 1 文字
  違うだけで同じことが起きる）。処理の結果が図面の外の資源に左右される。

## ソース定義（何を並べるか）は公開 API では設定できない

- **ソース定義は PIO のパラメータでは設定できない。** ソース定義はボタンのフィールド
  （type=14）で、選んだソースを保持する欄がパラメトリックレコードに無い。ISDK にも
  ソースへ触る呼び出しは無い。**そして既定のソースは空**なので、**スタイル無しで置いた
  凡例は中身が 0 セット＝何も出ない**（実機で確認。「既定のソースが集めたものがフィルタで
  絞られる」と読んでいたのは誤り）。
- **「ビューポートでフィルタ」を設定する API も SDK に無い**（VW 2026 SDK のヘッダを
  `Legend` で全文検索して確認）。凡例について公開されているのは
  `ovGraphicLegend*`（1645〜1650。**PIO のリセット中しか有効でない**画像再生成用の
  オブジェクト変数）と、条件ダイアログの文脈 `eGraphicLegendCriteria` だけで、
  ソース定義やフィルタに触る呼び出しは `ISDK` にも VWFC にも無い（`Filter…Viewport` /
  `LegendSource` / `LegendCriteria` / `Get|SetGraphicLegend…` のどれも 0 件）。
  VWFC の `VWObject.cpp` が使う `IGraphicLegendCoreSupport` /
  `IGraphicLegendCoreOperationsSupport` は**ヘッダが SDK に同梱されていない**内部
  インターフェースなので、こちらからは呼べない。

## パラメトリックレコードに載っているもの・いないもの

- **per-instance の設定はレコードにちゃんと載っている**（実機の全欄ダンプで、スタイルの
  違う凡例ごとに違う値が入っていた）。書き換えられる見込みのある欄:
  `SummarizeBy`（`StyleSymName` / `ClassName`）・`SortBy`（`StyleSymName` /
  `DesignLayerName`）・`SortOrder`・`HideEmptyCells`・`FixedCellWidth` / `FixedCellHeight`・
  `LayoutBy`・`TitleWidth`・`ScaleFactor`（記号の倍率）・`BoxWidth`。
  値を持たない type=14＝ボタンは `DefineSource` / `DefineImage` / `EditCellLayout` /
  `EditTitleLayout` / `ImageClasses` の 5 つで、**この 5 つのボタンの先にある設定だけが
  レコードの外**にある。レコードの版は `__version` ＝ 3100。
- **フィルタはレコードに載っていない**（実機のダンプで確認）。UI で「ビューポートで
  フィルタ」を掛けた前後で、36 フィールド中**変わるのは `BoxWidth` だけ**で、それも
  「並ぶセルが減って凡例が細くなった」結果にすぎない（153.99 → 48.80）。
- **関連（association）でもない。** フィルタを掛けた凡例で `associations=0`。
- **凡例の中の図形が UUID で持っているのでもない。** 凡例の中身はセルごとに
  グループ（`type=11`）＋ `GraphicLegendFrame`（＋画像）で、**UUID を値に持つレコード欄は
  1 つも無い**。

## 「ビューポートでフィルタ」の保存先はタグ付きデータ `'GrLg'`

凡例にぶら下がるデータオブジェクト（補助オブジェクトの連鎖）のタグ付きデータだった。
オブジェクト変数の総当たりで **703（`ovFirstAuxObject`）だけが違った**ことから割れた。
生バイトの読み方・`'DMDT'` が「入れ物の入れ物」である点は [Tagged Data](Tagged%20Data.md)。

- **書き方**: `TaggedDataCreate(legend, 'GrLg', 15, 5, N)` ＋
  `TaggedDataSet(legend, 'GrLg', 15, 5, i, &GetObjectInternalIndex(viewport))` を
  i = 0..N-1 で回し、**`ResetObject` より前**に呼ぶ。型 15 は
  `kTaggedDataObjectRefArrayTypeID`、タグは 5、値は**フィルタ先ビューポートの
  `InternalIndex`**。`'GrLg'` は多文字リテラルを避けて `0x47724C67` と書く。
- **フィルタ先は 1 つとは限らない**（UI はチェックボックスの一覧で複数選べる）。**同じ
  容れ物・同じ型・同じタグの配列の要素数が増えるだけ**で、別のタグへ移ったりはしない。
  3 つ選んだ凡例の `'GrLg'` は型 15・要素数 3・要素は 3 つのビューポートの
  `InternalIndex` だった。**要素数を決めるのは `TaggedDataCreate` の最後の引数**。

## ソース定義の保存先は `'GrLe'`（条件はトークン列）

**ソース定義とイメージの定義の保存先は `'GrLe'`**（`'GrLg'` と 1 文字違い。Graphic Legend の
別の容れ物）。**手で「凡例ソースの定義...」を設定した凡例にだけ**ぶら下がっており
（データオブジェクト 142 バイト、タグ 0、中身 22 バイト）、素のままの凡例には無い。

検索条件の文字列（`INVIEWPORT` 等）はどこにも現れない——**条件は文字列ではなくトークン列
（番号の列）**である。そもそも `(INVIEWPORT & (T=SYMBOL))` は ASCII で 25 文字あって
22 バイトに入らない。単純な 1 条件の 16 進（16 ビットずつ読んだ値を併記）:

```
9a 02  96 02  1e 03  96 02  09 03  0f 00  47 06  65 06  4f 06  a5 02  90 06
 666    662    798    662    777     15   1607   1637   1615    677   1680
```

- **6 番目の 16 ビット値が「条件が指すオブジェクトの型」**。検索条件だけが違う凡例を
  突き合わせると、変わるのは 6 番目だけだった:

  | 6 番目 | 検索条件 |
  | --- | --- |
  | 15 | `(INVIEWPORT & (T=SYMBOL))`（シンボル） |
  | 86 | `(INVIEWPORT & (T=PLUGINOBJECT))`（プラグインオブジェクト） |

  15 と 86 は**オブジェクトの型番号**そのもの（凡例自身が `type=86` なのが裏取り）。
  単純な 1 条件なら、この 22 バイトを写して 6 番目を差し替えるだけで条件を変えられる。
- **条件のトークン列の文法**（複数条件・グループ・文字列つきの凡例を 2 度ダンプして
  詰めた）。16 ビットずつ読む。**枠**は `666 662 798 …（条件）… 677 1680` で、`798` が
  `INVIEWPORT`。セレクタ（何で絞るか）と値の入れ方:

  | 値 | 意味 | 値の入れ方 |
  | --- | --- | --- |
  | 798 | `INVIEWPORT` | 無し |
  | 777 | `T`（タイプ） | **生の 16 ビット値**（11=グループ / 15=シンボル / 86=プラグインオブジェクト） |
  | 773 | `L`（レイヤ） | 文字列（マーカー 1627） |
  | 774 | `C`（クラス） | 文字列（マーカー 675） |
  | 808 | `PON`（プラグインオブジェクト名） | 文字列（マーカー 1627） |
  | 822 | 基準面 | 文字列（マーカー 1627） |

  **文字列は `<マーカー> 0 0 <UTF-16LE> 0`。** マーカーはセレクタごとに決まっているらしく
  （`773`/`808`/`822` は 1627、`774` は 675）、**比較の向きではない**——同じ `774 675` が
  「＝」でも「≠」でも出た。**比較の向きは条件の後ろに来る**（後置）: **1607 ＝
  「右項目のもの」（＝）／1606 ＝「右項目ではないもの」（≠）**。実例（ダイアログの 8 行と
  そのまま対応した）:

  ```
  666 662 798                                   ← 枠 ＋ INVIEWPORT
    777 11                             1607     ← タイプが ＝ グループ
    1637 773 1627 0 0 "共通" 0          1607     ← レイヤが ＝ 共通
    1637 1608 822 1627 0 0 "スクリーンプレーン" 0  1606  ← 基準面が ≠ スクリーンプレーン
    1637 1608 777 86                   1607     ← タイプが ＝ プラグインオブジェクト
    1637 774 675 0 0 "一般" 0            1607     ← クラスが ＝ 一般
    1637 1615 773 1627 0 0 "共通" 0      1607     ← レイヤが ＝ 共通
  1637 1615 1637 1608 1637 1615 677 1680        ← 閉じ
  ```

  **1637 / 1608 / 1615 は構造**（条件の区切りとグループの開閉）で、対応はまだ詰めていない。
  「いずれかの検索条件（OR）」と「すべての検索条件（AND）」の入れ子はこの 3 つで表されて
  いるはずなので、**グループの種類だけを変えた 2 枚**を差分に取れば決まる【未解決】。
- 書き込みは `TaggedDataCreate(legend, 'GrLe', 1, 0, 22)` ＋ `TaggedDataSet(..., i, &byte)`
  を 22 回、フィルタと同じく **`ResetObject` より前**に。器の 10 個の意味が解けていない
  ので**文書や VW の版をまたいで通用する保証は無い**——実機で「並ぶかどうか」を見て決める。

## 凡例イメージの正体はビューポート

SDK のヘッダを `GraphicLegend|LegendImage|ImageScale` で引くと、凡例は 4 つの内部 ID に
分かれている（`Kernel/API/MiniCadHookIntf.h`）:

| 定数 | 値 |
| --- | --- |
| `kInternalID_GraphicLegend` | 658 |
| `kInternalID_GraphicLegendImage` | 659 |
| `kInternalID_GraphicLegendFrame` | 660 |
| `kInternalID_GraphicLegendTitleFrame` | 661 |

ただし**これは `GetObjectTypeN` が返す値ではない**（あちらは `Kernel/API/Objs.TDType.h` の
節点型）。実機の凡例の中を `FirstMemberObj` / `NextObject` で辿って節点型を数えると:

```
凡例の中で見えた節点型: 0×102, 3×66, 10×6, 11×36, 86×42, 122×12
```

| 型 | 名前 | 中身 |
| --- | --- | --- |
| 0 | `kTermNode` | リストの終端 |
| 3 | `kBoxNode` | セルの枠 |
| 10 | `kTextNode` | 見出し・ラベル |
| 11 | `kGroupNode` | セルのまとまり |
| 86 | `kParametricNode` | 並べている PIO |
| 122 | **`kViewportNode`** | **凡例イメージ**（凡例 1 つに 1 つ） |

**つまり凡例イメージはビューポートで、「イメージの縮率」とはそのビューポートの縮尺**。
`ovGraphicLegendViewType` / `BgRenderMode` / `FgRenderMode`（`ObjectVariables.h`）が
ビューポートの属性そのものなのとも符合する。縮尺は通常のビューポートと同じ
`VWViewportObj::SetScale` ＋ `Update` で書ける。

- ヘッダだけから推測していた `kWorksheetImageNode`（＝56）は**実機の凡例に 1 つも
  入っていなかった**（`Get/SetWorksheetImageScaleFactor` は無関係）。
- **凡例イメージは作り直しの後にしか無い**（中身を流し込んだときに作られる）。
- **ビューポートの中へは潜らない。** 中身はそれが映している図そのものなので、潜ると
  デザインレイヤ全体を歩く。

## 打ち切った調査: 凡例のイメージの縮率を外から合わせる

**結論: プラグインからは合わせられない。** 変えられるのは凡例イメージ（＝ビューポート）の
縮尺＝**中身だけ**で、**セルの枠は既定（1:50）のまま残る**。中身だけ変わって枠が 1:50 と
いう半端な状態は「全部 1:50 で揃っている」より見た目が悪い。**手で OIP の「イメージの
縮率」を変えれば枠も中身も正しく変わる**ので、合わせたい利用者にはそちらを案内する。

| 何が | どこで決まる | プラグインから |
| --- | --- | --- |
| イメージの**中身**の縮尺 | 凡例イメージ（＝ビューポート）の縮尺 | **書ける** |
| セルの**枠**の大きさ | 凡例の内部状態（レコードの外） | **届かない** |
| OIP の「イメージの縮率」表示 | 同上（`ImageScale` は UI が書く控え） | **届かない** |

**枠は作り直しでは中身に合わせて組み直らない**——「中身を変えてから作り直せば枠も揃う」と
一度は読んだが、実機で否定された（中身 1/75・枠 1:50 のまま）。

決め手になった実測（同じ文書に、手で設定した凡例と SDK が置いた凡例を並べて全欄を比較）:

| | レコードの `ImageScale` | 絵 |
| --- | --- | --- |
| 手で OIP のポップアップを 1:5 にした凡例 | **5 に変わる** | **1:5 に変わる** |
| SDK が `SetParamReal` / `SetParamAsString` で 75 を書いた凡例 | **75 になる** | **変わらない** |

つまり `ImageScale` は縮率そのもの（ポップアップも「カスタム 1:」も同じ欄に落ちる）で、
**UI 側の書き込みだけがイメージの作り直しまで走らせている**。SDK の書き込みはレコードに
届いても、その副作用が起きない。`ImageScale` は UI が書く控えで、本体は別にある。

潰した道:

- **レコードを実数で書く**（`SetParamReal`）… レコードは変わる。絵は変わらない。
- **レコードを文字列で書く**（`SetParamAsString`。OIP の欄は文字列で入るので、同じ変換・
  通知の経路を通ることを期待した）… 結果は実数と同じ。
- **書く位置を総当たり**（作り直しの前／後／最後、undo イベントの内／外）… どれも同じ。
- **ポップアップ用の別の欄を探す** … レコードの全欄を実機で並べたが、種別 8（ポップアップ）は
  `TitleWidth` / `LayoutBy` / `SummarizeBy` / `SortBy` / `SortOrder` の 5 つだけ。縮率の
  ポップアップに当たる欄は無い。
- **文書内の全凡例を比べる** … SDK が書いている内容は、手で設定した凡例のレコードと
  一致している（＝「欄が足りない」のではなく「書き込み経路が違う」）。
- **パラメータ変更を PIO へ伝える** … `kParameterChangedReset` は PIO 側が受け取る
  メッセージで、外から送る API は無い（[Parametric Objects](Parametric%20Objects.md)）。
- タグ付きデータにもオブジェクト変数にも縮率は無い。
