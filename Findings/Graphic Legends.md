# グラフィック凡例

`GraphicLegend` PIO を SDK から生成・制御するときの知見。**公開 API がほとんど無く**、
実機のダンプで内部構造を割って初めて制御できた部分が多い。タグ付きデータの一般的な
読み書きの癖は [Tagged Data](Tagged%20Data.md) にある。ダンプ・生バイト・潰した道は
[計測記録](../Metrics/Graphic%20Legends.md)。

## 基本の作法

- **点で生成すると幅 0 に潰れる**（矩形モードの PIO）。`BoxWidth` を与える。
- 見た目（枠線・セル）は**クラスでは制御できない**ので属性として直接与える。
- スタイルを当てない場合は `SetPluginObjectStyle` も `UpdateStyledObjects` も呼ばない
  （中身は置いた時点の `ResetObject` で決まる）。**VW へ戻った後も追い付かない**
  （[実測](../Metrics/Graphic%20Legends.md#resetobject-を呼ばずに置いた凡例の実測245)）。
- **スタイルを当てる場合、スタイルの無い文書では凡例が空の箱**になる（名前が 1 文字
  違うだけで同じことが起きる）。処理の結果が図面の外の資源に左右される。

## ソース定義（何を並べるか）は公開 API では設定できない

- **ソース定義は PIO のパラメータでは設定できず、ISDK にも口が無い。既定のソースは空**
  なので、**スタイル無しで置いた凡例は何も出ない**（#245）。
- **「ビューポートでフィルタ」を設定する API も SDK に無い**【ヘッダ根拠】。公開されて
  いるのは `ovGraphicLegend*`（リセット中しか有効でない）と `eGraphicLegendCriteria` だけ。
  `IGraphicLegendCoreSupport` などはヘッダが SDK に同梱されていない
  （[検索の記録](../Metrics/Graphic%20Legends.md#ソース定義何を並べるかを設定する口を探した)）。
- 下の `'GrLe'` / `'GrLg'` を直に書くのが、いま分かっている唯一の道。

## パラメトリックレコードに載っているもの・いないもの

- **per-instance の設定（`SummarizeBy` / `SortBy` / `SortOrder` / `HideEmptyCells` /
  `LayoutBy` / `ScaleFactor` / `BoxWidth` など）はレコードに載っている。** 載っていないのは
  5 つのボタン（type=14）の先にある設定だけ。
- **フィルタはレコードにも関連（association）にも UUID にも無い**
  （[ダンプの比較](../Metrics/Graphic%20Legends.md#パラメトリックレコードに載っているものいないもの)）。

## 「ビューポートでフィルタ」の保存先はタグ付きデータ `'GrLg'`

凡例にぶら下がるデータオブジェクト（補助オブジェクトの連鎖）のタグ付きデータ。生バイトの
読み方・`'DMDT'` が「入れ物の入れ物」である点は [Tagged Data](Tagged%20Data.md)。

- **書き方**: `TaggedDataCreate(legend, 'GrLg', 15, 5, N)` ＋ `TaggedDataSet(…, i,
  &GetObjectInternalIndex(viewport))` を i = 0..N-1 で回し、**`ResetObject` より前**に呼ぶ。
  型 15 は `kTaggedDataObjectRefArrayTypeID`、値は**フィルタ先ビューポートの
  `InternalIndex`**。`'GrLg'` は `0x47724C67` と書く。
- **フィルタ先が複数なら同じ配列の要素数が増えるだけ**（要素数は `TaggedDataCreate` の
  最後の引数）（[実測](../Metrics/Graphic%20Legends.md#ビューポートでフィルタの保存先を探したタグ付きデータ-grlg)）。

## ソース定義の保存先は `'GrLe'`（条件はトークン列）

- **ソース定義の保存先は `'GrLe'`**（手で設定した凡例にだけある。中身 22 バイト）。
  **条件は文字列ではなくトークン列（16 ビットの番号の列）**。
- **単純な 1 条件なら、22 バイトを写して 6 番目の 16 ビット値（＝オブジェクトの型。
  15 ＝シンボル、86 ＝ PIO）を差し替えるだけで条件を変えられる。**
- 書き込みは `TaggedDataCreate(legend, 'GrLe', 1, 0, 22)` ＋ `TaggedDataSet` を 22 回、
  **`ResetObject` より前**に。**VW 2026 の既定テンプレートから開いた図面では並んだ**
  （#245。定義ごとに 1 行）。ただし**器の意味が解けていないので、文書や VW の版をまたいで
  通用する保証は無い**——実機で並ぶかを見て決める。
- 複数条件の文法（セレクタ・文字列・比較の向き）は割れたが、**`1637` / `1608` / `1615`
  （AND / OR の入れ子）の対応は【未解決】**——グループの種類だけを変えた 2 枚を差分に
  取れば決まる
  （[バイト列と文法](../Metrics/Graphic%20Legends.md#ソース定義の保存先を探したgrle)）。

## 凡例イメージの正体はビューポート

- **凡例イメージは型 `122`（`kViewportNode`）**で、「イメージの縮率」はそのビューポートの
  縮尺（`VWViewportObj::SetScale` ＋ `Update` で書ける）。`ovGraphicLegendViewType` /
  `BgRenderMode` / `FgRenderMode` がビューポートの属性そのものなのとも符合する。ヘッダの
  `kInternalID_GraphicLegend*`（658〜661）は `GetObjectTypeN` の値ではない。
- `kWorksheetImageNode`（56）は入っていない（`Get/SetWorksheetImageScaleFactor` は無関係）。
  **イメージは作り直しの後にしか無い**（中身を流し込んだときに作られる）。
- **ビューポートの中へは潜らない**（デザインレイヤ全体を歩くことになる）
  （[節点型の数](../Metrics/Graphic%20Legends.md#凡例イメージの中身内部-id-と節点型)）。

## 打ち切った調査: 凡例のイメージの縮率を外から合わせる

- **結論: プラグインからは合わせられない。** 書けるのはイメージ（ビューポート）の縮尺＝
  中身だけで、**セルの枠は既定（1:50）のまま**。枠は作り直しでも組み直らない。中身だけ
  変わって枠が 1:50 という半端な状態は「全部 1:50 で揃っている」より見た目が悪い。
  合わせたい利用者には**手で OIP の「イメージの縮率」を変える**よう案内する（枠も中身も
  正しく変わる）。

  | 何が | どこで決まる | プラグインから |
  | --- | --- | --- |
  | イメージの**中身**の縮尺 | 凡例イメージ（＝ビューポート）の縮尺 | **書ける** |
  | セルの**枠**の大きさ | 凡例の内部状態（レコードの外） | **届かない** |
  | OIP の「イメージの縮率」表示 | 同上（`ImageScale` は UI が書く控え） | **届かない** |

- **`ImageScale` は UI が書く控え**で、SDK から書いてもレコードが変わるだけで絵は変わらない
  ——欄が足りないのではなく書き込み経路が違う。`ImageScale` は縮率そのもの（ポップアップも
  「カスタム 1:」も同じ欄に落ちる）で、**UI 側の書き込みだけがイメージの作り直しまで
  走らせている**。本体は別にある。
- 教訓: 実数・文字列での書き込み、書く位置の総当たり、別欄の探索、全凡例の比較、
  タグ付きデータとオブジェクト変数まで潰した
  （[潰した道](../Metrics/Graphic%20Legends.md#打ち切った調査-凡例のイメージの縮率を外から合わせる)）。
  VW や SDK の版が変わらない限り再調査しない。
